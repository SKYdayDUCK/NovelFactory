# R1 补充需求追踪与跨模块验收边界

审查日期：2026-11-10。对象：`novel_factory_v2_0_r1` 设计包。本文追踪用户《统一世界时间线、动态知识演化与高并发 Agent 架构》补充要求，不替代各模块契约，也不宣称业务实现已通过验收。

**结论口径：设计覆盖、契约检查、有限机制实验、实际服务验收是四种不同证据。** 需求能在文档和 Schema 中定位，只说明已形成可开发的方案；依赖完整性、真实数据库并发、目标 Host 互操作、文学效果和服务容量仍须按阶段执行。

## 4. 关键契约覆盖与不能省略的校验

### 4.1 时间、查询与上下文

| 需求 | 明确契约 | 必须由业务实现保证的内容 |
|---|---|---|
| 查询作品/分支/修订/故事时间 | 核心 `WorldRef`，R1 `BranchSelector`、`RevisionSelector`、`SubjectTime`、`ResolvedReadCut` | `latest` 只在开始解析一次；游标/批量不得重新选取版本；branch 与 receipt 的祖先关系真实存在 |
| 事实、计划、误信、读者、模拟区分 | `KnowledgeCut`、`ReaderCut`、`TemporalSource`、`TemporalEntry` | plane 授权、actor 绑定、计划/文学清单和叙事 cut 正确；`FACT` 是 entry kind，不是另造世界 plane |
| 确认/未知/未推进/陈旧分开 | `TypedStateAnswer`、`StateQueryItem`、`QueryPayload`、`UnifiedQueryResult` | 原 `QueryAnswer` 的知识/求值/覆盖/索引状态有真实来源；不能用 `null` 混合多种状态 |
| 关系发生与有效期不同 | `OccurrenceTime`、`ValidityInterval`、`RelationTransition`、`TemporalRelationRecord` | 发生时间模糊时不擅自选端点；指定生效边界可晚于发生；关闭精确关系版本，保存证据 |
| 固定版本、读自己写入、可等推进 | `ReadContract` 及版本/过程/索引三个独立策略 | `WAIT_EXISTING_ADVANCE` 只等已有授权任务；不能把固定 revision 等成新 revision |
| 成包编译，硬约束完整 | `ContextCompileRequest`、`CompiledContext`、`ContextCompileResult` | recipe 不是权限来源；硬材料装不下必须失败/拆分；辅助 cut 不污染角色视角；同代输入不漂移 |
| 解释与 artifact 选择变化 | `ResolvedReadCut.interpretation_ref`、证书同名字段、`ScopeToken.INTERPRETATION` / `ARTIFACT_SELECTION` | 所有相关 writer 同事务更新守卫；相同 WorldRef、不同解释/计划选择不能误命中缓存或复用批准 |

`UnifiedQueryResult.status=PENDING` 表示等待已有推进作业的响应状态；普通 `ALLOW_PARTIAL` 查询可以返回 `READY`，而其状态载荷的 `evaluation_status=PENDING`。不能根据外层 READY 推断目标世界过程已求值，也不能把载荷 PENDING 一律包装成服务器启动了新模拟。

### 4.2 接受与效果

| 需求 | 明确契约 | 不能由 Schema 单独证明的内容 |
|---|---|---|
| 原客户端兼容 | 核心 `AcceptWorldRequest` / `CommitReceipt` | 原 strict HEAD 语义不变；新接口不能伪装为旧字段的宽松解释 |
| 无关旧输入可接受 | `AcceptancePrepareRequest`、`AcceptanceCertificate`、`GuardedAcceptRequest` | 仅注册封闭命令模板可申请；读写、负向范围、约束组、规则/覆盖/权限依赖须完整，不接受自由文本自报集合 |
| 审核到提交期间变化 | `ApprovalBinding`、`ScopeToken`、证书和实际提交父版本 | 短事务内再次验证载荷、任务代际、资格、当前权限、scope 与批准；必要时失效/重做，不静默搬运批准 |
| 防止幻读和写偏斜 | `PREDICATE_RANGE`、`RESOURCE_CONSTRAINT`、`SCOPE_REGISTRY` 等 token | 创建/删除/批量导入/修复/推进等所有写路径维护范围守卫；缺失登记不能安全返回“无变化” |
| 一个权威效果源 | `AcceptedEventR1`、`WorldChangeSetR1`、`RelationTransition` | 关系转换规范化为原效果槽位，不能同时在“图谱事件”和“资源事件”各扣一次 |
| 回包丢失、重复请求 | `GuardedCommitReceipt`、幂等键及不可变提案/效果身份 | key→payload 绑定、原结果可查、新 key 不绕过效果唯一约束；重放不重新推理已有裁决 |

## 8. 交叉审查结论与保留风险

本轮需求已明确落入时间、数据、版本、调度、编排、文学、接口和记忆主线；新增 13–15 承担专题展开。以下关键风险不能由纸面规范消除，实施时不可删除对应门槛：

- **依赖完备性**：受守卫接受只对服务器注册的封闭命令成立。自由语义提案、未登记跨域依赖或不完整负向范围继续保守处理。存在 token 类型不等于所有 writer 已正确维护它。
- **局部推进安全性**：入站影响通道与下界必须有完整登记和可复核来源。不能以“另一区域很远”代替安全证明，也不能以最慢全局前沿迫使所有地区串行。
- **关键投影与派生索引**：关键效果/前沿/失效屏障同事务；异步检索可以落后，但不能决定正式裁决。物理索引追平与故事过程推进是两件不同事情。
- **审批/权限随时间变化**：不可变内容缓存仍须检查当前权限；批准与解释/选择依赖必须绑定。单纯把 permission epoch 写进 key 但不检查当前值无效。
- **文学与效果等价**：MVP 的宏微细化只补表现。宏观事件替换为多个微事件时，中间可观察状态会影响角色认知；终态相同不足以证明等价。
- **并发和成本**：总连接预算、短事务、无状态服务提供扩展路径，尚未证明任一档位容量。必须报告过载失败和未知费用，不用拒绝请求的低延迟装作高成功吞吐。

设计包的结构/Schema/引用检查、独立机制模型和 15 行负载计算可以单独重跑；它们的通过结果不能更改业务案例的待执行状态。正式实施结果应另附冻结环境、真实执行证据、失败样本和限制，再由对应阶段门槛决定能否扩大范围。

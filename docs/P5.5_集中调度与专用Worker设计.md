# P5.5 调度及专用 Worker

| 固定消费组 | 业务处理 | 资格与完成收据 |
| --- | --- | --- |
| model | 角色、规划、写作、审核等已经登记且 READY 的岗位 | PostgreSQL 重查项目、Grant、epoch、知识边界及预算，原 generation、租约、调用账本和 GLOBAL/WORK/ROLE 额度继续生效 |
| world | 核查已持久化的联合裁决、编辑交接、卷级推进及角色候选 | 原 RuntimeSupervisor、Kernel、审核回执及幂等键 |
| compute | 按原 WorldRef 生成图谱和时间线 | 复用 DerivedWorldWorker 和版本化投影 Inbox，水位禁止回退 |
| recovery | 恢复过期任务、唤醒等待项、暂停已有不确定调用的 READY 任务 | 原 WorkflowService；SENT/UNKNOWN 须对账 |
| log | 记录规范化审计 | LogService 与本组收据同事务 |
| statistics | 推进统计投影 | StatisticsService 与本组收据同事务 |

服务端注册表位于 `novel_factory.orchestration.processors`。处理器名称、工作类型、输入版本、输出、权限、资源、最大并发、时间预算和故障处置均有声明。服务进程从启动参数选择消费组，消息字段不能选择 Python 代码。

### 启动与切换

1. 升级迁移并运行 relay。分别运行 `python scripts/run_processor.py --group model`、`--group world`、`--group compute`、`--group recovery`、`--group log`、`--group statistics`。这些基础设施进程不持有角色模型凭据。
2. 用现有私有项目凭据执行 `python scripts/run_supervisor.py --access-file project.json --set-transport redis`。单独部署项目执行器，如 `python scripts/run_supervisor.py --access-file project.json --processor model --workers 2`。world、compute、recovery 同理。未配置的分支默认走原 P5 入口。
3. 消费者的业务效果是向目标作品、分支、处理器写入一条可合并的持久唤醒信号。提交收据后释放连接，再由持有该项目凭据的进程读取权威状态。一个全局消费者可以为不同作品保存唤醒信号，但不能替任何角色调用模型。收据信号表示已调度，任务完成由原业务回执判定。每次恢复服务和定期到期都执行有界扫描，补回丢失的临时通知。
4. 模型领取与 transport 切换共用原数据库准入锁，已发送调用可继续完成；回退时执行 `--set-transport postgres`。旧版 P5 二进制不识别新围栏，部署时须先升级所有 Supervisor。回退时切换回 PostgreSQL 再降级。数据库额度从不随模式切换而增加。
5. 并行部署各组的消费者及多个作品执行器。每个 intake 进程的 PostgreSQL 连接上限为 `workers + int(adaptive)`，Redis 连接上限为 `workers + 1`。每个项目父进程另计 `max(5,workers+2)` 个池连接和 1 个 LISTEN 连接。compute 的每个子进程再计 1 个池连接。举例，1 个 relay + 6 个单线程固定消费组 + 1 个作品的 4 类项目进程（每类 2 workers）合计配置上界为 **34 个 PostgreSQL 连接和 14 个 Redis 连接**。可同时运行的每个独立 MCP stdio 另加 2 个数据库连接，备份、管理及其他客户端单列。不同分支可同时工作，正式世界写入保留原 Kernel 约束。

恢复进程仅在数据库中核对已有状态。处于等待中的卷和无 READY 项目不会触发新的模型调用。每个派发循环和接收批次有界。DECLARE 的耗时上界用于容量规划，数据库 statement/lock timeout、模型路由自身 timeout 和原租约负责具体中断或回收，缩容不强杀在途工作。

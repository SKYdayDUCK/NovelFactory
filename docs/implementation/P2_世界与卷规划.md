# P2-01｜世界底稿审核、卷契约与滚动计划

## 语义与数据边界

本实现沿用 v2.0-R1 模块化单体：PostgreSQL 继续保存世界版本、不可变对象与应用收据，没有新建第二份人物/资源真源。新增 `PlanningService` 只写规划产物、选择指针、依赖守卫与 outbox；这些操作的 `world_effects_applied` 恒为零。

`WorldDossier` 必须绑定当前作品的正式 `RULESET`、`INITIAL_SETUP` 和明确世界切面。结构底稿包含地理、历史、制度、资源、力量体系、未出场背景、势力代表及“移除主角后仍会做什么”。背景身份必须在已接受初始底稿中存在；势力和代表必须分别是组织和人物。段落与动机为有来源的审阅材料，其文本本身不赋予人物资源、认知或能力。

世界设置仍由受信作者初始化或 Kernel 世界提案与接受确立。`proposed_world_changes` 只记录尚未正式接受的差异，非空时不允许批准该底稿；不能用“审稿通过”的字符串替代世界接受。底稿批准要求独立审核主体、准确版本及无阻断问题。未出场背景已有正式版本保护，不因没有进入卷纲而消失。

保留原 `literary.schema.json` 的 VolumeContract 与 WindowPlan，不改变 core 2.0 或 temporal 2.1 旧契约。规划增量独立放在 `planning.schema.json`，注册版本名 `planning`。VolumeContract 的既有 `dependency_fingerprint` 作为上游记录保存，不被当作可信授权或接受证书；采用时使用服务端读取的世界版本、合同引用、节点前提和选择 CAS。

## 主要接口

| 应用接口 | 输入 | 结果与门禁 |
|---|---|---|
| `save_world_dossier(principal, payload, key)` | WorldDossier | 返回不可变 WORLD_DOSSIER 引用；校验 WORLD 角色与来源 |
| `review_world_dossier(principal, world_ref, dossier_ref, decision, issues, key)` | 指定底稿与批准/返工决定 | 独立 APPROVE 主体、最新世界切面；返回 DossierReview |
| `save_volume_contract(principal, payload, key)` | 原 VolumeContract | 返回 VOLUME_CONTRACT；保护承诺必须引用已存在的作品政策 |
| `save_window_plan(principal, payload, volume_contract_ref, key)` | 原 WindowPlan | 仅接收 DRAFT；核验真实 process 登记、窗口和接受事件 |
| `save_plan(principal, payload, key)` | PlanRevision | 保存候选，不自动采用；拒绝未知身份、虚假 realized 证据、硬依赖环 |
| `get_plan(principal, work_id, plan_ref)` | 明确计划引用 | PLAN profile 与 PLAN_READ 交集；角色行动者不能旁路读取 |
| `adopt_plan(principal, world_ref, plan_ref, expected_plan_ref, key)` | 精确候选和预期旧选择 | APPROVE、HEAD 和旧选择 CAS；返回计划引用及 PLAN 查询切面 |
| `replan(principal, payload, key)` | ReplanRequest | 根据已接受变化产生新候选及 ReplanReport，随后单独采用 |
| `bind_task(principal, task_id, generation, plan_ref, node_ids, key)` | 已在 TaskSpec 内冻结的计划、节点范围 | 不可变计划绑定与节点守卫；不改变同代输入 |
| `validate_task_plan_binding(repo, kernel, task, spec=None)` | 当前事务内任务 | 同步验证当前世界与节点依赖，阻断已失效计划；无绑定时保留 P1 行为 |

API 的 `key` 均为业务幂等键。同键异内容拒绝；丢回执后原请求可以取回同一已记录引用。创建另一个计划修订必须有新的 ID 与键，不能覆盖旧草稿。

## 动态规划

PlanNode 区分 PROPOSED、VIABLE、BLOCKED、REVIEW_REQUIRED、ABANDONED、REALIZED。VIABLE 只说明输入切面中的已声明前提成立，不保证未来结果。REALIZED 必须引用该 WorldRef 实际选中的事件；它仍是编辑对目标完成的有证据判断，不是自动世界事实。

可计算的前提为实体存续、当前关系等于给定值、当前资源达到下限、指定事件版本仍被选中。无法确定的状态返回 UNRESOLVED，不把未知当作 false。动态影响沿 HARD_PREREQUISITE 传播阻断；ALTERNATIVE、CAUSAL_RISK 和 LITERARY_PROMISE 引发复核，不被错误提升为必然失败。

局部重规划保留全部旧节点（失败节点可以明确 ABANDONED）、未受影响节点、已实现后果、合同与保护承诺、已发表前缀。替换只允许位于受影响依赖闭包的未来节点；新增路线必须连接到该范围。它保留全部取舍选项和理由，不把不满意的故事结果包装成技术重试。采用是另一受控操作；创建候选不会抢占正在使用的旧计划。

`PlanRevision` 通过适配生成既有 `kernel.PlanManifest`，统一查询可直接使用采用回执的 `knowledge_cut={plane:PLAN, plan_manifest_ref:...}`。原 P1 PlanManifest 明确只表达未来计划，因此 REALIZED 节点不塞入其禁止 fulfillment 的字段；它们保留在 PlanRevision 及实际 EventRef 中。BLOCKED 节点适配为 INVALIDATED，ABANDONED 为 CANCELLED，旧清单仍可按明确引用读取。

## 并发、失效与恢复

计划采用使用工作行锁保护选择不存在时的首次 CAS，再按内核顺序锁定分支。锁内不等待模型、网络或用户；对象先写入后注册。新选择更新 `PLAN:<volume_id>`、`PLAN_MANIFEST:<volume_id>`，并同步提升其 ARTIFACT_SELECTION 守卫。只有发生变化的节点提升 `PLAN_NODE:<volume_id>:<node_id>`，新 scope 同步提升 SCOPE_REGISTRY。

`bind_task` 要求计划已经冻结在该 TaskSpec 的 input_artifacts 中，并固定该任务代际的节点守卫。选择变更事务将依赖已变节点的任务标为 STALE，迟到输出仍由 P1 结果账保留。未变节点不会因无关卷纲修改而自动废弃。

仅等异步重规划不够：销毁必要道具接受后，旧任务可能先于重规划 worker 返回。`validate_task_plan_binding` 在实际资格检查中读取当前世界，重算前提及类型依赖闭包，同时核验 canonical 指针、解释版本、已实现前置事件、节点选择 epoch 和固定输入。相关前提已破坏或仍未知就阻断，不能静默继续。正式接受事务需要调用这一检查；网关在派发/收件处也应使用同一门禁。

计划产物、收据、选择、依赖、任务和 outbox 使用现有数据库与对象恢复机制；没有额外文件路径权威或需要另恢复的内存计划状态。世界历史、原计划、失败候选和重规划报告均不可变。

## 验证与当前边界

定向检查包括：

- 底稿引用伪造规则、未接受设定阻断、正式背景保留且世界版本不变。
- 未来计划查询为 PLAN；character_actor 不能通过计划读取旁路得到未来；同键异内容拒绝。
- 毁剑后即使重规划还未运行，旧后继任务的资格已同步失效。
- 局部重规划保留无关节点、合同、真实损失和被拒选项；只围栏相关任务。
- 真假 realized 证据、过时世界采用、凭空保护政策、依赖环、未知与失败区分。
- 两个独立 PostgreSQL 连接并发首次选择只能成功一个，另一个得到 PLAN_SELECTION_CONFLICT。

2026-11-10 在 PostgreSQL 17.11（fsync/synchronous_commit 开启）执行初始定向集成 6 项与纯规则 5 项，共 11 项通过。原始 JUnit 和服务会话见 `evidence/p2/batch1/planning.xml`、`planning-pg-pass/`。保留此前缺 cursor 的契约夹具失败和重复测试模块名导致的 collection 失败 XML；修复的是测试输入/命名，不是削弱业务断言。后续增加的回归及跨模块结果以最终开发报告为准。

本模块不声称完成真实模型调用、文学质量评估或作者阅读。自然语言目标是否合理、某个事件是否充分实现文学目标仍需要有证据的编辑决定。普通事件接受、资源守恒、角色认知、历史修订和正式发行均由原有内核及相应生产模块承担，规划不能豁免它们。

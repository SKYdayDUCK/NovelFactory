# P4-02 恢复与升级运行手册

## 适用范围

本手册对应仓库中的 PostgreSQL 17、单机 POSIX/本地 Windows NTFS 内容寻址对象存储及现有世界时间线。在线逻辑备份、空目标恢复、命名 WAL 恢复点演练、任务代际隔离和兼容元数据升级均有可执行入口；各入口的平台验证范围见下文。正式运行前应固定源码、依赖、Schema、运行时目录及配置，并保留对应 GitHub 提交和测试证据。[实现入口](../../src/novel_factory/infrastructure/online_backup.py)

当前物理恢复入口是**生成数据的隔离演练**，不接受生产数据库 URL；它不是通用生产集群恢复命令。未实现跨 PostgreSQL major 的原地物理恢复、通用解释器语义迁移、远程对象存储恢复或自动供应商账单核验。运行时升级仅允许规则 `version`、解释包 `package_release` 的元数据变化，其他语义字段必须相同。[升级边界](../../src/novel_factory/application/upgrades.py)

## 1. 在线逻辑备份、校验与空目标恢复

使用 Python 3.12 和可调用的 PostgreSQL 17 工具。以下路径和 URL 是操作员应替换的隔离环境示例；`PG_BIN` 应同时包含 `pg_dump`、`pg_restore` 等工具。备份目录必须不存在，恢复数据库及恢复对象目录必须为空。连接URL须显式给出PostgreSQL用户、单一TCP主机、端口及数据库；仅支持sslmode/sslrootcert/sslcert/sslkey四项单值查询参数。存在PGHOSTADDR、PGSERVICE或PGSERVICEFILE环境路由，或URL含hostaddr/service、多主机、Unix socket、conninfo式数据库名时，会在连接及创建目标前报BACKUP_TARGET_AMBIGUOUS。此限制避免SQLAlchemy与pg_dump/pg_restore实际指向不同数据库；应整理为明确URL并清除歧义环境。

```bash
export PG_BIN=/absolute/path/postgresql-17/bin
export NF_DATABASE_URL='postgresql+psycopg://nf_dev@127.0.0.1:56460/nf_sandbox'
export NF_OBJECT_ROOT=/absolute/path/nf-sandbox-objects
NF_DR_BACKUP=/absolute/path/new-nf-backup

uv run python scripts/backup.py create "$NF_DR_BACKUP" --online \
  --report "${NF_DR_BACKUP}-create.json"
uv run python scripts/backup.py verify "$NF_DR_BACKUP" \
  --report "${NF_DR_BACKUP}-verify.json"
```

`--online` 使用一个导出的 PostgreSQL MVCC 快照，同时生成逐表摘要与 `pg_dump`。它持有共享对象保留锁，正常业务写入可以继续，GC 不得删除该切面引用的对象。源码、Schema、角色/技能/权限资产的完整成员与哈希在数据库快照之前固定；复制完成后再次核对。备份期间部署变化、对象缺失或复制内容不符会阻止状态变为 `COMPLETE`。Schema 迁移应另行安排。省略 `--online` 使用已有的独占维护门逻辑备份。[备份 CLI](../../scripts/backup.py)

校验必须确认完整 manifest、数据库 dump 哈希、全部对象哈希/大小、保存的解释器文件和运行时资产，以及当前安装版本与备份匹配。不要只检查目录或 dump 是否存在。恢复时默认要求使用备份对应的已安装代码和资产；版本不匹配应先准备对应环境，不跳过检查。

```bash
# 由操作员事先创建并确认新的空数据库；此命令不会覆盖已有业务表。
export NF_RESTORE_DATABASE_URL='postgresql+psycopg://nf_dev@127.0.0.1:56461/nf_restore_empty'
uv run python scripts/backup.py restore "$NF_DR_BACKUP" \
  --restore-object-root /absolute/path/new-restored-objects \
  --report "${NF_DR_BACKUP}-restore.json"
```

恢复顺序为：验证备份 → 验证空目标 → 复制并校验对象 → `pg_restore` → 比较所有数据库表摘要 → 隔离恢复任务代际。只有 `snapshot_equal_before_fencing=true` 才说明恢复数据库与备份切面完全一致；任务隔离会随后有意改变任务输入、租约、未知调用和 outbox 状态。恢复期间保持 API、任务工作者和 outbox 派发停止，完成以下对账后再放行。[恢复与 fencing](../../src/novel_factory/infrastructure/recovery.py)

## 2. 命名 WAL 目标的真实隔离演练

下列命令自动创建两个独立集群、生成业务数据、设置本地 WAL 归档并执行故障恢复。输出目录必须为新目录；端口自动选择。该独立CLI进程会清除继承的libpq连接环境（保留PG_BIN工具路径），保护直接SQLAlchemy和工具子进程的目标一致性；这不会修改调用者进程的环境。显式恢复检查在python -O下仍会执行。`--keep-clusters` 保留已停止的集群、base backup、WAL 和对象用于独立检查；省略时，成功后清理这些大文件，保留结果与日志证据。

```bash
NF_DR_EVIDENCE=/absolute/path/new-nf-pitr-evidence
uv run python scripts/pitr_drill.py --pg-bin "$PG_BIN" \
  --output "$NF_DR_EVIDENCE" --keep-clusters
```

脚本的可审核顺序是：

1. 接受第一条真实世界事件，建立已发送但未结算的调用预算；执行 `pg_basebackup -Xstream --manifest-checksums=SHA256` 和 `pg_verifybackup`。
2. 接受目标事件，生成目标逻辑快照及对象清单，再创建命名恢复点 `nf_p4_verified_target`。
3. 故意接受一条更晚的世界事件；切换 WAL，确认相关段已归档且归档文件不可被不同内容覆盖。
4. 杀死本演练创建的源进程组，将 base backup 复制到新目录，通过 `recovery.signal`、`restore_command`、`recovery_target_name` 和 `recovery_target_action=promote` 恢复。
5. 等待脱离 recovery 状态，逐表比较目标切面，复制并验证目标对象，验证认证、正式 HEAD、旧历史、后续提交排除、任务 fencing、未知预算保留和原提交回执。

本演练独占生成的数据，目标逻辑快照与命名恢复点之间没有应用写入。**不能直接将这一前提推广到任意线上写入负载**：生产 PITR 的对象清单必须与恢复点建立明确一致性协议。数据库回退也不会撤回供应商调用或外部发布，恢复点之后的外部效果仍须独立对账。[完整脚本](../../scripts/pitr_drill.py)

首先查看 `result.json`；`status=PASS`、`snapshot_equal_before_fencing=true`、`target_commits_lost=0`、`old_worker_rejected=true` 和 `original_commit_receipt_equal=true` 是本演练的关键结果。再结合 `file_checksums.json`、`target_database_digests.json`、源/恢复日志和 fenced task 清单检查。任何断言、对象或 WAL 失败都不能当成成功恢复。

## 3. 恢复任务、UNKNOWN 与预算

恢复会把未终结任务推进到新的 `generation`，保存新的不可变任务输入，置为 `PAUSED` 并清除租约/执行身份；`SENT` 调用转为 `UNKNOWN`，已占用的费用与 token 预留保留；正在派发的 outbox 回到 `PENDING` 并推进派发代际。已接受的世界事件、旧修订、正式回执不因 fencing 被改写。

恢复顺序如下：

1. 用恢复报告中的旧/新任务代际和现存 `call_attempts` 清单建立对账范围。对 `PREPARED`、`SENT`、`UNKNOWN` 逐笔核对 `attempt_id`、请求哈希及供应商回执；证据不足继续保持未知。
2. 在受控运维进程中，依据已保留的供应商证据调用 `TaskService.settle_call(...)`。`PREPARED` 只能确认为未发送后按零费用、零 token 取消；已知结算须包含实际使用量与回执，不能把未知随意结算为零来释放预算。超出预留的费用需要另行处理，当前接口会拒绝。
3. 只有未决调用都已对账后，才通过受控维护流程调用 `TaskService.resume(task_id, expected_generation)`。重新 claim 并编译新代际上下文；旧工作者、旧证书和旧代际不能复用。
4. 再启用消费者和接入，核验必要的正式回执、派生工作者积压与 inbox 去重。outbox 是至少一次派发；恢复事务不承诺撤回灾难前已发生的外部副作用。

`TaskService` 的结算/恢复方法是内部可信运维接口，并非本文提供的公开、带身份验证的 HTTP 对账入口。当前系统没有自动向真实供应商核实未知调用的实现；没有外部证据时保持任务暂停是正确结果。[任务状态与预算实现](../../src/novel_factory/orchestration/tasks.py)

## 4. Schema、规则与解释器版本升级

先在隔离恢复副本运行目标代码和迁移，再决定业务切换。当前真实迁移回归从 `0002` 建立并接受 P1 世界事件，执行 `alembic upgrade head`，比较所有既有表（除迁移版本表）的摘要，并验证原正式提交回执与 HEAD。当前 head 为 `0003`；这证明已有的加法迁移路径，不能证明未来任意迁移或 downgrade。[迁移测试](../../tests/integration/test_p2_upgrade.py)

兼容运行时版本使用以下应用流程。HTTP入口分别为POST /api/v1/runtime-upgrades/prepare、POST /api/v1/runtime-upgrades/reviews和POST /api/v1/runtime-upgrades/activate，沿用Bearer身份、严格请求Schema及现有背压边界。

| 顺序 | 应用方法 | 操作要求 |
| --- | --- | --- |
| 准备 | `RuntimeUpgradeService.prepare(controller, request)` | 当前 canonical HEAD；非角色 WORLD/ADMIN；仅允许包版本元数据变化；重放选中历史并比较原投影哈希 |
| 审核 | `review(reviewer, request)` | 不同主体、有效 APPROVE 权限、精确包引用和明确审核记录 |
| 激活 | `activate(controller, request)` | 复核双方授权代际、当前 HEAD、源包及审批对象哈希；CAS 推进正式世界版本 |

请求 Schema 在 `contracts/upgrades.schema.json`；实际调用样例在 `tests/integration/test_runtime_upgrades.py`。包、批准、源规则和解释对象缺失或损坏时拒绝继续。相同请求和幂等键用于响应丢失恢复；同键不同内容拒绝，过期 HEAD 应重新准备并审核。激活追加新世界修订与 interpretation epoch，失效旧上下文/证书，沿用原世界状态和事件选择，不追加世界效果，既有正式接受回执仍可恢复。

改变 reducer、日历、谓词、资源下限等语义会返回 `UPGRADE_REQUIRES_REPAIR`。不以修改标签替代迁移证明，不直接改旧事件或指针。回退兼容元数据可作为新的受审阅兼容版本记录；实际程序或 Schema 回退须经过对应的恢复验证，不能直接降低版本号或执行未验收的 downgrade。

## 5. 模型配置变更与回滚边界

模型路由是作品级设置。HTTP入口为POST /api/v1/model-routes/select；只有应用构造器create_app(model_adapters=...)由可信服务配置注入的adapter可被选择，默认没有可选adapter，请求不能提交任意供应商URL或配置。先在服务端注册带固定安全配置的 adapter ID，再在当前 canonical HEAD 调用 `select_model`，使用当前 `expected_ref` 比较交换。仅有局部分支 ADMIN 的身份不能修改它。配置变化必须使用新的 adapter ID；同一 ID 对应不同指纹会返回 `MODEL_CONFIG_CHANGED`。

之后不显式指定 adapter 的 `AgentGateway.prepare_input` 使用选中路由；已存在的 `AGENT_INPUT` 保留原模型配置及运行时指纹。模型切换不会给旧任务偷偷替换配置，也不会解除未决调用的预算屏障。回滚默认路由可以重新选中仍然安装、指纹未变的旧 adapter，仍须通过当前选择 CAS；既有任务要按其冻结配置继续，或通过正常取消/重建流程处理。

这里验证的是配置冻结与选择语义。`TEST_FIXTURE` 适配器不证明真实模型可用、供应商稳定性或文学质量。

## 6. Windows 对象恢复与资源测量

### NTFS 只读历史对象

历史 POSIX 写入器以 `0444` 发布对象；经 WSL 写入 NTFS 时，文件可能带有 Windows `READONLY` 属性。Windows 的 [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) 要求句柄具备写访问，直接以只读句柄调用会失败，而 `READONLY` 又会阻止打开具备写访问的普通文件句柄。不能以“读得到字节”替代持久化确认。

`ObjectStore.verify` 的兼容路径先取得同对象跨进程锁，短暂清除 `READONLY` 以打开可 flush 的句柄，再恢复该属性，最后通过只读 Python 流计算 SHA-256、检查大小并执行真实 `os.fsync`。对象字节和 ACL 均不修改；普通可写对象仍可并发读取。哈希不符、flush 失败或属性恢复失败都不得返回成功；普通 ACL 拒绝也不会被当作恢复授权。[对象核验](../../src/novel_factory/infrastructure/objects.py)、[文件适配](../../src/novel_factory/infrastructure/native_files.py)

同对象锁名为对象目录 `tmp/durability-<sha256>.lock`，核验后保留。不要在线删除这类 sidecar：旧等待者与新打开者可能因此锁住不同文件身份。GC 只清理既有 `upload-` 临时文件，不清理这些锁。顺序保持为全局 store 锁 → 同对象锁；引用事务持全局共享锁至数据库提交，GC 先取全局独占锁再读取数据库引用、核验对象。兼容路径不将共享锁升级为独占锁。异常退出会尝试恢复属性；强杀或断电落在转换窗口时，不能承诺属性已恢复，重新接管仍须完整执行哈希与持久化核验。

本轮实际验证范围如下；这些结果不代表全库或所有备份/PITR 入口均已在 Windows 通过。

### Windows 资源指标口径

[进程服务测量](../../benchmarks/process_server.py)在 Windows 使用 `GetProcessTimes` 的用户态/内核态 CPU 累计值，按每秒一千万个 tick 换算为秒；报告中的 CPU 数值是服务采样基线到 snapshot 的差。内存取 `GetProcessMemoryInfo.PeakWorkingSetSize / 1024`，即进程生命周期峰值工作集 KiB，不能用当前 `WorkingSetSize` 冒充峰值。Linux 保留 `getrusage` 的 CPU 秒和 `ru_maxrss` KiB 路径。[Windows CPU 定义](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes)、[峰值工作集定义](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters)

`service_sum_peak_rss_kib` 是各服务进程生命周期峰值之和，各进程峰值可能发生在不同时刻；它不是同时内存占用，也不是压测窗口内新增内存。比较实验时应保留 `service_processes` 的逐进程值及相同的测量窗口。

## 7. 最小复核命令与交接

```bash
uv run python -m pytest tests/unit/test_online_backup_runtime.py -q
uv run python scripts/with_postgres.py --pg-bin "$PG_BIN" -- \
  uv run python -m pytest tests/integration/test_online_backup.py \
  tests/integration/test_runtime_upgrades.py tests/integration/test_p2_upgrade.py -q
```

每次交接保留代码/部署版本、备份 manifest、目标世界引用、目标恢复点或 LSN、对象与运行时哈希、实际恢复验证、fencing 和 UNKNOWN 对账清单、命令与环境、耗时定义及未解决问题。大体积数据放执行产物，仓库保留脚本和证据索引。远程提交与 GitHub Actions 状态以 `reports/P3_P4_开发与验收总报告.md` 和 `reports/P3_P4_独立审核交接.md` 的最终阶段记录为准；本文不预先宣称未完成的远程 CI 通过。

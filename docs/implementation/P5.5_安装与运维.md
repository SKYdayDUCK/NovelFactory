# P5.5 本地安装与运行

## 依赖与凭据

使用 Python 3.12、PostgreSQL 17、仓库锁定的 Python 依赖和支持 XAUTOCLAIM 的 Redis。验收组合为 PostgreSQL 17.11 和 Redis 8.0.2。Linux 或 Windows 的 WSL2 可分别安装 PostgreSQL、Redis 和 uv；Windows 使用 WSL 内的代码、虚拟环境、权限和数据库运行后台服务。安装前核对 `postgres --version`、`redis-server --version`。保留原 P5 对象目录、模型路由和项目绑定。Compose 中现有 PostgreSQL 也可与单独启动的 Redis 配合使用。

1. 在源码根目录运行 `uv sync --locked --group dev`。将 NF_DATABASE_URL、NF_OBJECT_ROOT 和本进程所需的配置写入服务账户的私有环境文件。按 P5 手册分别签发作者恢复绑定和服务端项目凭据。
2. 备份 PostgreSQL 与对象目录，运行 `uv run --no-sync python -m alembic upgrade head`。旧任务、等待边和模型账本使用原表。已有服务部署要在切换前更新所有 Supervisor。
3. 使用独立 Redis 数据目录、私有 ACL 文件以及 [Redis 配置](../../configs/redis-eventhub.conf) 启动实例。ACL 配置、备份、重放和裁剪约束见[消息总线设计](../P5.5_RedisStreams消息总线技术设计.md)。服务进程通过 NF_REDIS_URL 读取属于自己用途的凭据。一个 Redis 数据库只绑定一个权威 PostgreSQL 部署。
4. 设置 `ACCESS=/var/lib/novelfactory/private/m0/supervisor.json` 为服务端项目凭据路径。用下列入口启动服务；常驻命令分别在服务管理器或独立终端中运行。

|实例|命令（均从项目根目录运行）|
|---|---|
|每个部署至少一个 Relay|`.venv/bin/python scripts/run_eventhub.py relay`|
|每个接收组一个或多个实例|`.venv/bin/python scripts/run_processor.py --group GROUP`。GROUP 取 model、world、compute、recovery、log、statistics。|
|绑定作品的四类执行器|`.venv/bin/python scripts/run_supervisor.py --access-file "$ACCESS" --processor TYPE --workers N`。TYPE 取 model、world、compute、recovery；首次可各用 1，模型并行需要现有硬配额允许。|
|开启此作品分支的 Redis 调度|`.venv/bin/python scripts/run_supervisor.py --access-file "$ACCESS" --set-transport redis`|
|检查积压与独立订阅状态|`.venv/bin/python scripts/run_eventhub.py status`|
|裁剪已完成的流条目|`.venv/bin/python scripts/run_eventhub.py trim --limit 1000 --retention-seconds 86400`，由维护身份周期运行。|
|查询统计差异|`.venv/bin/python scripts/p55_statistics.py --binding "$STAT_BINDING" verify`，使用受权管理账户。|

STAT_BINDING 指向单独的 0600 项目管理绑定，带 token、database_url、绝对 object_root 和包含 work_id、branch_id 的 binding。统计查询在服务端重新核验 ADMIN 权限。

环境参数示例见 [environment.example](../../configs/environment.example)。可在支持的工作进程后追加 `--adaptive`，`--workers` 设定该进程天花板。部署前累加各服务的连接上限、监听连接、维护连接及正式 API 预留，再配置实例数量。部署资源受限时，从一个项目、每组一个接收者、低执行配额开始。

## 使用 systemd

仓库在 adapters/systemd 提供 relay、intake@、project-worker@、retention 和 retention.timer 单元。它们使用 /srv/novelfactory 的虚拟环境和 novelfactory 服务账户。将单元安装到 /etc/systemd/system 并执行 daemon-reload。为每个实例建立相应的 0600 环境文件：relay.env、intake-GROUP.env、project-TYPE.env、retention.env。project-TYPE.env 包含 NF_ACCESS_FILE、NF_WORKERS、数据库和对象目录配置；配置模型及能创建后续模型任务的控制器时，还需匹配登记任务的模型路由。retention.env 配置维护身份及 NF_RETENTION_SECONDS。凭据保存在部署环境。

```bash
systemctl enable --now novelfactory-relay.service novelfactory-retention.timer
for group in model world compute recovery log statistics; do
  systemctl enable --now "novelfactory-intake@$group.service"
done
for processor in model world compute recovery; do
  systemctl enable --now "novelfactory-project-worker@$processor.service"
done
```

模板命令针对单个项目提供。多作品可分别部署带各自访问文件的执行器，传输层接收者可共享。Windows 的 WSL2 若未启用 systemd，可用前面的命令直接运行并由外部服务管理器托管。

## 故障与回退

Redis 中断后，先查 status 的 relay backlog、最久等待、各组 PENDING/DEAD 及 Redis 状态。恢复同一实例并启动 Relay 和所需接收组后，观察 backlog 回落并核对 PG 回执。对 DEAD 先修复处理器，再执行 redrive。核对统计时保留 source_cut 与 metric_version。UNKNOWN 外部请求按 P5 账本对账。

停用某项目的 Redis 调度时，先运行 `scripts/run_supervisor.py --access-file "$ACCESS" --set-transport postgres`（使用项目虚拟环境的 Python），确认新领取走 P5，再停专用执行器并启用原 Supervisor。模式切换保留在途调用。只有空扩展可直接执行 schema downgrade；活跃审计、订阅或配额数据应先按迁移守卫归档或从隔离备份恢复。物理恢复测试使用 `python scripts/pitr_drill.py --with-redis --output NEW_DIRECTORY`，演练会创建独立的 PG 和 Redis 实例。

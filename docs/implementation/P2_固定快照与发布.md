# P2-06：固定快照写作与内部正式发布

实现入口为 `application/release.py`；纯依赖图、顺序和版本差异规则位于
`domain/releasing.py`。新增契约是 `contracts/release.schema.json`，版本 2.2。
原 `core.schema.json` 中 2.0 `ReleaseManifest` 保持原样。

这部分交付的是可运行的固定输入写作、正式正文交接、统一世界切面对账和内部冻结流程。
它不执行世界效果，不向外部平台发送内容，也不把工程夹具的审稿判断当作文学质量证明。

## 1. 依据与边界

对应 [路线 P2-06](../11_研发路线与测试计划.md)、[生产线第 6–10 节](../07_剧情与文学生产系统.md)、
[R1 并发协议](../14_高并发服务与一致性协议.md) 中的固定快照、正文/世界接受分离、显式重验证及批准绑定要求。

| 边界 | 执行服务 | 可产生的结果 |
|---|---|---|
| 世界接受 | `Kernel.propose/prepare/accept` | 新世界事件、权威投影、过程进度 |
| 场景正文与事实对账 | `NarrativeService` | 固定正文、抽取、服务器对账及 AlignmentReport |
| 正文接受 | `NarrativeService.accept_narrative` | 零世界效果的不可变 NARRATIVE_ACCEPTANCE |
| 全文覆盖、多尺度审核与整卷编辑 | `ReviewService` | 精确正文绑定的 EDITORIAL_APPROVAL |
| 内部正式冻结 | `ReleaseService.freeze` | core ReleaseManifest、ReleaseRecord、活动版本 CAS |
| 外部交付 | 本轮未启用 | `external_delivery=NOT_REQUESTED` |

服务器对账、编辑批准、世界接受证书是不同的资格。发布服务从不拿 Kernel 的 guarded
世界证书替代正文对账、读者披露或整卷批准。

## 2. 固定写作批次与 DAG

`create_writing_batch(principal, payload, idempotency_key)` 创建 `WRITING_BATCH`。
它固定 WorldRef、卷/计划精确引用、风格引用、叙事版本、编排版本和场景槽位。
每个槽位固定 scene_id、故事半开区间、阅读序号和必要前驱 scene_id。
一个批次最多 128 个槽位，与本轮编辑绑定的容量一致；这一结构上限不代表 128 场密集依赖图的性能验收。

创建前校验当前采用计划、计划与批次同一输入世界、有效故事区间、唯一场景/阅读序号、
前驱存在性及无环。模型完成顺序不进入 DAG，也不改变故事时间或阅读顺序；倒叙仍合法。
`ready_scenes` 只把调用者明确提供且经过实时验证的已接受正文作为已满足前驱。
自然语言“已经完成”、尚未接受的 draft、预计会发生的事件均不满足依赖。

### 写作任务的实际顺序

1. 控制面采用计划并创建批次、不可变 ScenePlan。
2. 为 writer 创建固定任务输入：场景、批次、计划引用，以及必要前驱的精确 acceptance 引用。
3. `PlanningService.bind_task_for_controller` 绑定计划节点守卫。该入口要求 ADMIN；
   它不赋予运行时 writer 查询整份 PLAN 的能力。
4. writer 调用 `bind_writer_task`。服务核验自身当前任务、代际、上下文和固定输入，
   以及每个前驱同批次、同世界切面、已完成正式对账的正文。
5. `NarrativeService.store_draft` 再调用 `validate_writing_task_binding`，防止绕过调度器直接存稿。
   DraftRecord 中 `handoff_refs` 必须与服务器绑定完全一致。

绑定存为不可变 `WRITING_TASK_BINDING` 和按 `task_id:generation` 唯一的 selection。
新到达的前驱不能追加进已经运行的 TaskSpec。必须创建新的固定输入执行；旧代仍可审计。
角色 actor 无权读取批次控制信息；writer 只能在已经授权的场景材料和任务输入范围内工作。

两个没有依赖的场景可用独立 Session/任务并行执行。一个同时依赖两场的后继必须等两份
正式 acceptance，不能读取 writer 的私有聊天记录取得“预期结果”。

## 3. 统一采用切面与相关失效

`freeze` 接收显式 `world_ref`，不会自行读取“最新章节”并替换引用。
它调用 NarrativeService 的事务内验证，核对正文、场景、抽取、对账执行、AlignmentReport、
来源任务/授权、当前计划节点、关键世界/认知检查及采用的事件选择。

无关 HEAD 前移不会自动废弃已固定正文。旧切面仍可明确发布，前提是当前权威历史中的
相关选择、规则、解释版本及场景约束没有使资格失效。
需要采用更新世界切面时，使用 `build_alignment` 生成新的服务器报告与对账；
再形成新切面的 narrative acceptance 和多级编辑批准。文本字节可完全保留，旧引用不改写。
修改 POV、场景、风格或编排则需要相应新场景与批准。

发布额外核对每场 `NARRATIVE_SCENE` 当前选择。新稿已经接受时，旧批准所绑的旧 acceptance
不能继续作为当前稿静默发布。对于有前驱的场景，所选前驱必须与 writer 当时使用的
draft/text/scene 三个精确引用一致。仅由于新世界对齐产生新 acceptance、但三者不变的情况
允许通过；前驱改稿而后继未更新交接会返回 `STALE_SCENE_HANDOFF`。

重要新世界增量 pending、关键状态未推进、认知/披露冲突、未满足依赖或取消/换代任务均阻断。
发布服务不把未知改成“没有影响”，也不通过重复呈现事件扣除资源或更新认知。

## 4. 发布输入、产物和 CAS

`ReleaseRequest` 固定：

- 统一 WorldRef、volume_id、plan_ref、batch_refs；
- 有序 narrative acceptance 引用；
- 精确 editorial approval 引用；
- narrative_revision_id、arrangement_version、disclosure_revision_id；
- style_refs、literary_refs；
- 预期 prior_release_ref 及明确 revision_reason。

必须恰好覆盖所选批次的全部场景槽位；不能漏掉一个未完成后继后仍声称完整。
顺序必须匹配 SceneContract 的阅读序号。所有批次在采用切面上有同枝祖先关系；正式冻结
仅允许当前 canonical branch，模拟分支候选不能冒充正式卷。

`RELEASE_MANIFEST` 保存原 core 2.0 类型。有序文本项均为真实 `TEXT` 引用，
`manifest_sha256` 对去掉自身摘要字段后的规范 JSON 取哈希；
`dependency_fingerprint` 绑定整个明确发布请求。

额外的 `RELEASE_RECORD` 保存 plan/batch/scene/draft/acceptance/reconciliation/alignment/
editorial approval 精确引用、前版引用、修改理由、差异清单及 `world_effects_applied=0`。
差异区分新增/移除场景、改正文、改场景契约、重排，以及世界/计划/风格/文学/披露变化。
阅读顺序改变必须采用新的叙事、编排与披露版本。

没有新增数据库表。正式事务依次使用作品、分支和 selection 锁，比较
`RELEASE:<volume_id>` 当前指针与 `prior_release_ref`，再原子写入对象引用、不可变记录、
新选择 epoch、选择失效屏障、收据和本地 outbox。作品锁也覆盖“第一次发布还没有指针行”的竞争。
两次不同请求不能以晚到覆盖先到；同一幂等键重试返回原收据。

旧 manifest 与 ReleaseRecord 从不更新。`get_release` 按精确引用读取历史版本；
`export_release` 在读取前后核验授权并返回固定顺序的原文，未进行外部发送。
内部冻结后即使后续批准撤销，已冻结历史对象依然保持不可变；新冻结必须重新通过当前资格。

## 5. 持久化、撤销与失败恢复

文本/清单对象先持久化并校验哈希，数据库随后引用；对象共享锁避免 GC 与冻结竞争。
正式短事务重新检查当前来源代际、批准人/审稿人授权、计划/场景/正文选择、相关世界约束和批准内容。
长模型调用、人工阅读、外部网络均不在事务内。

| 失败点 | 观察结果 |
|---|---|
| 对象已落盘、数据库未写 | 只有可回收未引用对象，没有正式 release |
| 事务提交前异常 | manifest/record 记录、selection、收据及 outbox 一起回滚 |
| 提交成功后回执丢失 | 用相同键恢复同一 receipt，只有一个正式版本 |
| 预检后编辑批准撤销 | 最终事务以 `EDITORIAL_APPROVAL_REVOKED` 拒绝 |
| 预检后审核任务取消 | 最终事务以 `REVIEW_REVOKED` 拒绝 |
| 两个首次冻结并发 | 一次成功，一次 `RELEASE_SELECTION_CONFLICT` |
| 旧批准绑定新披露版本或新正文 | `EDITORIAL_BINDING_MISMATCH` |

故障注入是 `freeze(..., fault=callback)` 的测试端口，边界为 `after_objects`、`before_commit`、
`after_commit`；没有改变普通调用的正式接受规则。

## 6. 实际验证和复现

2026-11-10 的定向验证：10 项纯领域与契约测试、11 项 PostgreSQL 17.11 集成测试通过；
PG 开启 fsync、synchronous_commit 和数据校验和。此前另有 18 项调度 PG 回归与两项写作集成一起通过。
完整证据保存在 `evidence/p2/batch2/release/`。父任务的跨模块和 CI 结果另行记录，不能由这里的定向结果代替。

```bash
.venv/bin/python scripts/with_postgres.py \
  --pg-bin /path/to/postgresql/17/bin \
  --log-dir /tmp/nf-p2-release \
  -- .venv/bin/python -m pytest \
  tests/integration/test_release.py tests/unit/test_releasing.py \
  -q --tb=short --junitxml=/tmp/nf-p2-release.xml
```

反例覆盖：循环/混合批次、actor 越权、writer 不可读 PLAN、两 writer 真正并行、DAG 后继阻塞、
TaskSpec 不可追加新前驱、零世界效果、旧版不可变、首次发布 CAS、提交前回滚、提交后丢回执、
批准撤销、审核取消、正文/顺序/披露/漏场景绑定、跨切面对齐，以及前驱改稿后旧后继失效。

保留了实际失败记录：单元夹具最初遗漏 core StoryInterval 的 `bounds` 被严格拒绝；
首个 PG 对账暴露 narrative Schema 对 commands 的 URI 错写，已修到既有 `/contracts/p1/`；
审核取消测试最初预期底层任务错误，实测编辑层明确定义为 `REVIEW_REVOKED`。
最后一轮跨模块同步新增了正确的改稿来源授权检查，两份改稿夹具补入固定 TaskSpec 的
`prior_draft_ref` 后重新通过 21 项验证；相应失败和最终成功记录均保留。
这些更改没有放松拒绝条件，也没有删除失败证据。

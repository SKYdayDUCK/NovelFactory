# P2-04：固定场景、正文、事实抽取与接受

本实现沿用 `docs/07_剧情与文学生产系统.md` §5–7、`contracts/report_templates.md` §1/§5、core 2.0 `SceneContract` 和 `DraftSubmitRequest`。它只增加文学产物与可核验的交接；世界事件仍由原 Kernel 正式接受。P2-01 的依赖闭包与局部重规划由 `PlanningService` 继续负责。

## 1. 权威边界

`NarrativeService` 不调用世界 `accept`、模板执行或效果 reducer。正文里出现一个事件时，只链接已经选中的 `occurrence_id + event_version_id`。回忆、倒叙和多视角重复呈现相同事件不会再次扣资源、移动物品或增加认知。事件发生身份与文本版本身份各自独立。

世界先行时，场景卡固定已接受事件与关键入/出状态，正文和抽取必须覆盖声明为必要呈现的事件。正文先行时，新重要后果保存为 `NARRATIVE_WORLD_DELTA`，状态固定为 `PENDING_WORLD_REVIEW`。对账保持阻塞；控制面必须用原 Kernel 正式接受对应命令，然后显式给出断言与事件的映射。服务核对该事件的 `CLOSURE.template_id`、精确参数哈希及当前选择，不能用另一条无关的已接受事件消除待审问题。

正文接受、文学批准、发布是三个不同边界：

| 边界 | 产物与职责 |
|---|---|
| 正文接受 | `NARRATIVE_ACCEPTANCE`；工程对账通过、事件引用与披露资格有效，世界效果为零 |
| 多层审核与总编批准 | P2-05；独立事实/认知/连续性/文学检查，真实原文覆盖、结构编辑及保留分歧 |
| 固定版本发布 | P2-06；精确接受清单、统一采用世界、有效批准与前驱交接，发布 CAS |

`NARRATIVE_ACCEPTANCE` 不代表文学质量通过，不单独赋予正式 release 资格。

## 2. 契约兼容

原 `core.schema.json`、`literary.schema.json`、`temporal_concurrency.schema.json` 保持原样。新 `narrative.schema.json` 使用显式 2.2 版本：

- `ScenePlan.scene_contract` 完整嵌入原 core 2.0 `SceneContract`，服务另存精确 `SCENE_CONTRACT` 引用；新增计划节点、batch、前驱、直接状态检查与披露选择。
- `DraftRecord` 固定正文 `TEXT` 引用、原始世界、写作任务代际、上下文、前稿来源、交接和可选真实模型候选引用。
- `AssertionCandidate` 使用 docs07 的七种分类，保留原文 Unicode 码点跨度和 UTF-8 片段哈希。作者声明的重要增量必须有对应断言，不能改标普通装饰后消失。
- `AlignmentReport.contract_version=2.2` 保留报告模板的共同头部、精确源引用、阻塞问题、未解作用域、`WorldStateBinding`、重要跨度、直接关键检查、开放增量与阅读证据；新增明确的解释版本、源/目标世界以及对账产物引用。
- `submit_draft` 继续接受原 core 2.0 `DraftSubmitRequest`。它核对原字段与精确 AlignmentReport，再调用受控正文接受。没有向旧 DTO 塞入新字段。

`WorldStateBinding` 的记录清单哈希来自服务端当前解析的 genesis 哈希和事件选择；效果清单逐项包含 occurrence、event version、effect group、representation、effect key 与效果内容哈希。规则、投影器、过程注册表、策略及 `interpretation_ref` 一同固定。覆盖证明只声明实际核验点对应的半开区间，不把一个端点检查夸大为全部剧情时间已推进。

对账报告还必须存在服务写入的 `NARRATIVE_CHECK_EXECUTION` 选择记录，绑定报告、AlignmentReport、验证证明及源任务授权 epoch。仅保存一个 JSON 合法、状态为 CLEAR 的 ArtifactRef 不能通过接受。

## 3. 主要接口

| 接口 | 返回与限制 |
|---|---|
| `save_scene(principal, payload, key)` | 不可变 `SCENE_PLAN`，用 `prior_scene_ref` CAS 更新场景选择；计划/风格/编排变化形成新场景 |
| `PlanningService.bind_task_for_controller(admin, task_id, generation, plan_ref, node_ids, key)` | 给真实 writer 固定计划节点守卫；不授予 writer `PLAN_READ` |
| `store_draft(principal, task_id, generation, scene_ref, text, key, ...)` | `NARRATIVE_DRAFT`；接受 RUNNING 或合法 RESULT_STORED 等代际，不要求网络调用仍在运行 |
| `bind_reader_task(admin, task_id, generation, draft_refs, key)` | 明确授权不可变全文材料；TaskSpec 引用本身不构成读取许可 |
| `read_text(principal, task_id, generation, draft_ref, start, end)` | 实际精确文本、跨度、TEXT 引用及服务器 `TEXT_DELIVERY` |
| `submit_extraction(principal, task_id, generation, draft_ref, delivery_ref, assertions, key)` | `ASSERTION_EXTRACTION`；要求该任务已获得全文，验证每段精确跨度 |
| `reconcile(principal, draft_ref, extraction_ref, world_ref, key, resolution_event_refs=...)` | `reconciliation_ref`、`alignment_ref`、CLEAR/BLOCKED 及待审增量引用 |
| `build_alignment(..., target_world_ref, ...)` | 显式重算同分支后续世界的对账；不改原稿或旧报告 |
| `accept_narrative(principal, draft_ref, reconciliation_ref, world_ref, key, alignment_ref=...)` | `NARRATIVE_ACCEPTANCE`；跨世界采用必须显式给出匹配的 alignment |
| `validate_for_acceptance(repo, principal, draft_ref, reconciliation_ref, world_ref)` | 发布短事务内活检；返回精确 draft、scene、reconciliation 和 alignment_ref |

P2-06 的已授权后继交接可调用私有 `_validate_for_acceptance`；仅在先验证自身任务和精确前驱输入后使用，不作为公开 API。普通 writer 无法借此取得计划或前章全文。

真实 Agent 候选必须属于同一任务/代际的 CURRENT `TaskResult`，且 `AGENT_CANDIDATE` 正文和重要增量声明与拟存正文完全一致。晚到候选、其他任务输出或擅改模型文字都不能冒充当前候选；人工/夹具直接写稿仍需正常任务权限，并在运行报告中标明其来源。

## 4. 读取权限与模型材料

角色主体来自持久 grant，不能相信输入自报角色。全文读取要求当前任务、代际、上下文、授权 epoch、故事上限、合法角色和精确 `NARRATIVE_READ_SCOPE`。把未知正文引用放进自建 TaskSpec 不会获得阅读权。角色 actor 不能借全文、场景加载或错误消息读取作者材料。

`read_agent_material` 是 Gateway 的可选受限端口，返回 UTF-8 bytes：

- SCENE_PLAN 返回已绑定 writer 的场景卡、必要事件、直接检查、披露约束、文学目的及所选 StyleGuide；不返回原始 PlanRevision。
- NARRATIVE_DRAFT/TEXT 走全文授权，返回实际文本和 delivery 证据。TEXT 必须唯一映射到该任务已授权的 draft。
- LITERARY_MEMORY 委托 P2-05 的专用读取，源正文逐一受同一阅读作用域约束；摘要不提升为世界事实或角色记忆。
- 不支持的类型才返回 `None`，由 Gateway 使用原 Kernel 的证据读取规则。已支持类型越权必须报错，不能降级绕过权限。

`TEXT_DELIVERY` 表明精确字节实际提供给调用者，不能证明人类或模型已经理解。P2-05 在其实际读取路径再签发 `ReadingCoverage` 并执行审核门禁。抽取的 `semantic_completeness` 明示仍需独立回读；没有声称语义零漏报。

## 5. 认知、猜测和披露

`KNOWS` 必须同时符合角色的已接受认知与客观事实；`BELIEVES` 只要求该角色确实持有这一信念。引用必须来自该 actor、该取得时点的实际认知证据，服务回读源事件/对象及跨度；存在一个哈希正确的无关材料不够。另一角色的证据、未来取得的认知、未经角色获得的引用都会阻塞。

`GUESSES` 不提升为确定知识或客观事实；如果附带证据，其来源仍必须属于角色当时合法获得的材料。角色知识的取得点不得越过场景的排他结束点。未知、未推进和确定不存在保持不同状态。

当前正式命令没有独立的 speaker/utterance 注册语义；因此重要 `SAYS` 候选保持未解，资源事件或 OBSERVATION 不能冒充“某角色确实发言”。重要消息接收可沿既有 `RECORD_COGNITION` 正式记录并按对应认知断言核验。普通不承担持续因果的对白表达仍可作为表层细节；独立审核负责识别不应隐藏于表层分类的重要变化。此处是明确的保守边界，不是已实现一个完整自然语言发言事件解释器。

读者披露分别保存 `WORLD_FACT`、`REPORTED_BELIEF`、`UNRELIABLE_CLAIM`。WORLD_FACT 必须有已选择事件和 typed WORLD check；其余不携带世界真值检查。被正文实际采用的披露记录进入 acceptance 的 `accepted_disclosures`，没有写入世界投影。一个不可靠叙述者声称“桥下有龙”，仍只是已经展示给读者的声称。

## 6. 固定快照、失效与跨分支重资格

无关 HEAD 推进不会一律丢弃正文。接受时同时核验报告的原始固定世界绑定，以及当前 HEAD 上真正相关的事件选择、状态、认知、计划节点、场景/风格/编排。相关变化要求显式重对账，不能替换一个 WorldRef 字段后继续。P2-06 batch 场景还必须通过前驱正式交接守卫，DraftRecord 记录的 handoff_refs 与绑定精确一致。

场景或正文选择变更在同一事务更新 selection、scope 版本及最小 invalidation 记录，正文接受另发 durable outbox。同步活检无需等异步失效消费者完成。正文接受只关闭原写作任务的当前代际，不重放世界。

`build_alignment` 只允许同分支祖先到后继版本。跨 repair/candidate 或 canonical 切换后，使用新世界、新计划、新 SceneContract、新 writer task，任务显式包含 `prior_draft_ref`，新场景用 `prior_scene_ref` 声明来源；再保存新正文、重新抽取、对账和编辑批准。旧稿由已有合法权限的控制面提供，旧分支全文权限没有自动开放给新 writer。候选分支的正文接受不代表 canonical 推广或 release 发布；两者仍通过原内核和 P2-06 门禁。旧 release 保留其原始不可变引用。

## 7. 验证与剩余边界

单元反例覆盖 Unicode 码点、伪造片段哈希、未推进状态、多次事件呈现、重要增量遗漏、猜测与知识、认知证据串用以及历史资源冲突。PostgreSQL 反例覆盖真实 writer 无 PLAN、阅读作用域、取消/撤权、伪造 CLEAR 报告、正文先行正式世界接受后对账、同切面复用与跨分支新资格。

证据目录为 `evidence/p2/batch2/`；保留首次契约引用错误、测试夹具命令字段和幂等键错误的失败 XML，以及修复后的运行结果。结果数量以最终开发报告与 CI 原始日志为准。

这是确定性工程验收，不能据此声称模型文学质量提升。事实抽取遗漏仍需直接终态核验和 P2-05 独立原文审核补防。密集章节依赖图的重复活检成本将在 P2-08 负载和 SQL 测量后判断；没有提前声称任意规模已验证。

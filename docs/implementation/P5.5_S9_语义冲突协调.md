# P5.5 S9 跨工作流语义冲突协调

## 权威边界及一封伪造密信的生命周期

`MessageSourceService.save_version` 将正文以不可变 `TEXT` 保存；同一家族的 `artifact_id` 稳定，每个版本有自己的 `artifact_revision_id` 和 SHA-256。追加版本要验证原签发回执以及调用者对原分支和目标分支的授权。相同幂等键的并发请求只交付一个结果。某分支引用哪一版本、角色何时获知消息、角色相信什么、WORLD 中什么为真，各自依原有事件、认知记录及关系版本保存。未来的揭伪可以使“按信中承诺行事”的任务失效，旧 WorldRef 中角色当时的信念和已经发生的行动仍可查询。

| 入口 | 本次留下的服务端依据 | 后续读取或提交方式 |
|---|---|---|
| 创建任务、编译 ContextBundle、正式查询 | `task_id + generation`、固定世界、角色/认知切面、对象、谓词、故事时间；空结果也留下查询范围 | 查询结果和缓存命中均经受限入口。指定过去时点的已结束事实与仍在使用的计划前提分别判定。 |
| 已授权的素材交付与任务查询 | 来源 ArtifactRef、版本及已证明的上游观察 | 下游只有取得实际授权的材料才继承相应因果读集；一个附件编号本身不足以读取另一角色的材料。 |
| `POST /api/v1/queries/semantic-assumptions` | 原文、已读来源、关系种类、规范化键以及歧义标记 | `SemanticAssumption` 是增量收据；服务端校验工作项所有者和代际。角色提交的补充材料无法收窄既有读集。 |
| 提案、计划绑定及 Kernel 接受 | 客观效果、资源/约束范围、计划节点和选中版本 | `nf_semantic_manifests` 按代际汇总，`nf_semantic_changes` 随世界事务产生。作用域与版本回执可回溯至原对象。 |

语义判断只覆盖这些已登记的依赖。自由文本可能有多种文学解释；无法消歧的命题进入有范围的独立审核。未观察的现实世界语义没有可供系统从中推断完整性的证据。

## 与 Redis 延迟无关的提交屏障

Kernel 在正式接受事务中读取当前分支和语义回执；正文接受及出版冻结也复查写作和提取任务的登记依赖。相同作品中两个尚未接受、在同一故事现场竞争排他物品的候选会进入联合裁决。计划采纳使用原计划选择 CAS；仅在已获独立编辑审核、图拓扑/出版前缀/世界切面一致、受影响节点及因果输入可证明不交叉等条件满足时，可将不同节点修改合入新的不可变计划。原候选和两条修改的来源可查。

Outbox 通知 Redis Streams 消费者。PostgreSQL 同时保存待扫描记录；`scan_event` 在同一事务里移除待扫描项并写判定证据，进程退出导致整个事务回滚。Supervisor 可在运输中断时从库内继续扫描，重领、重复通知或倒序扫描按不可变世界和 case 键归并。空闲解析器先查待办，进入特定案件处置时才按既有 `work → branch → task` 锁序操作。世界版本上的读写匹配使用按分支和版本收窄的 GIN 作用域索引；迁移前缺少证明的回执走保守路径。

## 处置、预算与操作回执

| 路径 | 与既有服务的交接及完成标志 |
|---|---|
| REVALIDATE | 在新切面重放可证明的读语义；成功后按 observation 和新世界记录不可变证明，保留可复用的产物。后续变更再次检查。 |
| REBASE_CANDIDATE | 保留原候选、输入世界和来源。Kernel 用还有效的审批和上下文重新发证；正式接受再次经过现有守卫。 |
| RECOMPUTE_DEPENDENTS | 可安全重编译的未发布任务进入下一 generation，旧输入、旧结果与旧供应商回执保留。下游按已交付的物料依赖判定。涉及特权知识、专用任务绑定或额外假设时交给审核。 |
| JOINT_ADJUDICATION | 独立审核人把案件及有签名证据的共享范围绑定到原调度器 `prepare_interaction`。多方密封意向由原联合裁决流程处理。 |
| REPLAN_WINDOW | 依据原绑定和 RollingPlanning 窗口计算已受影响的未来节点，保存 PlanRevision 与保留节点清单。生成候选和采纳分别留存回执。 |
| CANDIDATE_BRANCH | 保留两条已授权的分支选择并比较，或从当前 HEAD 建立候选。审核单记录待决事项。 |
| REPAIR_HISTORY | 已经接受的任务记录 `HISTORY_PRESERVED`。需要修改正式历史时，独立审核凭据可以开启 REPAIR 分支，然后由原修复流程验证和提交。 |
| ESCALATE_REVIEW | 冻结案件与审核范围，创建有期限、零模型调用预算的 `WAITING_REVIEW` 单。审核人需有本作品/分支 ADMIN 与 APPROVE，且身份有别于来源及受影响的生产者。 |

由运维在 Supervisor、World Worker 和受权决定命令的服务进程环境中配置相同的上限。每个新处置器读取一次配置。已保存的案件回执幂等重放时保留当时的结果。

| 服务进程变量 | 默认值 | 作用范围 |
|---|---:|---|
| `NF_S9_MAX_REFRESHES` | 2 | 同一任务跨代际累计的自动刷新次数 |
| `NF_S9_MAX_WINDOW` | 8 | 单次自动重规划可改动的未来节点数 |
| `NF_S9_MAX_IMPACT` | 32 | 单案件的受影响任务数；联合转介的 scope 和参与者数量分别受限 |

参数接受 0 到 2147483647 的十进制整数，非法值使处置器初始化失败。0 会阻止相应的自动刷新、未来窗口或有参与者的联合转介。新处置回执的 `repair_limits` 记录当时的配置。员工与角色请求没有这些配置字段，原有任务授权、审核权限和模型预算仍各自校验。

原世界无进展、权限改变、缺少可重编译证明、超窗、已有模型调用等情况均有明确分流。已发送结果未知的调用保持 `PAUSED`、原 attempt 和费用预留；收到原请求的对账结果后才转为独立审核。`REPLAN_PROPOSED`、`RECOMPUTE_QUEUED` 和 `WAITING_REVIEW` 分别表示提议、排队和等待，查阅下游实际回执才能确认采纳或完成。

## 审计、迁移和恢复

使用有作品/分支权限的控制端绑定运行 `python scripts/p55_conflicts.py --binding "$STAT_BINDING" list --limit 30`。独立决定使用同一脚本 `decide --request decision.json`，需给出 `case_id`、`expected_head`、`decision` 和签署的 `evidence_ref`。联合转介另需 `interaction`，其哈希须写入证据。审计可按 case、trace、task/generation、来源 WorldRef 和策略回放。角色 stdio 接口不公开控制端案件目录。

StatisticsService 指标 v5 以不可变审核事件为原始数据，提供增量归集和同一 source cut 的历史重算。重新派发的实际模型用量按原冲突 `RECOMPUTE_QUEUED` 与下一 generation 关联。协调器自身零调用、合成 fixture、供应商报价与实际结算分别记账。正式采纳 S9 窗口后，原计划 CAS 在同一事务记录 REPLAN_APPLIED，可与 REPLAN_PROPOSED 区分。缺少独立标签时，报告将误报、漏报和无效返工率标为未测。

有独立标注时，可调用 `python scripts/p55_statistics.py --binding "$STAT_BINDING" conflict-quality --labels-ref labels-ref.json`。该文件只含完整 ArtifactRef；它指向不可变 EVIDENCE，内容为 kind=SEMANTIC_LABEL_SET、work_id、branch_id、reviewer_grant_id，以及 1～128 项 labels。每项填写 task_id、generation、world_revision_id、affected（布尔）和判断理由 reason。审核人须对该分支有 APPROVE 权限，且与被标任务和变更来源的生产者身份均不同。标注集应事先固定，同时覆盖受影响与独立任务。输出给出样本实际冲突数与混淆矩阵，按真实新代际 RUNNING 回执计算无效返工率，返回可回放的 source_cut。无实际重跑时分母为零，比例留空。

1. 部署前记录原 Alembic 版本、作品切面、未完成任务代际、尚未对账的调用及备份对象清单。为库和对象存储建立配套恢复点，演练异机恢复。
2. 在迁移窗口执行 `python -m alembic upgrade head`。`0013` 新增观察/变更索引与案件；`0014` 注册 Outbox 扫描及处置回执；`0015` 追加旧回执水位、重验证证明和按分类的唯一键。`0016` 根据固化版本补齐旧图、时间线、素材及生命周期影响范围，安排必要回扫。已有回执保留，历史时间缺失保持 NULL 并保守复核。索引创建和表约束变更需持锁，按现有库规模安排窗口。
3. 恢复 EventHub 与 Supervisor，检查 Inbox 消费、积压、案件和当前 generation。物理恢复后先处理 Redis 中超越恢复目标的事件，复核 UNKNOWN 原预留，再恢复派发。
4. 有 S9 回执或不兼容旧约束时，降级会中止。用兼容应用或经演练的成对备份恢复；先留存不可变证据。升级测试从固定历史源码生成 P1 和 0014 的真实数据。

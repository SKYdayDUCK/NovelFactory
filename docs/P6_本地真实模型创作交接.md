# P6 本地真实模型创作验证

首轮回答两个问题：在同一份开篇设定下，3～5 名主要人物能否推进 10～20 个连续场景；当消息被证伪时，后续场景能否更新，同时保留早先角色的所知、所信和所为。把研究作品与工程测试作品分开建库或分配独立作品和对象目录。保留每次运行的 Git SHA、模型配置、预算、起始 WorldRef 和计划版本。

## 1. 在本地建立可复核的工程基线

在 Linux 或 Windows 的 WSL2 中进入本次部署固定 SHA 的 NF 根目录。使用普通服务账户，准备 Python 3.12、uv、PostgreSQL 17、Redis 8、Codex CLI、bubblewrap、unshare 和能静态编译 C 的工具链。当前仓库的工程 CI 指定 Redis 8.0.2、PostgreSQL 17.11、Codex 0.167.0-alpha.4。核对当前提交的版本锁和工作流。

```bash
git status --short
git rev-parse HEAD
uv sync --locked --group dev --python 3.12
postgres --version
redis-server --version
codex --version
bwrap --version
```

设置 NF_DATABASE_URL、NF_OBJECT_ROOT、各进程的 NF_REDIS_URL 与 PG_BIN。用于 pytest 的 NF_TEST_DATABASE_URL 和 NF_TEST_REDIS_URL 指向可丢弃的测试部署。备份已有作品的数据库和对象目录后，在服务账户环境执行以下操作。PITR 输出使用尚不存在的目录。

```bash
uv run --no-sync python -m alembic upgrade head
uv run --no-sync python -m alembic current
uv run --no-sync python -m alembic heads
uv run --no-sync python -m pytest tests -q --junitxml=p6-local-engineering.xml
uv run --no-sync python scripts/pitr_drill.py --with-redis --output p6-local-pitr
```

核对迁移当前值等于 heads，记录 JUnit 的失败和跳过项。角色容器、actor MCP、Redis 多进程场景、故障恢复以及 S9 的本地结果都要对应本次 SHA。物理恢复检查 result.json 的 status、target_commits_lost、old_worker_rejected、unknown_calls_retained 和 Redis 的隔离回执。若角色容器测试在当前主机跳过，应先在可运行 user namespace 的 Linux/WSL2 环境完成测试，再让真实演员访问作品。安装与 Redis ACL、进程启动和回退命令见 [P5.5 安装手册](implementation/P5.5_安装与运维.md)。

## 2. 检查模型路由和部署权限

| 运行身份 | 准备与核查 |
|---|---|
| 项目服务 | 为本次作品准备 supervisor.json，含 token、work_id、branch_id，文件保存在服务账户私有目录。另为统计审核人员签发带 ADMIN 的项目绑定。 |
| 作者 | 安装项目级 MCP 配置，指向受限 SSH 别名和该作品的 resume_operator 授权。打开作者工作区，调用 nf_project_status，核对作品、分支和待办。 |
| 模型执行器 | 服务账户从其私有环境载入 NF_MODEL_ENDPOINT、NF_MODEL_NAME、NF_MODEL_API_KEY、NF_MODEL_MAX_OUTPUT_TOKENS 和 NF_MODEL_TIMEOUT_SECONDS，使用已授权的 HTTPS 路由。 |
| 有工具权限的演员 | 部署已编译的角色 MCP relay，配置 NF_ROLE_MCP_RELAY。冻结输入中的 adapter_id 须与服务实际登记的通道一致。用集成测试证明 actor 的 BELIEF cut、秘密对象拒绝和工具列表。 |

```bash
uv run --no-sync python scripts/probe_model_environment.py --output p6-route.json
uv run --no-sync python scripts/run_eventhub.py status
```

第一条默认只检查配置，无供应商调用。CONFIGURED_NOT_DISPATCHED 表示本地配置齐全。首次实际请求只在作者落实供应商授权、总金额、每次金额预留、总 Token 与单轮输出上限后放行。缺少合法路由时，保存工程 JUnit、PITR 和本地合成 HTTPS 回执，真实创作标为未运行。在 Linux 服务账户中编译角色 relay，然后把生成文件的绝对路径写入该服务的 NF_ROLE_MCP_RELAY。

```bash
mkdir -p "$P6_PRIVATE/bin"
cc -Wall -Wextra -Werror -O2 -static adapters/codex/role_relay.c -o "$P6_PRIVATE/bin/role-mcp"
chmod 700 "$P6_PRIVATE/bin/role-mcp"
```

P6_PRIVATE 为本机新实验的私有目录。项目级安装、凭据签发入口分别见 [MCP 配置器](../scripts/install_p5_project.py) 和 [授权脚本](../scripts/provision_resume.py)。

## 3. 冻结首轮实验材料并登记工作

1. 用白桥测试世界的仓粮、守卫、资源归属作为第一套对照素材；建立新实验作品。登记场景前，准备已接受 WorldRef、已采用卷计划、可执行的未来节点与相应世界过程、角色初始认知、可用地点、约束及预算。记录素材版本与后续评审量表。使用仓库可执行的宴会场景作为 3 人工程样例，扩写时重新定义每个场景的冲突和动机。[场景登记样例](../tests/integration/test_p5_autonomous_banquet.py)
2. 设置一条固定情节线索，例如“信称北桥封锁”。保留原文版本、送达角色、相信该说法的记录和初始世界事实。安排晚到的证据改变真实性；另保留一个仅涉及南方仓粮的独立场景。事先标注预期受影响的计划节点与正文，把标注留给验收者。
3. 首次先批准一个场景与一个后继，再按结果扩展到 10～20 场。scene_limit 是有限授权窗口上限。following_scenes 的每个条目绑定现有 node_id 与 process_id，故事时间递增，预算按角色、裁决、编辑和可能的修正分别预留。当前场景控制器授权的位置变化、可选物品交付及世界过程定义限制了可执行的动作。如果素材要求尚未支持的动作，记录缺失模板与具体场景，保留未接受的候选。
4. 把场景登记 JSON 放在实验服务的私有目录。使用真实的授权引用填写 world_ref、story_time、scope_ids、volume_id、scene_limit、participants、subject_id、destination_id、budget_id、adapter_id、reserve_amount、token_reservation、idempotency_key，按需要加入 following_scenes。首次登记保存响应以便同键重试。后台服务尚未启动时，登记本身不会调用模型。[场景入口及字段校验](../src/novel_factory/application/scene_runtime.py)

```bash
uv run --no-sync python scripts/run_supervisor.py --access-file "$ACCESS" --register-scene "$SCENE_FILE"
uv run --no-sync python scripts/run_supervisor.py --access-file "$ACCESS" --set-transport redis
```

按 P5.5 安装手册分别启动 relay、各接收组、作品的四类执行器。首次固定并发，每类执行器从 1 开始，预算和硬配额按已批准值配置。作者在 VS Code 通过 Codex 发出“继续未完成的任务”。保留首次恢复回执、随后空转时的 IDLE 或等待状态，以及业务事件到达后的唤醒回执。M0 bootstrap 将创建两个摘要任务，可单独用于安装自检；10～20 场实验使用上述独立的场景和计划。

## 4. 每场记录和盲评

| 层次 | 保留的证据 | 验收方法 |
|---|---|---|
| 世界与认知 | 角色授权切面、输入 WorldRef、事件和关系版本、采纳计划、当前 HEAD | 逐条核对守卫和资源，比较消息送达前后及被证伪前后的认知；历史世界引用须可回查。 |
| 语义协调 | 依赖、case、处置及关联 trace、受影响与保留产物 | 对照预标注场景逐例计 TP/FP/FN，标注缺失则为未测。核对已发布事件及独立场景的版本和哈希。 |
| 模型和费用 | 请求键、attempt、route、提供方回执、输入/输出 Token、币种、UNKNOWN 与预留余额 | 分开列出报告用量、价卡估算、已对账金额及未决金额。停止派发超预算任务。对 UNKNOWN 按原 attempt 对账。 |
| 文本质量 | 每场匿名文本、匿名评阅人、评分、对应句与修改建议 | 1～5 分评价因果连贯、认知一致、角色动机、人物声音与文笔。两名独立评阅人先分别打分，再对相差 2 分以上的条目复核并保留原评分。 |

```bash
uv run --no-sync python scripts/p55_statistics.py --binding "$STAT_BINDING" trace --trace-id "$TRACE_ID"
uv run --no-sync python scripts/p55_statistics.py --binding "$STAT_BINDING" verify
uv run --no-sync python scripts/p55_statistics.py --binding "$STAT_BINDING" literature
uv run --no-sync python scripts/p55_diagnostics.py --limit 100
```

统计输出冻结 source_cut 与 metric_version。按章归集需先固定章节映射和价卡引用，命令见 [费用报告入口](../scripts/p55_chapter_costs.py)。相邻版本盲评使用同一素材、预算、评阅量表及参与者，随机交换展示顺序。若有费用授权，可重复固定场景，记录供应商随机性；一次短卷评分只报告该次结果。

### 导出冻结卷与独立审读材料

在作者的私有实验目录保存冻结操作返回的 `release_ref`，其中有 `artifact_id`、`artifact_revision_id` 和 `sha256`。下例假设完整冻结回执为 `freeze-receipt.json`，当前目录为已固定提交的 NF 根目录，`AUTHOR_BINDING` 和 `STAT_BINDING` 各由对应角色持有。场景还处于草稿或已经产生另一个修订版时，均依照本次选定的发布引用导出。

```sh
umask 077
jq '.release_ref' "$P6_PRIVATE/freeze-receipt.json" > "$P6_PRIVATE/release-ref.json"
uv run --no-sync python scripts/p6_export_release.py --binding "$AUTHOR_BINDING" \
  --release-ref "$P6_PRIVATE/release-ref.json" --output "$P6_PRIVATE/release.txt" \
  > "$P6_PRIVATE/export-receipt.json"
sha256sum "$P6_PRIVATE/release.txt"
trace_id=$(jq -er '.release_ref.artifact_revision_id' "$P6_PRIVATE/export-receipt.json")
uv run --no-sync python scripts/p55_statistics.py --binding "$STAT_BINDING" \
  trace --trace-id "$trace_id" > "$P6_PRIVATE/release-trace.json"
```

正文文件须用新文件名。导出回执中的 `text_sha256` 指向冻结后的原文 UTF-8 字节，`manifest_sha256` 指向发布清单。发布冻结的 trace 可按其修订标识导出，场景运行日志使用该场景的原 `trace_id`。统计运维身份拥有对应作品、分支的 `ADMIN`。正文导出需要非演员项目绑定、`READ` 和 `PLAN_READ`，角色及授权同时允许 WORLD、PLAN，故事时间范围涵盖冻结版本；命令也核对绑定分支。一组可用的只读权限是项目主管 `volume_director` 的上述两项能力。同一作者的恢复身份只用来继续项目。保留审计日志、发布引用、计费记录在私有运行目录。

把完全相同的 `release.txt` 与一张空表分配给每位读者。表号 A、B 标记两份独立副本，读者化名由本人填写。协调人保存冻结哈希及收件记录。日志、工作流审核结论、其他读者的评分与原始绑定保留在各自权限范围内。两份原表返回前，文学验收保持 `NOT_EVALUATED`。

```sh
digest=$(jq -er '.text_sha256' "$P6_PRIVATE/export-receipt.json")
for form in A B; do
  mkdir "$P6_PRIVATE/reader-$form"
  cp "$P6_PRIVATE/release.txt" "$P6_PRIVATE/reader-$form/release.txt"
  sed -e "s/{{TEXT_SHA256}}/$digest/g" -e "s/{{FORM_CODE}}/$form/g" \
    reports/handoff/P6_READER_FORM.md > "$P6_PRIVATE/reader-$form/review.md"
done
```

本机可以先在可丢弃的 PostgreSQL 17 上运行已有的六场 `TEST_FIXTURE`，仅验证导出和材料交接。命令会产出 `release.txt`、`run_manifest.json`、`author_feedback.md` 及工程明细。重放受限作者命令及两份空表的集成用例是 `tests/integration/test_p6_export_release.py`。工程明细中的角色上下文和审核材料不属于匿名评阅包。[工程样卷与运行条件](implementation/P2_端到端短卷生产.md) · [独立读者空表](../reports/handoff/P6_READER_FORM.md)

```sh
uv run --no-sync python scripts/with_postgres.py --pg-bin "$PG_BIN" --migrate -- \
  python scripts/run_short_volume.py --execution-kind TEST_FIXTURE \
    --output "$P6_PRIVATE/fixture" --object-root "$P6_PRIVATE/fixture-objects"
```

## 5. 中止、恢复与交接

发生 WORLD/角色秘密越权、同一 attempt 二次发送、已接受历史被静默修改或预算不足时，暂停对应作品的执行器，记录最后的任务 generation、case、分支 HEAD、统计水位和待对账请求。普通 Redis 中断先恢复 relay 和接收组，核对积压下降及 Inbox 幂等回执，再恢复作品执行器。真实创作期间以生产库和对象目录的匹配备份为恢复点。在独立目录验证恢复和旧代际围栏后，再决定恢复运行。

交接记录包含本轮场景总数、接受和退回数、当前有效正文/计划引用、失败和待决 case、剩余预算、未结算调用与独立文学评语。能够按同一输入复现的缺陷进入 P6 修复清单。每次只修改被证据定位的环节，复跑原失败场景及相邻受影响场景，并保留修复前后的文本。

### 语义复核入口

运行 `uv run --no-sync python scripts/p55_conflicts.py --binding "$STAT_BINDING" list --limit 30` 获取有权查看的 case、代际、处理收据及人工单状态。默认角色工具不提供这个索引。每场预标场景的独立审核人可冻结 SEMANTIC_LABEL_SET 证据，控制端用 `p55_statistics.py --binding "$STAT_BINDING" conflict-quality --labels-ref labels-ref.json` 重建该样本的实际/误报/漏报及无效返工率。独立审核人以自己已获 ADMIN 和 APPROVE 的受限作品/分支配置执行 `scripts/p55_conflicts.py --binding "$REVIEW_BINDING" decide --request decision.json`。请求字段为 expected_head、case_id、decision、evidence_ref；联合裁决另需 interaction。用例见 [决议与证书复验](../tests/integration/test_s9_resolution.py)。审批历史修复仅开启 REPAIR 分支，替换正式事件仍经现有 Kernel 证据和接受流程。

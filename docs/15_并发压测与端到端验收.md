# 15｜并发负载、容量验证与 A–H 端到端验收

> 修订：v2.0-R1。本文规定待执行的压测与业务验收；10/50/200/500/1000 是研究档位，不是已经实现的容量。当前只执行了独立负载算术模型，结果见 [benchmarks](../benchmarks/README.md)。

## 1. 六种规模指标分别定义

| 指标 | 计数对象 | 不能据此推断什么 |
|---|---|---|
| 已配置 Agent / 活跃 Agent | 可运行逻辑任务槽位；采样窗口内实际发生操作的槽位另计 | 1000 个槽位不等于 1000 个正在发请求的客户端 |
| 接入连接 / 会话 | HTTP 连接、请求在途、Host 会话分别计数 | 不与角色数或数据库连接一一对应 |
| 工具请求率 | 进入服务的请求、完成、拒绝、超时、重试分别计数 | 一个批量请求可能包含多项查询；低 RPS 不等于低数据库负载 |
| 数据库吞吐与占用 | 读取/写入 SQL 语句、事务、连接占用、锁等待和扫描量 | 多条 SQL 不等于多次世界接受 |
| 世界正式接受吞吐 | 新接受的命令、事件及效果分别计数，另报每事务事件数 | 幂等回执重取、候选保存、计划批准不算新增世界提交 |
| 模型并发与费用 | 排队/在途/UNKNOWN 调用、输入输出 token、实际费用 | 服务可接入1000 Agent不代表模型提供方允许500路并发 |

叙事接受、世界接受与后台派生处理分别记录吞吐。按 work/branch/class 统计公平性；总体平均可能掩盖同一热资源或某作品持续饥饿。

## 2. 可复现的初始行为模型

### 2.1 从角色周期推导需求

初始参数来自本项目假设，未从真实用户流量拟合。完整输入是 [workload_model.json](../benchmarks/workload_model.json)，不同档位按最大余数法分配整数角色数，小档位的比例允许有取整偏差。

| 任务族 | 槽位比例 | 参考周期/秒 | 每周期工具请求 | 模型平均在途/秒 | 每周期控制面接受机会 |
|---|---:|---:|---:|---:|---:|
| 角色行动 | 30% | 120 | 7 | 60 | 0.20 |
| 写作 | 25% | 300 | 5 | 180 | 0.02 |
| 审核 | 20% | 180 | 7 | 90 | 0 |
| 卷导演 | 10% | 240 | 8 | 120 | 0.05 |
| 事实/记忆维护 | 10% | 90 | 6 | 35 | 0.15 |
| 后台维护 | 5% | 300 | 3 | 20 | 1.00 |

后台每周期假定平均0.5次、每次40秒的语义调用，其余工作为确定性任务。“控制面接受机会”是按联合裁决分组摊分的流量假设，不是授予角色直接提交权；也不表示每个提案最终成功。周期包含外部模型等待、空闲和请求阶段；模型等待不占数据库事务。

对角色族 i，设槽位数为 Nᵢ、周期为 Tᵢ、每周期请求数为 qᵢ，则参考请求需求 λ = Σ Nᵢqᵢ/Tᵢ。数据库语句需求还需要逐操作的 SQL 扇出、缓存命中假设和控制面接受开销；不能把依赖条目数直接当成吞吐。模型平均在途需求可按调用率乘调用持续时间估算，只在稳定流量且未被提供方配额限制时有此含义。

### 2.2 算术结果，不是压测成绩

下表由所附脚本实际计算，保留两位小数方便阅读。SQL 扇出与缓存率仍是输入假设；服务实际吞吐、尾延迟、内存、CPU和费用均未测量。

| 配置槽位 | 工具请求需求/秒 | 控制面接受机会/秒 | 冷缓存 SQL 语句需求/秒 | 假定80%可缓存读取命中时 SQL需求/秒 | 模型平均在途需求 |
|---|---:|---:|---:|---:|---:|
| 10 | 0.40 | 0.007 | 1.62 | 0.99 | 5.19 |
| 50 | 2.00 | 0.042 | 8.09 | 4.99 | 24.88 |
| 200 | 7.99 | 0.174 | 32.36 | 19.98 | 98.44 |
| 500 | 19.97 | 0.435 | 80.91 | 49.96 | 246.11 |
| 1000 | 39.94 | 0.871 | 161.81 | 99.92 | 492.22 |

此例说明，长时间思考的1000个 Agent可能只有几十工具请求/秒，却对外部模型并发和token预算产生更高压力。它不能证明当前数据库能满足该需求；若改成高频追问、无思考循环、重规划风暴或集中完成模型调用，负载会完全不同。

批量、缓存和Context Compiler会改变工具次数和SQL数量，所以压测同时报告“HTTP/MCP请求数”“查询项数”“返回证据字节数”。批量大小1/8/32、上下文证据上限20/100/500是测试维度，不是角色必须使用的固定数量。

### 2.3 两种到达模型及突发

行为闭环保留“读取→思考→提交→空闲”的顺序，用于模拟真实任务和预算；另设 open-loop 到达率0.5×/1×/1.5×/2×参考流量，用于查找排队拐点。闭环中服务变慢会降低后续到达，可能掩盖过载；k6 官方区分这两种模型并说明此影响。[R1-E03](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)

必须保存计划到达、实际发出、完成和未发出的数量。k6 的 dropped_iterations 可能源于负载机分配不足，也可能与被测服务变慢有关，需结合负载机资源和时序归因；不能仅删除未发出样本后公布成功请求延迟。[R1-E04](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/)

额外测试三种突发：场景屏障后20% Agent在5秒内取上下文；早期Retcon使25%的适用上下文同时需要复核；外部提供方一批结果同时返回。随机错峰采用固定种子，突发窗口单独报告，不能用整小时均值稀释。

## 3. 数据规模与输入分布

| 数据档位 | 事件数 | 实体数 | 关系版本 | 角色/认知记录 | 产物版本 | 分支数/最大继承深度 |
|---|---:|---:|---:|---|---:|---|
| small | 10,000 | 2,000 | 40,000 | 100 / 20,000 | 3,000 | 3 / 5 |
| medium | 100,000 | 20,000 | 400,000 | 1,000 / 200,000 | 30,000 | 10 / 20 |
| large | 1,000,000 | 200,000 | 4,000,000 | 10,000 / 2,000,000 | 300,000 | 50 / 100 |

这是待生成的合成数据规范，不是本轮已装载的数据。100/1000/5000章只是元数据规模标签，不代表生成过相应数量的合格正文。平均实体历史长度可以相同，但最大实体历史长度分别取2000/20000/200000，专门覆盖贯穿全书的高频人物和关键道具。

世界/分支查询必须混入早期1%、中间50%、最近99%的故事时间；不能只测最新投影。图查询测1/2/3跳、100/1000节点预算、不同入度和容器链；截断返回PARTIAL，不把预算耗尽伪装成完整否定。热资源占比0/20%/80%，独立事件域1/8/32，作品1/10分别变化。

冷缓存分开记录：应用缓存清空、数据库缓冲冷/暖、对象读取冷/暖，不能笼统称“冷”。重放比较从初始状态、相容快照增量、缓存命中三条路径；输出一致性必须先通过。比较早期Retcon与尾部修订的影响范围、重建量和同步失效开销，不能只报告快照最近时的快路径。

PostgreSQL多列索引的列序会影响扫描范围；range上的GiST/SP-GiST可用于包含或重叠等查询。两者只是候选访问路径，具体索引取舍由实际SQL与执行计划决定。[R1-E09](https://www.postgresql.org/docs/17/indexes-multicolumn.html) [R1-E10](https://www.postgresql.org/docs/17/rangetypes.html)

## 4. 十类核心负载与正确性判据

| 负载 | 操作安排 | 除速度外必须核验 |
|---|---|---|
| 高频历史状态 | 同实体/不同旧版与不同时间交错读取，热点和长尾混合 | 对应WorldRef及valid time正确，未知/未推进不当NONE |
| 跨实体多跳图 | 制造者→物品→持有者→宗门，功法前置和容器路径 | 权限、时间约束和路径预算逐跳生效，循环不无限展开 |
| 角色上下文 | 数百人物各读自己的固定时点，带真假信念与私有目标 | 缓存和检索不串角色，硬约束证据不被token预算静默丢弃 |
| 并行写作 | 多场景同一批固定切面，另一批在世界推进后开始 | 同批不混用HEAD，旧稿有明确重验证与对账 |
| 独立地区推进 | 8/32事件域、部分有消息边、部分无依赖 | 不被无关慢区域全局阻塞，相关交汇前沿不越界 |
| 单资源高冲突 | 多行动属于同一故事窗口，先封闭联合裁决 | 数据库到达顺序不决定胜负；不把正常语义竞争当可盲重试事务 |
| 正式批量接受 | 1/10/50事件的合法因果包；不同work并发 | 每包全成或全不成，效果一次；吞吐分别按命令/事件/效果报告 |
| 早期历史修订 | 早期1%位置改产权，与只读/写作/新世界提交交错 | 旧史可还原；同步屏障生效；晋升双端CAS；范围充分 |
| 缓存命中和失效 | 固定旧版命中、最新别名解析、撤权、同键并发miss | 缓存命中仍核验权限；合并构建不跨授权；旧版仍可合法读取 |
| 长时运行与恢复 | 至少覆盖队列清理、快照、索引追赶、限流和进程中断 | 内存/连接/对象无持续泄漏；未知调用不重复计费假定，已接受历史不丢失 |

`SKIP LOCKED`只服务队列领取，不能为了降低查询延迟跳过锁住的世界记录后返回“完整”。该限制来自 PostgreSQL 官方对其非完整视图语义的说明。[R1-E06](https://www.postgresql.org/docs/17/sql-select.html)

## 5. A–H 的具体端到端验收

完整初始条件、操作、预期状态、反例和证据要求见 [r1_case_matrix.json](../validation/r1_case_matrix.json)。以下为人工执行导航；所有案例状态仍为 `PLANNED_NOT_EXECUTED`。

以下PENDING默认指状态载荷的 `evaluation_status`；允许部分结果的响应信封仍可READY。顶层PENDING只用于等待已有推进任务，查询本身不获得推进权限。计划被破坏时先由同步屏障停止执行资格，再追加失效/重规划记录；旧APPROVED版本保持不可变。

### A：历史物品与未来计划

独立R1测试作品：D01制造，D10赠给主角，D20借朋友，D30被反派盗走，D40毁坏；D15已批准D50持剑入秘境计划。最终选定版本的目标范围已求值到D42排他前沿，因此D41可查询：D25应是主角所有/朋友持有，D35主角所有/反派持有，D41没有活跃持有与使用，但保留最后权属历史。销毁接受同时阻断依赖存续的执行资格；异步更新计划/章节/摘要并产生重规划任务。D50仍未推进，正式事实查询必须保持未求值，不能自动执行批准计划。

### B：修改过去但保留旧版

把D20借用改成赠与。固定W_old与W_new，D25旧版owner=主角、新版owner=朋友，两版holder均为朋友。REPAIR重建复核D30/D40后续发生，保留未被修订的发言与误信；确认受影响伏笔、章节、摘要和计划。重建期间旧canon变化必须使推广重新核验；旧稿不能只换WorldRef获得新批准。

### C：两线独立推进后交汇

east已求值D40，west已求值D35，remote只到D20；登记证明remote最早相关影响为D45。主角从D40和反派从D35按旅行规则都在D42到桥，争夺唯一钥匙。局部推进不等待remote追平；D42必须封闭参与集合并联合裁决。改变模型到达顺序不得改变选定裁决；移除通道完整性证据应阻断相关推进。到达下界H只证明严格早于H，不证明H处事件已处理。

### D：候选未来与正式世界

main只求值到D60，candidate从其固定版本推演到D100并在D70毁剑。candidate D90能读到该分支正式接受的毁坏；main D90应按覆盖返回PENDING，不能借用候选结果。作者比较候选与角色可读范围分别授权。采纳候选必须生成目标分支变化包及正式接受资格，不能直接覆盖主分支投影。

### E：角色误信与客观事实

主角D20看见朋友持剑，D30盗窃未被告知。D35角色上下文保留“朋友持有”的有源信念；裁决者在授权范围看到反派实际持有。第80章读者视图取决于该叙事版本披露，不能把世界已发生等同读者已知道。D36收到报告只证明听闻发生，是否采信另记；对所有检索、证据、计数、错误和缓存通道检查泄漏。

### F：并发与旧输入

200逻辑Agent中160只读/写作、20个封闭足迹独立命令、20个同窗口争剑意图。独立命令同基线W0，可在HEAD前进后经服务端scope/规则/覆盖/权限复验接受；保留原输入与实际接受parent。争剑意图先联合裁决，不能变成20次抢锁。加入负向查询幻读、不同实体共同容量的write-skew、证书过期和撤权反例；报告“仅HEAD变化”和“真实依赖变化”的不同处理。

### G：宏观转微观

宏观运输D50→D53已接受：粮食100→88、health100→97、crate占有carrier→receiver。微观写作、闪回和多视角重述后这些值与有效效果集合不变。若细写引入新伤害、耗粮、消息或知情人，进入变化提案。P3等价实验必须检查中间观察和权利，不能只看最终余额。

### H：提交成功但回包丢失

命令K已在数据库提交，回包前断连，并停索引worker。相同K/载荷重试获得原回执；同K换内容拒绝。READ_YOUR_WRITES或固定提交版本读取权威结果，搜索明确显示滞后。取消先则旧代不能新提交，接受先则后取消不撤销。父任务部分失败不自动删除成功子事件；继续、显式反向事件或Retcon由相应用例决定。

每个案例至少保存WorldRef、任务代际、权限/规则版本、提案及证书哈希、回执、相关token变化、状态查询和错误；文学选择另保留文本及编辑证据。读取数据库“记录条数正确”不足以证明故事语义和角色认知正确。

## 6. 测量、环境与执行步骤

### 6.1 必备观察项

每种操作分别记录P50/P95/P99和样本数，分解客户端排队、网络、鉴权、连接池等待、SQL、对象读取和上下文编译。异步任务另外记录从接受请求到可用产物的端到端延迟。错误/超时单列，不能仅统计成功响应；高分位样本过少时明确不稳定性。

服务器记录CPU、RSS/峰值、GC、磁盘吞吐/延迟、数据库连接active/idle/idle-in-transaction、锁等待、死锁、WAL、临时文件和队列年龄。`pg_stat_statements`可提供聚合执行与块I/O统计；请求级P99仍由应用追踪获得，不能用其平均值代替。[R1-E08](https://www.postgresql.org/docs/17/pgstatstatements.html)

缓存报告按层命中率、构建合并率、陈旧阻断数和权限失效次数；索引报告world revision覆盖/水位与现实延迟。正式接受报告新命令数、重复回执、自动重验证成功、真实依赖冲突、语义返工、事务重试和失败原因。把成功去重结果作为有效吞吐，不能用快速拒绝或重复回执制造高TPS。

费用记录每次实际供应商请求、输入/输出/缓存token、被取消但可能收费的UNKNOWN和废稿。报价在选定供应商及日期后输入；模型脚本默认价格为null，只算token需求。总成本包括准备、检索、失败预演、返工及人工阅读，不把只生成最终文本的费用称作整部小说费用。

### 6.2 冻结环境与负载机

每次运行先填：CPU/vCPU、内存、磁盘与文件系统、OS、PostgreSQL/驱动/ORM版本、配置、API/worker进程数、池size/overflow、负载机位置、网络、代码提交、数据种子/哈希和模型stub或真实供应商。H1可先用现有单机；增加进程、内存或副本各自形成新实验条件，不假设某硬件型号天然能承载1000 Agent。

进程池预算算例是4个API进程×(8+4)连接，加4个worker×4连接，加16个维护预留，总需求上界80，低于示例配置100。它只核对配置算术，不是推荐生产连接数。使用PgBouncer时要区分客户端上限、每user/database服务端池以及数据库总连接上限。[R1-E02](https://www.pgbouncer.org/config.html) 每个并发任务有自己的短生命周期Session；SQLAlchemy明确Session/AsyncSession不供多个并发任务共享。[R1-E07](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)

### 6.3 分步执行，避免全因子爆炸

1. 先执行A–H正确性和单请求基线，使用small数据、一个服务进程、固定模型stub；收集真实SQL/对象扇出替换假设。
2. 在同一环境运行10、50 Agent闭环，比较一个与多个服务进程；验证池预算、取消、限流和独立命令复验。
3. 在medium数据运行50、200档，交错历史/图/上下文/写作/提交，分别冷暖缓存和20%热点。
4. 对已验证设置施加open-loop倍率、同步突发、80%热点，找有效吞吐与排队的转折；记录负载机未发出请求。
5. 只有前述正确性通过后，探索500/1000与large数据；可以报告该档位未达到及具体瓶颈。不要先启动1000个真实付费模型调用。
6. 选代表性可持续负载做长时运行，至少跨过清理、快照和索引维护周期；建议起始4小时、后续24小时，均为待执行时长。注入worker退出、提交丢回包、索引暂停与恢复。
7. 重复关键设置、保存输入和输出；必要时换种子检查热点偶然性。真实模型短卷实验独立进行，校准思考时间、token及语义返工率，不把stub质量当文学效果。

## 7. 验收门槛与后续扩展

正确性门槛：测试中不得出现重复世界效果、越权接受、主/候选污染、世界时间被墙钟推进、不可还原已保留历史或模糊状态被伪装确定。出现其中任一项即停止相关接受路径，不用更快吞吐抵消。

性能门槛在P0/P1基线后固定：每类请求的交互预算、最大排队年龄、拒绝比例、索引追赶预算、总内存/连接预算和恢复目标分别设定。可采用同环境基线相对回归门槛，例如P95退化超过20%时必须解释，但它是候选项目门禁，不是测得的性能保证。排队在稳态窗口持续增长的档位不可标作可持续容量；拒绝、限流和不完整结果必须计入报告。

事务级40001需要重新执行完整事务决策，部分其它错误需区分持续冲突与可重试故障；不能一律无限重试，更不能通过重新调用模型“碰运气”恢复原事件。[R1-E05](https://www.postgresql.org/docs/17/mvcc-serialization-failure-handling.html)

| 取舍 | MVP / 早期选择 | 何时比较替代方案 |
|---|---|---|
| SQLite / PostgreSQL | 生产并发以PostgreSQL验证；SQLite仅独立离线辅助 | SQLite WAL同库仍单writer，不能作为多worker事务语义替代证据 [R1-E01](https://sqlite.org/wal.html) |
| 关系时态查询 / 专用图库 | PostgreSQL索引、限定递归、派生邻接 | 实测复杂遍历占主要成本，且新库能保持权限/版本/失效语义 |
| 单进程 / 多进程无状态 | 共享持久状态、少量进程及总池预算 | CPU/连接等待/吞吐曲线表明增加进程有净收益 |
| 模块化单体 / 微服务 | 单仓库模块边界与多个worker角色 | 独立资源/故障隔离确有需求，拆分收益覆盖一致性和运维成本 |
| PG任务队列 / 消息队列 | PG任务状态＋outbox，有限重试 | 清理、抢占或投递吞吐已成瓶颈；业务幂等不交给队列保证 |
| 进程缓存 / 共享缓存 | 版本键缓存与同键构建合并 | 多进程重复构建成为显著成本；共享层仍复验权限 |
| 同步 / 异步投影 | 关键状态与最小失效同步；检索/摘要异步 | 显式水位和一致性契约成立后扩展可容忍滞后部分 |
| 提交序列 / 细粒度冲突 | 保留短分支提交序列，封闭命令依赖守卫 | 先优化token粒度和批量；只有序列临界区实测饱和才研究分片 |
| MCP / HTTP / SDK | 统一应用服务，选择一个主要外部接入 | 分别比较传输开销、会话/身份、批量与Host兼容，不重写业务 |

## 8. 本轮实际完成的验证资产

本轮运行 `python benchmarks/calculate_load.py`，生成 [JSON](../benchmarks/load_model_result.json) 与 [CSV](../benchmarks/load_model_table.csv)：5档人口×3缓存假设，共15行计算结果；另有固定种子的虚拟到达计数、闭环变慢敏感性和连接预算算术。模型没有睡眠、网络、数据库或真实模型调用。

1000档参考闭环在每次工具额外增加5秒后，计算到达率由39.94降为32.24请求/秒；独立到达的计划负载仍为39.94。该算例只说明负载生成方式的差别，不能得出任何服务延迟结论。

统一机制检查实际运行原18项及R1新增17项，共35项通过；新增范围和反例见[R1实验说明](../experiments/R1_NOTES.md)。它们是显式有限交错的标准库参考模型，没有数据库、真实并发或模型调用。

所有A–H业务案例及真实压测仍未执行。本轮没有把模拟到达量写成完成吞吐，没有把未调用的模型计为已支出费用，也没有将35项内存机制实验升级为数据库并发证据。

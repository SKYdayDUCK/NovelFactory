# P5.5 Redis Streams 消息总线

## 事件身份与路由

PostgreSQL 的 `nf_outbox.outbox_id` 是稳定的 event_id。Redis ID 只标识一次投递。工作进程共享消费组，组与组独立。每个作品都使用以下六条版本化流。应用身份不能连接 Redis。完整正文只能通过经授权的业务服务读取。

| routing_key | Redis Stream | 消费者组 |
|---|---|---|
|domain|nf:events:domain:v1|world、compute、recovery、log|
|model|nf:jobs:model:v1|model、world、recovery、log|
|world|nf:jobs:world:v1|world、log|
|compute|nf:jobs:compute:v1|compute、log|
|observability|nf:events:observability:v1|statistics|
|maintenance|nf:jobs:maintenance:v1|recovery、log|

`EventEnvelope` 的版本为 1。payload_ref 是 `outbox:<UUID>`，producer 固定为 nf.outbox。trace_id 优先来自持久事件，其次是 task_id，再次是 event_id；correlation_id 缺省使用 trace_id。generation 是产生该记录时的代际。未提供的关联、作品、分支、任务、世界引用为 null。WorldRef 包含三项 UUID；任何附加字段都会被舍弃。未知旧 topic 只发送 domain.changed；数据库保留原主题。内部 observability 只触发统计，从而阻止日志递归。角色可用工具与权限仍由 P5 在执行时检查。

## 事务与恢复

0008 在 0007 之后安装投递触发器，新增事件只在本地 SQL 事务作一次索引写入。旧 Outbox 分批回填。Relay 短事务用 SKIP LOCKED、唯一租约 token 认领，释放数据库连接后才对 Redis 进行批量 XADD。成功回写 token 与 redis_id。发送与回写之间中断会保持重复投递机会。既有 Outbox.state 和原 Inbox 收据保持兼容。

组接收端先 XAUTOCLAIM，再 XREADGROUP。将消息同 PostgreSQL 当前留存的权威 Outbox 元数据比对。通过行锁保护订阅收据，业务回调与原 nf_inbox(consumer,message_id) 共用事务，提交之后才 XACK。回调必须仅使用传入的连接写入同库；模型网络调用由持久工作提示交给原 P5 租约及调用账本处理。处理失败通过 SAVEPOINT 回滚效果及收据，五次后进入 DEAD。错误信息存固定代码。损坏、超长、来自未知未来事件的消息只保存传输定位到隔离表。每组都有自己的完成时间、Stream ID、尝试次数和错误。领取者及空闲时长由 Redis PEL 提供，relay 租约持久存在 PG。

Redis 断开期间继续接受 PostgreSQL 世界事务和审计。恢复后 relay 补发。定期 repair 比对每个未完成订阅的 Stream 实体、组游标及 PEL；Stream 已删除、恢复位置领先、游标曾越过但无持久收据时，会重新发布稳定 event_id。若整组丢失，消费者以 0-0 重建组。只有 DEAD 需要通过 redrive 修复后解封。世界接受、代际、权限、模型调用发送和 UNKNOWN 约束继续由原服务判断。恢复到模型发送之后的数据库历史缺失位置，须先完成供应商或 Host 对账，再开放调用。

## 安装与运行

Linux 或 Windows 的 WSL2 内安装 PostgreSQL 17、Redis 7 或 8（XAUTOCLAIM 要求 6.2 以上）、Python 3.12，按根安装指南安装项目锁定依赖。P5 PostgreSQL 模式仍可无需 Redis 服务启动。Redis 模式使用独占实例和独立数据目录。以下命令在项目根执行，环境变量通过服务管理器单独提供。真实凭据不要加入仓库或命令历史。

```bash
redis-server configs/redis-eventhub.conf --dir /var/lib/novelfactory-redis --aclfile /etc/novelfactory/users.acl
python -m alembic upgrade head
python scripts/run_eventhub.py relay
python scripts/run_eventhub.py status
python scripts/run_eventhub.py repair --limit 128
python scripts/run_eventhub.py trim --retention-seconds 86400
python scripts/run_eventhub.py redrive --event-id UUID --group statistics
```

通过 `NF_DATABASE_URL` 绑定单一权威库，`NF_REDIS_URL` 绑定同一部署的独占 Redis，跨机使用带证书验证的 rediss:// 和私网。ACL 文件所有权归 Redis、权限 0600；禁用 default 用户，给服务账户独立密码，角色账户没有 Redis 权限。将 [ACL 模板](../configs/redis-eventhub.acl.example) 的三个占位符分别替换为该账户随机密码的 SHA-256 十六进制摘要，保留摘要前的井号。通过服务管理器分别注入 relay、worker、maintenance 的连接串。使用独占实例的数据库 0。客户端 ACL 覆盖状态采样所需的 EXISTS 和 XINFO GROUPS。

生产部署给不同进程各自的 NF_REDIS_URL。trim 需专门的维护身份。ACL 不授予 KEYS、FLUSHDB、CONFIG 或角色应用访问。AOF everysec、noeviction、256 MiB 和 maxclients 64 是本地初始值。按实际峰值及 AOF 重写期间占用配置私有实例的资源限制；达到上限时 XADD 失败，已提交事件仍留在 Outbox。将持续增长的 backlog、oldest_wait、Redis pending/lag、DEAD 和磁盘不足接入告警。CLI relay 独立占用至多 2 个 PG 和 2 个 Redis 连接；在进程数上累计配额，给正式提交和管理留余量。

trim 仅在所有需要的订阅都有持久 DONE、超过保留期且权威源仍可重放时逐条删除已确认的前缀，未完成的订阅形成保留边界。在 Linux/WSL2 服务管理器中以 maintenance 身份设置每分钟执行一次的定时任务，命令为 `python scripts/run_eventhub.py trim --limit 256 --retention-seconds 86400`。每次最多检查每条流前 256 条，在积压持续增长时按实际处理速率增加频率或批量。PG 外键保护重放来源；本版未提供删除 Outbox 或归档交付记录的命令。按部署保留策略归档证据时，须先保证历史重算源与备份的可读性。禁止用无条件 MAXLEN 裁剪核心消息。

升级在 Alembic 的安装事务内创建触发器和空表，等待任务仍在原 P5 表内。代码回退可停 Redis 守护进程并按项目执行围栏切换为 PostgreSQL 模式。空扩展可 downgrade；一旦尝试投递、创建订阅或记录隔离证据，就拒绝危险降级。仅由触发器建立的未尝试发布指针可由原 Outbox 完全重建，允许回退到 P5。

## 运维诊断与故障时间线

在运维服务账户下运行 `python scripts/p55_diagnostics.py --limit 100`，可选 `--component relay` 或 `--since 2026-11-11T00:00:00+08:00`。入口只读 PostgreSQL，返回持久的基础设施观察以及 `nf_scale_decisions` 中已有的加减并发原因、目标值和连接池压力。操作员可以在 Redis 离线时查询。该入口不向角色 MCP 注册；只给运维服务账户相应的数据库权限。

0012 的 `nf_service_diagnostics` 用固定组件、固定错误码和分钟分桶，记录首次、最后观察、采样次数以及恢复时间。连续错误在各服务进程每 30 秒最多写入同类采样一次；这一计数表示采样数。PENDING_RECLAIMED 单独累计 XAUTOCLAIM 实际取回条数，同一条消息再次被取回时会再计数。失联不等同于进程已经死亡；操作系统或容器服务日志提供 exit code、信号与进程退出原因。重启或网络恢复后，正确的 Redis PING 可关闭连接问题，成功的真实 XADD 才关闭发送失败。短暂 SQL/池超时保留消息 Pending，不消耗毒消息的业务重试次数。

诊断表不设 Outbox 触发器，无任何诊断事件回发到 log/statistics。业务或世界接受事务不访问该表。运维信息没有原始异常文本、连接串、Prompt、Worker 自选名称、模型密钥或角色资料。数据库不可写时，服务输出固定错误码和 UTC 时间到 stderr；Linux 由 systemd journal 或容器日志采集，Windows 服务由其进程管理器保留。存活进程在数据库恢复后补记这段故障以及恢复时间。若进程在连接恢复前终止，这一段只能从进程管理器保留的日志中查到。

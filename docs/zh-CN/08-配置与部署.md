# 配置与部署

[English](../en/08-configuration-and-deployment.md) · [快速开始](02-快速开始.md)

单机开发有两种配置。只运行小说内核时，仓库根目录的 [Compose 文件](../../docker-compose.yml)在本机 `55432` 端口提供一套 PostgreSQL 测试库。需要 Workshop、作品级模型路由或双服务恢复时，使用[双服务模板](../../reports/p6_readiness/templates/wsl/compose.yaml)。以下命令采用后一种配置。

## Windows 与 Linux 原生运行

在仓库根目录使用普通服务账号、Python 3.12 和 uv。以下 PowerShell 示例将对象保存到本机 NTFS，Docker Desktop 承载根目录 Compose 文件中的 PostgreSQL 17 测试库。Python、MCP、HTTP 和 Supervisor 均在 Windows 中原生运行。示例使用的口令只适用于本机一次性测试库，长期部署要配置独立数据库账号和口令。

```powershell
uv sync --locked --group dev --python 3.12
docker compose up -d --wait postgres
$env:PYTHONUTF8 = '1'
$env:NF_DATABASE_URL = 'postgresql+psycopg://nf_dev:nf_dev_local_only@127.0.0.1:55432/nf_test'
$env:NF_OBJECT_ROOT = Join-Path $env:LOCALAPPDATA 'NovelFactory/objects'
$private = Join-Path $env:LOCALAPPDATA 'NovelFactory/book-one'
uv run --no-sync python scripts/nf.py doctor
uv run --no-sync python scripts/nf.py migrate upgrade head
$book = uv run --no-sync python scripts/nf.py init-book --book reports/p6_readiness/templates/book.json --private-dir $private | ConvertFrom-Json
uv run --no-sync python scripts/nf.py grant-resume --admin-binding "$private/control.json" --work-id $book.world_ref.work_id --branch-id $book.world_ref.branch_id --object-root $env:NF_OBJECT_ROOT --hours 24 --output "$private/resume.json"
'{}' | uv run --no-sync python scripts/nf.py call --binding "$private/resume.json" nf_project_status
uv run --no-sync python scripts/nf.py serve --host 127.0.0.1 --port 8000
```

初始化命令在创建私有目录时赋予当前用户可继承的专有 ACL。已有目录共享给其他账号，或绑定文件的所有权、ACL 无法验证时，命令会拒绝读取。对象目录应放在服务账号拥有的本地磁盘。Linux 使用 0700 的私有目录和 0600 的绑定文件。NF 与 Workshop 各自安装的 wheel 共享同一份私有文件校验代码。Windows 的每个 stdio Host 及其子进程归一个 Job Object 管理。使用原生 Codex 时，将 `codex.exe` 加入 PATH，或把其绝对路径写入 `NF_CODEX_EXECUTABLE`。

`control.json` 中的管理员绑定用于签发权限，`resume.json` 中的限分支绑定用于状态查询和恢复。`grant-resume` 只创建新文件。重复运行时复用仍在有效期内的绑定，续期时使用新的输出文件名。示例授权在 24 小时后失效。`doctor` 检查本机依赖并报告配置是否存在。迁移和经过授权的状态查询会实际访问数据库。建书和查询状态均不产生模型调用。

HTTP 命令会占用当前终端。要在另一终端运行世界任务 Worker，先在那里设置相同的数据库 URL、对象目录和私有目录，再执行下方命令。按 Ctrl+C 启动优雅停机。负责模型调用的 Worker 还需要已授权的 Provider 配置和预算。

```powershell
uv run --no-sync python scripts/nf.py supervisor --access-file "$private/supervisor.json" --processor world --adaptive
```

恢复当前分支已就绪的工作可执行 `'{}' | uv run --no-sync python scripts/nf.py call --binding "$private/resume.json" nf_resume_project`。Linux 设置下文的环境变量后使用同一组 Python 命令。双服务引导脚本与 Bubblewrap 角色工具隔离使用 Linux。Windows CI 在原生 PostgreSQL 17 上覆盖初始化、真实 MCP stdio、模拟 Provider、对象发布、租约恢复、取消和空闲连接释放。对应提交的测试结果给出实际验收范围。

## 首次建立服务

准备 Linux 或 WSL2、可用的 Docker Engine 与 Compose v2，以及 uv 和 Python 3.12。在仓库根目录执行。两个项目分别安装依赖，Workshop 的 `streams` 额外依赖用于 Redis 通知。

```bash
uv sync --locked --group dev
uv sync --project workshop --locked --group dev --extra streams
umask 077
export P6_PRIVATE="$HOME/novelfactory-local"
export P6_SECRETS="$P6_PRIVATE/secrets"
mkdir -p "$P6_PRIVATE"
.venv/bin/python reports/p6_readiness/templates/wsl/make-secrets.py
docker compose -f reports/p6_readiness/templates/wsl/compose.yaml config --quiet
docker compose -f reports/p6_readiness/templates/wsl/compose.yaml up -d --wait
```

密钥生成器仅在首次建库时运行。它为两个数据库和 Redis 生成独立口令，并要求密钥目录归当前用户所有、权限为 `0700`。重新启动时，复用该目录和原数据卷，重新导出 `P6_PRIVATE`、`P6_SECRETS` 即可。模板中的服务端口只绑定本机回环地址。

| 服务 | 端口 | 服务账号或用途 |
| --- | --- | --- |
| NF PostgreSQL 17.11 | `56431` | `nf_service` 访问 `novel_factory` |
| Workshop PostgreSQL 17.11 | `56432` | `aw_service` 访问 `agent_workshop` |
| Redis 8.0.2 | `56379` | NF 使用逻辑库 0，Workshop 使用逻辑库 1 |

## 应用迁移

以下是本机运维终端的设置。部署独立进程时，把每个服务的 DSN 和 Redis URL 交给对应的操作系统账号。角色工作区保存其绑定和 MCP 入口；模型密钥由执行宿主读取。

```bash
export NF_DATABASE_URL="postgresql+psycopg://nf_service:$(cat "$P6_SECRETS/nf_password")@127.0.0.1:56431/novel_factory"
export AW_DATABASE_URL="postgresql://aw_service:$(cat "$P6_SECRETS/aw_password")@127.0.0.1:56432/agent_workshop"
export NF_REDIS_URL="redis://:$(cat "$P6_SECRETS/redis_password")@127.0.0.1:56379/0"
export AW_REDIS_URL="redis://:$(cat "$P6_SECRETS/redis_password")@127.0.0.1:56379/1"
export NF_OBJECT_ROOT="$P6_PRIVATE/nf-objects"
.venv/bin/python -m alembic upgrade head
workshop/.venv/bin/aw-migrate upgrade
.venv/bin/python -m alembic current
workshop/.venv/bin/aw-migrate current
```

两个服务账号分别拥有自己的数据库。新的部署从空库执行迁移；升级已有部署前，先用恢复副本验证迁移和在途任务。[运维与恢复](09-运维与恢复.md)

## 绑定组织、作品和执行宿主

1. 运维人员在 Workshop 建立安装关系与组织，为管理者签发私有绑定。组织管理者可以按授权给作品发布角色路由策略。
2. NF 执行进程通过 `NF_RUNTIME_PROFILES` 读取宿主私有的 Provider 配置。`secret_ref` 填宿主环境变量名。模板的 `model` 是待替换的账号模型名。首次验证可保留零预算，在授权正式推理前完成状态查询与路由预览。
3. NF 管理员为每本书建立作品记录、分支、预算和 Supervisor 绑定，将路由策略激活到对应作品，再登记流水线。检查角色路由使用 `runtime_policy.py preview`；查看已登记节点使用 `run_supervisor.py --pipeline-status`。

完整的两作品命令、模型配置样例和现行接口可从这些入口继续。[两作品运行手册](../../reports/p6_readiness/README.md) · [Provider 模板](../../reports/p6_readiness/templates/providers.json) · [接口参考](07-接口参考.md)

验收环境实测了 Python 锁文件安装、两个独立 PostgreSQL 集群、Redis Streams 和 MCP stdio。两个 Compose 文件通过 Compose v2.32.4 配置解析。Windows 宿主上的 Docker Desktop 启动和真实计费账号接入需在目标机器核验。

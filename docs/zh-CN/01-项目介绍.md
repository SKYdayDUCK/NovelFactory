# 项目介绍

[English](../en/01-project-overview.md) · [快速开始](02-快速开始.md)

写到第二卷时，作者常常要回头核对三件事：某个人物当时知道什么，编辑读过哪一版草稿，以及哪段情节已经成为世界事实。NovelFactory 为这些问题保存可查询的记录。作者可以在分支里尝试一个转折，同时让另一章沿现有版本继续写。

## 一场戏的去向

1. 规划者提出下一场戏的目标。候选计划记录它依赖的世界版本和假设。
2. 选择 Creative Harness 的候选方案时，由持有 `APPROVE` 且独立于提案者的主体作出决定。角色任务拿到冻结的上下文、当前代际及获准的工具。尚未收到消息的人物，与已经读过消息的人物，看到的材料不同。
3. 写作者提交一版草稿。编辑按这份草稿定位具体段落，提出定向修改。新稿拥有自己的标识，旧稿与审读记录仍可查阅。
4. 控制端核对世界提案、当前 HEAD、相关变化、批准记录和任务权限。接受成功后追加事件和世界版本。正文发布和世界事件接受分别留下回执。
5. 下一卷可采用已经审核的跨卷快照。前提发生变化时，受影响的任务可以重新规划，并可追查上一卷的世界状态和编辑当时看到的材料。

## 自动化与运行方式

轻量管理器由程序实现：监听持久任务变化、检查权限与预算、按需唤醒 Worker，空闲后回收执行池。规划、事实核查、复杂编辑与审核交给 Codex；正文、角色扮演和简单摘要交给 DeepSeek Flash。正文接受、世界事件接受、章节冻结和整书最终冻结各自留存回执。缺少授权、未知请求或反复无进展时保留诊断和原账务，等待可验证的新输入。

运行 `python scripts/nf.py dry-run --books 3 --chapters 5 --seed 42`，可以在不连接数据库和模型的情况下，经过真实 Harness 调用边界模拟三书完本。随机审核退回会触发新稿、事实对账及重新审核，最后检查同一终稿上的双路独立全文审核与最终冻结清单。异常矩阵另外覆盖 27 类场景。[Dry Run 与程序生命周期](11-Dry-Run与程序生命周期.md)

真实生产使用 PostgreSQL 保存权威状态和调用账本，Redis 可提供通知。Provider 密钥通过宿主凭据库或环境变量提供，仓库仅登记引用。上下文先校验信息边界，再将稳定角色/Schema 和材料放在请求前部、易变任务身份放在尾部，提高供应商前缀缓存的复用机会；实际命中率以回执 Token 统计为准。[模型、凭据与缓存](05-Agent-Runtime.md)

离线模拟验证程序通路；真实小说还必须通过实际数据库、宿主回执及全文文学审核。恢复实验中已保留原三书快照和未知账务，生产前验收仍持续记录真实结果。

## 每个参与者能做什么

| 参与者 | 职责 |
| --- | --- |
| 作者或项目操作人员 | 管理项目绑定、作品范围、模型配置和支出授权，处理需要控制身份的决定。 |
| Workshop 管理者 | 管理员工、层级、委托、已授权的 Skills 及其范围。组织通过安装凭据连接 NovelFactory。 |
| 角色宿主 | 执行一个已登记的任务，提供获准工具，读取冻结输入，并在使用时核对当前授权。 |
| 编辑或评估者 | 针对指定的候选、稿件或指令版本作出判断。要求独立审核的操作还会核对实际主体身份。 |

研究人员可以用确定性夹具复现计划、知识切面、修订与恢复，不必向模型商发送手稿。读者可以另行评分，并指明所读的稿件。正式写作时，为每部作品准备独立的项目目录，再配置获准的模型路由。[Agent 系统](04-Agent系统.md) · [Agent Runtime](05-Agent-Runtime.md) · [性能与实验](10-性能与实验.md)

# 运维与恢复

[English](../en/09-operations-and-recovery.md) · [配置与部署](08-配置与部署.md)

排查一次写作停顿时，先固定作品、分支、任务代际和 Attempt ID。NF 的 PostgreSQL 保存任务、预算、调用和世界变更回执；正文与材料按哈希写在 `NF_OBJECT_ROOT`。Workshop 在自己的数据库保存安装关系、委托和预算预留。Redis 传递通知，恢复所需的业务记录来自两侧数据库。

## 找出停在哪一步

| 现象 | 操作 |
| --- | --- |
| 跨卷节点一直等待 | 使用对应作品的 Supervisor 绑定执行 `--pipeline-status`。检查上游交接、节点状态、当前任务与历史任务的 Attempt ID。 |
| Redis 暂停后任务没有唤醒 | 读取 EventHub `status`，对照数据库订阅状态与最近成功时间。恢复 Redis 后执行一次 `repair`，再执行一次 `relay --once`。 |
| 模型已发送，宿主没有拿到可靠回执 | 保留原 Attempt 及其预算预留。核对 Provider 回执、账单和 NF 账本。已记录为 `UNKNOWN` 的发送需要对账。 |
| 角色重新连接后看不到原工具 | 核对绑定的安装、作品、分支、身份、代际与撤权状态，再由角色通过 `tools/list` 获取该会话的工具。 |

下面的只读命令在服务运维账号中执行。`NF_ACCESS` 指向当前作品的私有 Supervisor 绑定；EventHub 需要 `NF_DATABASE_URL` 和 `NF_REDIS_URL`。

```bash
.venv/bin/python scripts/run_supervisor.py --access-file "$NF_ACCESS" --pipeline-status
.venv/bin/python scripts/run_eventhub.py status
```

## 备份和隔离恢复

管理员需要 NF 服务库及对象目录的访问权，并准备同一主版本的 PostgreSQL 客户端工具。在线备份从一致的数据库快照读取，核对对象清单与解释器材料。快照覆盖该 NF 数据库保存的作品。将生成的目录作为一个整体归档。

```bash
umask 077
export NF_RECOVERY_RUN="$(mktemp -d)"
.venv/bin/python scripts/backup.py create "$NF_RECOVERY_RUN/backup" --online \
  --report "$NF_RECOVERY_RUN/create.json"
.venv/bin/python scripts/backup.py verify "$NF_RECOVERY_RUN/backup" \
  --report "$NF_RECOVERY_RUN/verify.json"
```

恢复前准备一个全新的空 PostgreSQL 17 数据库，将其 DSN 写入 `NF_RESTORE_DATABASE_URL`。保留源服务配置，另指定新的对象目录。恢复命令会检查备份哈希、目标数据库版本及是否为空，导入后对比快照，再更新在途任务的代际以阻止旧工作进程继续提交。

```bash
.venv/bin/python scripts/backup.py restore "$NF_RECOVERY_RUN/backup" \
  --restore-object-root "$NF_RECOVERY_RUN/restored-objects" \
  --report "$NF_RECOVERY_RUN/restore.json"
```

核对 `snapshot_equal_before_fencing` 和 `fenced_tasks`。若返回 `RESTORE_TARGET_NOT_EMPTY`，选择一个新的空数据库和对象目录。[备份入口](../../scripts/backup.py) · [恢复与任务代际](../../src/novel_factory/infrastructure/recovery.py)

## 演练 WAL 和双服务恢复

下面的演练自行创建临时源与恢复集群。将 PG17 工具目录设为 `PG_BIN`，将 `redis-server` 放在 `PATH`，用普通用户从仓库根目录执行。回执中的目标 LSN、重放记录、校验结果和预算状态可用于复核实际恢复位置。

```bash
export NF_DRILL="$(mktemp -d)"
.venv/bin/python scripts/pitr_drill.py --with-redis --shared-token-budget \
  --creative-harness --output "$NF_DRILL/pitr"
```

生产安装恢复后，两侧数据库可能停在同一委托的不同阶段。例如，Workshop 已预留预算，而 NF 已写入任务回执。按原 operation ID 核对双方记录，再恢复调度。

1. 停止两侧调度及工作进程，恢复数据库和匹配的 NF 对象快照。保持 NF 出站围栏，对每个安装运行 Workshop 的 `recovery freeze`。
2. 使用绑定到该安装的 NF 启动器，按批执行 `aw-reconcile --lookup-only`。处理全部分页，让每项委托在当前冻结代际取得新的远端证明。
3. 分别导出 NF 的安装快照和 Workshop 的已核对账本。NF 使用 `manage_workshop_binding.py reconcile` 核验 Workshop 快照，Workshop 使用 `recovery permit` 核验 NF 回执。保留有分歧的原账本、操作 ID 和 `UNKNOWN` 预算预留，处理完差异后恢复服务。

双库集成演练分别验证过同一物理集群内的两个数据库、两个独立物理集群，以及 Redis 丢失后从数据库重建通知。双服务启动、冻结、分页查回执和解冻的参数见[Workshop 运维手册](../../workshop/docs/operations.md)。[WAL 演练实现](../../scripts/pitr_drill.py) · [双库恢复验收](../../workshop/integration/test_paired_restore.py)

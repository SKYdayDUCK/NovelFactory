# P3-02｜有限宏微等效替换与验收

## 结论与适用范围

本轮实现了**已接受原子事件的有限微观效果表示替换**。正式替换保持 `occurrence_id` 和 `effect_group_id`，创建新的 `event_version_id`、`representation_id`，在现有 REPAIR 分支中重放、独立审批和严格接受；原事件、原 WorldRef、历史正文均保留。世界效果不进行“先减回再加上”，不另建权威历史库。

已验证的范围是 `nf-reducer-1` 注册的精确时间效果：资源分配、物品所有权与持有/位置、生命周期、伤势等注册关系、观察/信念/私有决定及其证据。微观分步可以拆分同一原子阶段的资源数量、组织不同参与者的效果项，但不能把同刻联合裁决解释成依次获得资源的行动。

这不是通用自然语言或社会模拟等价求解器。新增承诺、新传闻、变化的伤势区间、提前得知消息、临时权属改变、未知解释器、模糊/延迟效果，以及不能保持的精确事件版本因果引用，都拒绝直接替换。需要新增故事事实时继续走受审核的历史修订。当前上限为 200 个选中事件、64 个微步骤、256 个效果、1,024 个观察边界，不能据此声称任意长篇历史的等效替换已经完成。

## 为什么不只比较终态

证明首先比较每个故事坐标上的转换。资源比较分别保留总借方和总贷方，净额相等但多走一次资源、用同刻入账融资、三方超额请求都不能混过去。非资源效果保留其完整注册字段，包括关系身份、效力边界、角色身份、认知类别、认知来源和证据。

随后从同一 genesis 重建替换前后**完整选中历史**。对所有实体创建、关系生效/终止、资源/生命周期转换、认知获得、事件发生及注册消息/过程时间，逐一比较边界前和边界时的状态。检查对象包括活跃关系、资源余额、生命周期、角色认知、状态覆盖和事件可见性。允许变化的只有有明确定义映射的表示版本溯源；任意 UUID 文本不会被泛化替换。

注册效果在这些边界之间是分段常量，因此“相同入口 + 相同注册转换 + 相同因果与所有边界可观察状态”构成此有限模型内的证明。自然语言暗示、模型行为和文学效果不包含在证明范围内。

例如 D30 交付 30 袋，拆成 D30 同阶段 10+20 袋可以通过；改为 D25 先交 10 袋、D30 再交 20 袋，即使 D30 余额相同也会拒绝。相同终态下提前收到消息、暂时把剑交给第三人、伤势提前生效，同样拒绝。

## 服务与正式接受边界

- `WorldRepresentationService.prepare_refinement(principal, request)`：读取一个固定 WorldRef，校验证明，持久化服务端专属 `REFINEMENT_PROOF`，返回修订命令；不修改世界。相同业务幂等键返回相同产物，不同内容复用该键拒绝。
- `WorldRepresentationService.propose_refinement(...)`：仅接受从证明源版本分叉的 REPAIR 任务，复核当前任务代际、权限、解释版本、选中事件、快照和过程状态，并调用原有 `Kernel.propose`。
- `REPAIR_EVENT.equivalence_proof_ref`：兼容性增加的可选字段。带证明时，调度验证钩子在提案、证书准备和正式接受时重验服务端证明及具体替换字节；客户端上传普通 `EVIDENCE` 无法伪造证明。
- 正式接受继续要求不同主体审核，使用严格 HEAD、原来的证书、scope 失效、事务回执、对象哈希核验、任务 fencing。提升 canon 继续走原有双 HEAD/CAS 协议，服务不会自动提升。

已完成联合裁决的过程状态、消息通道及原裁决证据保持不变。历史评估记录继续指向原已接受的发生事件版本；新修订通过 `refinement_source_event_ref` 和 `equivalence_proof_ref` 明确关联替换映射，不静默改写历史评估。一般过程 Retcon 缺少该证明时仍返回 `SCHEDULE_REPAIR_REQUIRED`。

证明记录所有登记依赖的保守复审清单和已发布清单引用。正式修订依旧使相应 scope 失效；既有正文不会被自动替换。证明不替代正文一致性复核和文学审核。

## 实际验证

环境：CPython 3.12、真实 PostgreSQL 17.11、独立 loopback 测试集群；`fsync=on`、`synchronous_commit=on`。无外部模型调用。

| 执行范围 | 实际结果 |
|---|---:|
| 新增有限证明单元用例 | 26 passed |
| 新单元用例 + 既有全部契约兼容性用例 | 117 passed，0.94 s |
| 新增 PostgreSQL 集成用例（最后 API 复核） | 9 passed，7.18 s |
| 新 PG 用例 + 既有模拟/历史修复/history epoch 回归 | 33 passed，32.42 s |

测试覆盖三方资源分配与超分配、净零循环、所有权/持有与伤势有效区间、四种认知/决定记录及其来源、原子事件身份、下游精确因果版本拒绝、未知解释器、伪造证明、跨作品/错误分叉、短故事授权、角色隔离、取消代际、并发同键证明，以及提交前故障和提交成功后丢回执。最后一种情形重试返回同一接受回执，正式选择仍只有一个发生事件，粮食仍为 70/30。

首次 PG 测试有两个测试设置错误：新审核者未显式获授 REPAIR 分支访问。服务正确拒绝；修正测试授权范围后全部通过，没有放宽服务授权。

  uv run python -m pytest tests/integration/test_refinement.py \

## 验收分层

工程：以上有限机制及对应真实数据库反例通过。HTTP 对外路由与全仓 CI 由本轮集成提交统一复核，正式 SHA/CI 见总报告。

真实模型：本模块没有调用模型，不能声明模型驱动微观场景已验收。

文学质量：仍需对完整作品独立阅读评价。工程等价只证明登记事实与认知边界相容，不证明细写更好看。

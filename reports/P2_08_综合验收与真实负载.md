# P2-08 综合工程验收与真实服务负载

日期：2026-11-10。基线：`0609f680fad782c827dd3834a073f8f9bcddaf0d`。

**结论：A–H 已形成可追溯的 PostgreSQL 工程测试组合，50 逻辑任务的受控负载完成；200 档混合负载没有完成全部预期业务。P2-08 的测量工作已执行，容量门槛不能标记为通过。** 真实模型生产及作者全文阅读由独立门槛记录，本报告不以工程夹具代替它们。

## 1. 本批新增内容

- [真实 TCP 行为负载](../benchmarks/p2_behavioral_load.py)：建立独立 PostgreSQL 数据库，经正式 bootstrap、任务、授权、上下文和世界接受服务准备数据，测量状态、图、历史、Context Compiler、提案、证书、接受及同键重试。请求经过 Uvicorn 的真实 loopback TCP，不使用内存 ASGI transport。
- [R1-F 人口组合](../tests/integration/test_p2_r1_f_population.py)：160 个固定读任务、20 个独立 guarded 命令、20 个密封角色意图。独立命令保留 W0；联合裁决在 HEAD 改变后必须显式重新建立共同输入。没有扩大 `JOINT_INTERACTION` 的权限或并发模式。
- [R1-H 网络丢回包](../tests/service/test_p2_response_loss.py)：TCP 代理收到上游已提交的成功回执后关闭下游连接，真实客户端得到 `RemoteProtocolError`；随后核对同键重试、内容不符、新键重复、撤权和 outbox 再投递。
- [A–H 执行矩阵](../benchmarks/p2_acceptance_matrix.py)：将原始设计检查与真实 JUnit 节点关联，原设计矩阵保持不变；正确性、负载和整体门槛分别输出。
- [只读指标后处理](../benchmarks/p2_load_derived.py)：从保留的逐请求数据重算分位数和计数，输出新文件，不覆盖原始结果。独立审查发现的 invalid-200 重试计数、计划到完成延迟、客户端等待者命名及负载门槛问题均有对应修复和反例测试。

本批未改变核心领域契约、数据库迁移、正式接受权限、历史语义或服务队列预算。

## 3. 环境、数据和统计口径

| 条件 | 实测配置 |
|---|---|
| 宿主 | Linux 6.18.57 x86_64；CPU 型号显示 AMD EPYC 9V74；本环境可见 9 个逻辑 CPU；可见内存 10,206,472 KiB；无 swap |
| Python / ORM / 驱动 | Python 3.12.14；SQLAlchemy 2.0.57；psycopg 3.3.8 |
| HTTP | Uvicorn 0.54.0；httpx 0.28.1；一个 API 进程；客户端与服务位于同一进程的独立事件循环，通过实际 TCP 通信 |
| PostgreSQL | 17.11；`max_connections=60`；`shared_buffers=128MB`；`fsync=on`；`synchronous_commit=on` |
| 应用连接池 | size=8，overflow=0；独立数据库观察器最多 1 个连接 |
| 接入预算 | 默认入站 128、队列 64、同 Principal 并发 2、排队超时 2 秒；没有为通过压测放大这些限制 |
| 50 档数据 | 82 实体、169 初始关系、4 个经 Kernel 正式接受的历史事件；50 个实际逻辑任务，另有 4 个初始化历史任务 |
| 200 档数据 | 262 实体、619 初始关系、4 个正式历史事件；200 个实际逻辑任务，另有 4 个初始化历史任务 |
| 模型 | 真实外部调用 0、在途 0、Token 0；未运行模型 stub；费用字段为未派发、无供应商账单 |

这是**小数据集真实服务实验**，不是设计中 10 万事件的 medium 数据，也不是 200 个真实模型完整创作。宿主与其他开发进程共享，所有延迟仅为本轮观察值，不能当作独占机器 SLA。

状态冷/暖表示同一进程查询结果缓存。没有清空 PostgreSQL shared buffers 或操作系统缓存。每个档位先执行新 Context Compiler，再对相同固定 WorldRef 的状态查询先冷后暖；命中仍做当前授权和版本检查。50/200 暖阶段分别观测到新增 50/200 次缓存命中，但这没有消除数据库访问。

**热点比例只描述读对象集中程度。** 20% 或 80% 的逻辑槽位读取同一个物品；每档共享写候选数始终为 `Agent数/10`，独立写候选也为 `Agent数/10`。没有将“80%读热点”写成“80%写冲突”。共享候选的一个选定控制命令先成功接受，才发送剩余陈旧候选；后者验证依赖冲突。故事中的胜负由独立 F 用例的封闭联合裁决验证。

计数分别保留：逻辑任务数、HTTP 尝试/完成/未发送、成功调用、SQL、世界新 revision、重复回执、预期冲突、429、客户端错误和模型调用。有效调用吞吐扣除重复回执；世界吞吐仅计新 revision。`peak_outstanding_client_requests` 包含 HTTPX 连接池等待，不能当作服务端在途；实际服务端入站峰值另看 `ingress`。

最初全图密集阶段和两次 50 档调速失败均保留。最终冻结分布为：普通查询计划 10 次/秒、编译最多 10 次/秒、写任务每秒启动 1 个；混合阶段 90% 状态、10% 图查询，另每任务执行一次 FACT 历史查询。图/状态与提案/证书真实重叠。200 档冻结后失败，不再继续降速或换分布寻求 PASS。

|---|---:|---:|---:|---:|---:|---|---|

表中分位数包含成功和失败响应。新增的 `*.derived.json` 另给成功、失败/拒绝、计划到完成三组分位数。200 正常档计划 1141 次调用，实际发送 1081 次，剩余 60 次因前序提案/资格步骤未完成而未发出；200 热点档计划 2141、发送 2089，差 52。不得把未发出的下游步骤算作成功。

200 正常档 200 次编译、200 次冷状态和 200 次暖状态成功；FACT 历史是 **189/200 成功**，图查询是 **18/20 成功**。200 热点档 FACT 历史 **193/200 成功**，图查询 **16/20 成功**。因此“200 个查询任务已建立”不能解释为整个混合工作流均成功。

两个最终热点实验的数据库语句数分别为 **13,778** 和 **51,213**；应用连接峰值均为 8，结束与真正的阶段汇合点为 0。最终数据库分别约 **12.58 MB**、**18.36 MB**（十进制）。Python 客户端＋服务进程峰值 RSS 为 **108,992 KiB**、**151,828 KiB**，不是 PostgreSQL 总内存。数据库连接状态、等待、WAL 和统计计数逐采样保存在原结果中；数据库统计计数可能有采样延迟，不能取代应用 SQL 监听器的准确语句计数。

## 5. 开放到达的生成器限制

计划到达率设为 1000/s，但同进程生成器受到 Python/服务 CPU 竞争影响，**实际没有达到该速率**：

| 档位 | 开放到达调用数 | 实际客户端调用开始速率 | 完成窗口 | 完成率 | 最大调度滞后 |
|---|---:|---:|---:|---:|---:|
| 50 | 250 | 40.47/s | 7.21s | 34.66/s | 5.90s |
| 200 | 1000 | 23.86/s | 44.56s | 22.44/s | 40.86s |

客户端调用开始还可能包含 HTTPX 连接等待，因此这些值也不是声称达到的网卡请求率。服务入站峰值分别仅为 27、34。实际 429 背压已经在混合读写负载中观察到；本轮不能宣称通过 1000 RPS 入站能力验证。若下一轮要测精确开放到达能力，需要独立负载进程/机器并校准实际发包率；本轮不扩大到 P3-04。

扣除重复回执后，50/200 最终热点档的有效调用吞吐分别 **12.7003/s、10.3898/s**。200 热点档“计划开始到完成”的 P95 为 **39.15 秒**，远高于只看请求已开始后延迟的 P95 **5.98 秒**。两组同时保留，避免用生成器停滞隐藏长尾。

## 6. 失败、修复与能够复现的范围

1. 初次 10 槽位 smoke 的控制写者 grant 没有 `ADMIN`，而现有 control_operator 查询 profile 要求该能力；2 个编译请求收到正确的 403。修正的是隔离控制面夹具，未放宽服务授权，随后 smoke 完成。
2. 初次 50 档有一次 TCP ReadError；后续将客户端 keepalive 存活期缩短到 2 秒以避开服务端 5 秒闲置边界，原失败保留。负载没有无限重试。
3. 密集图查询与提案重放重叠时出现长尾、队列超时和 429；没有增加连接、队列时限或关闭版本检查来提高成绩。
4. 第一份 200 全图实验中，预先指定的共享候选未能完成准备，旧脚本仍发送其它共享候选，导致一个合法控制命令被接受。**该失败实验不能作为故事联合仲裁证据。** 修复后先要求指定接受确实成功，否则不发送其它共享候选；若本应冲突的请求返回 200，也会记录明确的正确性错误。200 冻结正常档共享余额仍为 100，证明未在缺少指定接受时自行选胜。
5. 并发阶段的单项结束不等于全部工作结束。连接释放断言放到 `mixed_join`，同时保留 prepare/graph/history 中间连接样本；未删除这些在途连接记录。
6. 独立数值审查重算了所有保存的结果，见 [independent_numeric_review.json](../evidence/p2/batch3/independent_numeric_review.json)。该报告只证明算术口径一致，不把 FAIL 负载升级为 PASS。

两个最终热点实验的源快照完整保留，且原始结果的源哈希与快照逐字节吻合：

`evidence/p2/batch3/load/source_snapshots/e3af3c650cec9d48708f4a400b947f0740e7d5b6006a6b540b2bc9ff0d2888da.py`

之后的统计修复仅通过独立派生文件重算，没有覆盖上述原始结果。**较早的开发尝试只保留 raw、命令、日志和当时源哈希；没有完整保存当时每版脚本，不保证从最终脚本逐字复现早期失败。** 后续 CLI 会在启动时保存已加载的源字节，避免再次出现这个缺口。

## 8. 进入 P3 的依据与停止点

# P1 对象、任务与恢复模块：实现及独立验证

## 范围与状态

本记录覆盖 P1-03、P1-05 和 P1-07 的模块实现，以及它们与正式接受协议的接口。完整世界语义、HTTP 权限网关、青霜剑恢复后的业务查询，由整合测试另行验收；本记录不代替 P1 总验收，也不涉及 P2。

最新模块复验：**34 passed，0 failed，0 skipped**。此前的 27 项可靠性测试与 20 项世界并发、来源及修订反例联合执行为 **47 passed，0 failed，0 skipped**；收尾审查又增加了 7 项对象持久性和任务接受事务反例，34 项结果对应更晚的可靠性模块版本。执行对象为 PostgreSQL 17.11，`fsync=on`、`synchronous_commit=on`；不存在 SQLite 回退。初始失败及修复后的输出均予保留。

## 关键协议

### 对象及引用

`ObjectStore.put(bytes)` 返回 `ObjectRef(sha256,size)` 前完成内容核验、临时文件 fsync、不可覆盖的原子链接发布以及父目录 fsync。两个并行写者保存相同内容会得到相同引用；不会以新内容覆盖既有哈希路径。哈希不符或对象缺失均失败关闭。

`verify` 在检查正确内容后也同步该文件、分片目录与对象根目录。原因是另一个写者可能在原子 link 后、目录 fsync 前崩溃；“路径已经可见”不能证明发布已持久化。复用已存在对象与登记数据库引用都要重新确认这一持久性边界，不能仅验证哈希后返回。

新增数据库引用时先取得对象目录的共享 `flock`，验证内容，再持有该锁完成短数据库事务。GC 取得排他锁后才读取当前数据库保留集合，因而不能在“验证完文件、尚未提交引用”之间删除文件。数据库通过 `nf_object_refs.object_hash` 和事件/任务结果对象外键引用 `nf_objects`。

本阶段的保留策略应将所有正式、候选和任务结果对象纳入保留集合；不主动清除历史正文。最小 GC 处理未登记的持久孤儿和中断上传。若以后删除登记对象，必须把元数据删除、保留引用检查与文件回收作为新维护协议一并设计，不能只删文件。

### 任务与输入代际

创建仅允许 generation 0 的 READY/BLOCKED。领取以真实 PG 锁和 `SKIP LOCKED` 执行，增代并存储新的不可变输入快照与执行身份。新代际保留原 WorldRef，清空旧 ContextBundle 绑定；编译器必须持久化本代 ContextBundle，随后同事务绑定。

`bind_context_in_transaction` 和 `guard_task` 查询真正持久化的 ContextBundle，并核对 task、generation、principal、grant、work、WorldRef、依赖指纹。只有 UUID 非空不足以获得接受资格。运行期接受还核验租约、deadline、当前状态。RESULT_STORED/VALIDATING/WAITING_REVIEW 可进入后续审查，ACCEPTED 不允许再制造世界效果。

取消与结果保存针对同一任务行线性化。旧租约或旧代际结果仍可归档为 LATE，但不能成为当前有效结果。返回丢失后用相同结果 ID/内容重取既有收据，变更内容则报幂等冲突。世界提交须先查询原命令收据，再调用 `guard_task`，从而保留撤权/取消后的合法历史回执读取语义。

P1 封闭命令的正式世界接受在同一数据库事务调用 `accept_in_transaction`，将其任务置为 ACCEPTED，清除执行租约并写入 task.state Outbox。世界事务回滚时任务终态和消息一起回滚；一个任务完成接受后不能重新领取、取消或提交新的世界效果。未确定的调用账本占用不会因任务终态而消失，已经发送的调用仍可进行明确结算。通用产物任务的验证状态机保留独立含义，不把任意 TaskResult 的 SUCCEEDED 映射成正式世界接受。

任务服务是可信内部应用组件。外部调用者不能通过自行填写 `principal_id` 获得权限；公共网关必须先认证并校验当前 grant、作品及任务范围。公开领取注入 principal/grant/task 过滤条件，在查询阶段排除他人任务。`create`、`claim`、`cancel`、`store_result` 提供 `authorize_in_tx` 回调；统一 Kernel 在每个实际写事务取得维护锁后、任何队列或任务锁之前重新校验并锁定当前授权，阻断“外层预检通过后撤权、内层仍写入”的时间竞争。有效 TaskResult 的新收据和重复收据均按原始 TaskReceipt Schema 验证。

### 调用和预算

调用状态为 PREPARED、SENT、SUCCEEDED、FAILED、UNKNOWN。预留和结算锁定任务、预算及调用记录，以相同锁序完成。工作预算与任务货币上限均核验，任务 token 上限也覆盖已结算和未确定占用。

发送网络请求前完成 SENT 短事务并归还连接。UNKNOWN 继续占用货币和 token 预留；恢复不会假定未执行并自动重调。只有明确结算后才能释放占用。未发送 PREPARED 只可按零费用/零 token 取消，不可直接宣称调用成功。结算幂等，改变已结算数据会被拒绝。

本轮没有接入外部模型；调用账本测试使用真实数据库生命周期。无法据此宣称供应商支持幂等、准确计费上限或网络副作用的 exactly-once。

### Outbox / Inbox

业务事务同时写入 Outbox。并行派送通过短租约领取，迟到的旧代际无法 ack 新派送。`consume(consumer,message_id,handler)` 把本地数据库副作用和 Inbox 记录放在同一事务：处理失败一起回滚，提交成功但确认丢失时重复消费不会重复产生本地效果。

handler 必须只操作提供的数据库事务。外部 HTTP、邮件、模型调用等副作用不属于本地 Inbox 的恰好一次保证，本轮未实现外部投递。

### 备份与恢复

普通写服务取得共享维护锁 `721943001`。备份先取得对象共享锁，再取得该 PostgreSQL session advisory lock 的排他模式，等待现有短事务排空；随后记录逐表规范化行摘要，运行真实 `pg_dump`，复制所有数据库登记对象，并保存解释器源文件、原始 Schema、查询权限配置 `runtime/query_profiles.json` 的内容与哈希清单。安装为 wheel 时优先读取包内 `data/contracts` 和 `data/runtime`；源码环境读取项目目录。校验同时比对备份文件和当前安装解释版本，权限配置变化或缺失会拒绝恢复。

恢复只接受显式提供的空数据库和空对象目录；使用 `pg_restore --exit-on-error`，对比全部 public 表的行数和精确服务器 JSON 文本摘要，并核验每个对象。这个比较在恢复后运行任务围栏之前完成。恢复随后将未终结任务增代并置为 PAUSED，SENT 调用转 UNKNOWN，派送中的 Outbox 旧租约失效。再次启动必须先完成对账/重验证，不能自动接受备份中的旧执行资格。

备份是单机 P1 逻辑备份，**不是 PITR**，不包括集群角色与外部系统状态。数据库检查和 hash 清单提供完整性检测；备份签名、加密、跨站点灾备和 WAL 保留不在本轮范围。

## 限制与整合检查点

1. 文件锁方案针对同一 POSIX 文件系统上的单机多进程；NFS/分布式对象存储必须另验一致性与锁语义。
2. 所有权威写入必须参与维护锁。直接持有数据库所有者权限的运维 SQL 不属于受限 Agent 接口。
3. 模块恢复夹具是最小真实 work/branch/revision。青霜剑、历史修订、认知权限等恢复后的完整业务结果，需要总体集成测试核对。
4. 任务权限由统一应用服务授予；模块 API 本身是内部可信组件。审计时应追踪每一个公开路由，确认不能直接暴露带任意 principal 的内部函数。
5. 原始 TaskSpec/TaskResult 2.0 Schema 保留。调用货币/token 记账和运行时租约采用内部 SQL 数据模型，不将运行字段塞回封闭原 Schema。
6. 记录的最初失败已经修复，仍需在最终冻结源码上执行全套集成检查。此处的最新 34 项模块结果及此前 47 项联合结果不能替代全项目最终结果。
7. 已发布崩溃反例实际终止了进程，并跟踪真实 fsync 调用；这证明恢复路径执行了必要持久化协议，不冒充物理断电或硬盘故障实验。

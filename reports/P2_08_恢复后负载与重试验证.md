# P2-08 恢复后的负载诊断与有界重试

## 本轮范围

本轮复用已找回的 `benchmarks/p2_behavioral_load.py`、A–H 矩阵、真实 PostgreSQL 与 TCP 故障测试。新增的是负载客户端的有界同请求恢复和更严格的结果口径，没有改变正式世界接受、权限、证书、任务代际、服务器队列或连接池。

本地测量在恢复的 `20971bcdb375197ba92181f74629a7f515e6c950` 工作树加本轮改动上执行，包含已恢复的 P3 Context Compiler 候选。它不是原始 P2-B 与新版本的纯规模/性能配对实验。完整应用源码 SHA-256、dirty 清单、负载源码快照和每条命令的退出状态均保留；GitHub CI 应按每次 run 的实际 commit SHA 解读。

## 旧 200 档失败的直接原因

对找回的原始 JSON 重新计数，得到下列因果链：

| 旧测量 | 提案成功/尝试 | 证书成功/尝试 | 最终新提交 | 操作队列超时 |
|---|---:|---:|---:|---:|
| 正常混合 | 27/40 | 14/27 | 7/21 | 50 |
| 80% 读热点＋开放到达 | 26/40 | 15/26 | 8/21 | 50 |

正常档提案阶段 13 次、证书阶段 13 次 `BACKPRESSURE`；热点档分别 14 次、11 次。正常档指定共享候选未能成功提出，因此驱动正确地没有自行选另一个胜者。两档实际准备完成的 7 个独立候选均接受成功；热点另外完成指定共享候选，形成 8 次提交。

这说明缺失提交主要发生在提案/证书被操作队列拒绝后，旧驱动直接终止其后续步骤。旧驱动的 `infrastructure_retries` 为 0。原数据中的操作队列峰值只有 24/25（预算 64），入站峰值只有 35/34（预算 128），但操作队列记录各 50 次超时；直接瓶颈是 2 秒操作等待预算被耗尽，而不是已经证明入站连接总量达到上限。

数据库记录没有死锁，也没有新增 `blks_read`。采样多数为 PostgreSQL 等待客户端，应用进程消耗较多用户态 CPU；这支持“应用侧状态处理、JSON/校验与同进程 CPU 竞争拖长操作时间”的解释，但尚不足以精确归因到某个函数。不能据此把问题归结成磁盘慢、数据库锁竞争，或宣称增加连接池必然解决。

重新计数见 `evidence/p2/recovered-load/historical_failure_diagnosis.json`，每个输入都有原始文件路径和 SHA-256；旧失败结果保持原样。

## 有界恢复的语义

新增参数 `--max-attempts` 默认 1，保留不重试的比较入口。本轮恢复候选固定为最多 5 次尝试，启动重试的预算为 30 秒。只对已校验的 429/503、`retryable=true` 且恢复动作是 `WAIT` 或 `RETRY_SAME_COMMAND` 的响应，以及真实 HTTP 传输错误重试。

每个逻辑操作只序列化一次请求，所有尝试发送完全相同的字节，保留幂等键、任务代际、WorldRef、proposal 与 certificate。等待取服务 `Retry-After` 与 1、2、4、5 秒指数退避中的较大值；等待结束后、再次发出之前重新检查期限。此预算限制新尝试的开始，已经在途的请求沿用 HTTPX 的 30 秒分阶段超时；这不是单次操作严格的总墙钟上限，事件循环拥塞也可能推迟超时回调。

403/401、代际错误、依赖冲突、失效证书、历史变化等不是基础设施重试。驱动不会换键、自动重新准备证书或改绑当前 HEAD。上游提交后回包丢失时，仅重发原请求查询其幂等结果，世界效果不再执行第二遍。业务故事中的共享胜负仍由预置控制决定/另行联合裁决测试验证，没有改成数据库抢锁决定胜者。

服务负载始终保留原定逻辑任务数、初始到达率、查询配比、共享候选数、冷热查询与期望提交数：50 档 6 个、200 档 21 个新提交。尝试数可能增加，但没有减少逻辑操作。未发出的下游调用仍算未完成；业务通过明确要求未发出的逻辑操作为 0。

## 计数和门禁

结果分别提供 `first_attempt_capacity_gate`、`bounded_recovery_business_gate` 和总体 `capacity_gate`。恢复通过不能把首次背压或未达到的开环到达率改写成容量通过。

HTTP attempts、逻辑操作、成功调用、重复回执、新世界 revision 和模型调用分开统计。`infrastructure_retries` 是额外尝试次数；失败 429、重放回执不能计入有效世界吞吐。逻辑操作完成延迟从原定开始计算到最后一个尝试结束，包含退避和调度延迟；逐尝试响应延迟另列。

开环实际速率只统计 `attempt=1`，重试不成为新的外部到达。冻结检查为实际首次 call-start 达到目标的 95%；同进程生成器的 call-start 仍可能包含 HTTPX 连接等待，因此即使通过这一检查，也不等于已经证明线速或持续生产容量。派生记录的首尝试 completion rate 包含拒绝，只是响应完成率，不是有效业务吞吐。

CLI 默认 `--gate-scope capacity`，容量未满足返回 1。明确选择 `--gate-scope recovered-completion` 时，退出码只检验恢复后的业务完成和不变量；JSON 同时保留容量未满足。A–H 的完整门禁读取容量字段；`executed-tests` 仅控制 CI 已执行范围，不能把整体 P2 改成通过。

## 复现与后续

```bash
uv sync --locked --group dev --python 3.12
uv run --no-sync python scripts/with_postgres.py --pg-bin "$PG_BIN" \
  --log-dir evidence/reproduction/load-pg -- \
  .venv/bin/python -m benchmarks.p2_behavioral_load \
  --agents 200 --profile overload --hot-fraction 0.8 \
  --arrival-rps 10 --open-loop-rps 1000 --rounds 5 \
  --max-attempts 5 --retry-budget-seconds 30 \
  --gate-scope capacity --output evidence/reproduction/load.json
```

正常档使用 `--profile mixed --hot-fraction 0.2`；50 档保留其余参数只改 `--agents 50`。要专门检测恢复完成，可以显式使用 `--gate-scope recovered-completion`，报告的容量字段不变。原始逐请求日志由 GitHub Actions Artifacts 保存；仓库保留精简结果、源码指纹和稳定证据索引。

若 200 档仍有操作未恢复或开环目标未达到，继续标 `NOT_MET`。下一项合理工作是用独立进程/独立机器校准开放到达，并在有采样依据后分析应用 CPU 和事务内状态解码成本。不能用增加超时、降低到达率或删除失败候选把容量门槛变绿。

真实模型生产仍为 `BLOCKED_ENVIRONMENT`，作者全文评价仍为 `PENDING_AUTHOR`。本轮没有模型调用，也没有文学质量改善结论。A-04 的异步依赖 worker、E-02 的统计侧信道、H-05 的完整索引 worker 和严格 JOINT 重绑定限制，仍按既有 A–H 矩阵保留。

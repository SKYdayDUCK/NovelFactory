# P0/P1 复现与运行指南

本指南以交付包中的 `project/` 为工作目录。命令中的 Python、迁移、Schema、脚本和测试均来自该项目；测试生成的数据与原设计资料、正式小说数据分开。交付证据保存在包中的 `evidence/`，建议将审核者重新运行的证据写到新目录，保留首次开发记录。

## 1. 要求与已验证范围

| 项目 | 本轮实际验证 | 复现要求 |
|---|---|---|
| Python | CPython 3.12.14 | Python 3.12；`.python-version` 固定 3.12.14 |
| 依赖安装 | uv 0.13.6、CPython pip 25.0.1、锁定依赖、全新 venv 与 wheel | `uv.lock` 或带哈希的 `requirements.lock`；首次安装需要可访问包源 |
| PostgreSQL | 17.11，Debian 官方二进制包 | PostgreSQL 17 服务端及 `initdb/psql/pg_dump/pg_restore/createdb` 工具 |
| 操作系统 | Debian 13 x86_64 | Linux 或兼容的 Linux/WSL 环境；对象锁使用 POSIX `flock` |
| 服务接入 | 本机真实 TCP HTTP、多进程 Uvicorn | 能监听 loopback TCP；无需外部模型密钥 |
| Docker | 镜像 manifest 与 digest 已核查，未运行容器 | 可选；本次执行器没有 Docker |

本轮 PostgreSQL 启用数据页校验、`fsync=on`、`synchronous_commit=on` 和 `full_page_writes=on`。没有 SQLite 回退。数据库测试缺少 PostgreSQL 时会失败，不会自动跳过。

所有示例仅面向隔离开发/审核环境。包内 `configs/environment.example` 的固定数据库密码是公开的本地示例值；正式 Bearer token 由本地 bootstrap 随机生成。不要把生成的凭据文件、数据库目录或对象目录再次放入审核包。

## 2. 安装项目

解压后进入项目根目录：

```bash
cd novel_factory_P0_P1_review/project
uv sync --locked
export NF_EVIDENCE_DIR="$PWD/../reviewer_evidence"
mkdir -p "$NF_EVIDENCE_DIR"
```

如果已安装 uv 但没有目标 Python，可先执行 `uv python install 3.12.14`。Python/uv 的下载步骤取决于审核环境的网络许可；工具版本见 `reports/环境与依赖验证.md`。

不使用 uv 管理项目时，可按相同依赖哈希安装到独立 venv：

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements.lock
.venv/bin/python -m pip install --no-deps .
```

`requirements.lock` 包括测试工具。`pyproject.toml` 固定构建工具 hatchling 1.33.0；运行时依赖的精确版本由锁文件确定。wheel 包含所有 Python 模块、公开 Schema 和运行时查询 profile。数据库迁移与操作脚本属于完整项目交付内容，运行时应保留项目目录，不要只复制 wheel 后假定迁移文件也在其中。

独立安装审查脚本会创建临时空 venv，校验依赖哈希、构建 wheel、安装 wheel，并在仓库外导入包以排除 editable/source 路径污染：

```bash
.venv/bin/python scripts/run_recorded.py "$NF_EVIDENCE_DIR/clean_install" -- \
  .venv/bin/python scripts/clean_install_check.py
```

P0 阶段树使用 `scripts/clean_install_check.py --phase P0`。`P0-complete` 标签不包含 P1 服务、P1 数据库迁移和 PostgreSQL 业务测试；该参数只检查 P0 已交付模块。

最终 P1 脚本另支持 `--installer pip`，使用 CPython 自带 `venv` 与真正的 `python -m pip` 安装锁定依赖和 wheel；构建步骤仍调用 uv。两种安装器均已实际运行。完整 pip 路径证据为 `environment/pip_clean_wheel_reproduction_final.*`。

## 3. PostgreSQL 路径 A：已实际验证的独立进程包装器

### 3.1 准备 PostgreSQL 17 工具

如果系统已有 PostgreSQL 17，指定其二进制目录，例如：

```bash
export PG_BIN=/usr/lib/postgresql/17/bin
"$PG_BIN/postgres" --version
```

在与本次环境相同的 Debian 13 x86_64 环境，没有 root 权限也可以下载并校验固定的官方 Debian 包：

```bash
.venv/bin/python scripts/bootstrap_pg17_debian.py .runtime/pg17
export PG_BIN="$PWD/.runtime/pg17/dist/usr/lib/postgresql/17/bin"
"$PG_BIN/postgres" --version
```

脚本校验三个包的 SHA-256 后解压，不安装系统服务。它针对 Debian 13 ABI；其他系统应安装兼容的 PostgreSQL 17 或采用 Docker。下载文件与哈希见 `evidence/environment/postgresql_download.json`。

### 3.2 验证空库迁移

```bash
.venv/bin/python scripts/run_recorded.py "$NF_EVIDENCE_DIR/p0_migration" -- \
  .venv/bin/python scripts/with_postgres.py --pg-bin "$PG_BIN" \
  --log-dir "$NF_EVIDENCE_DIR/p0_pg" -- \
  .venv/bin/python scripts/p0_database_check.py
```

这会创建真实空集群，执行 `0001` 迁移两次，核验原三份 Schema 哈希，并从两个独立 PostgreSQL backend 读取 PID。P0 检查应在空库执行；已经升级到 `0002` 的库不适合作为 P0 空库验收目标。

验证完整 P1 迁移：

```bash
.venv/bin/python scripts/with_postgres.py --pg-bin "$PG_BIN" \
  --log-dir "$NF_EVIDENCE_DIR/migration_head_pg" -- \
  .venv/bin/python -m alembic upgrade head
```

包装器默认创建新临时集群，测试完成后关闭并清理数据库，持久保留指定日志。它把 `NF_DATABASE_URL`、`NF_TEST_DATABASE_URL`、`PG_BIN` 和 PostgreSQL 客户端连接环境传给被执行命令。测试夹具再创建自己的随机数据库，避免测试世界互相污染。

本次执行器禁止 Unix socket，不同工具命令拥有不同网络命名空间。包装器把数据库和测试/HTTP 子进程放在同一命令中，解决这一限制。普通工作站不一定存在此限制。包装器无需降低 PostgreSQL 持久化保证。

## 4. PostgreSQL 路径 B：Docker Compose

该路径已给出固定镜像 digest 和配置，但本机没有 Docker，未在本轮执行。有 Docker 的机器可运行：

```bash
docker compose up -d --wait postgres
export NF_DATABASE_URL='postgresql+psycopg://nf_dev:nf_dev_local_only@127.0.0.1:55432/nf_test'
export NF_TEST_DATABASE_URL="$NF_DATABASE_URL"
export NF_OBJECT_ROOT="$PWD/var/objects"
.venv/bin/python -m alembic upgrade head
```

集成测试需要创建独立测试库，因此示例账号有 `CREATEDB` 能力。Compose 中的超级用户是隔离测试账号，不是建议直接分配给外部 Agent 的生产数据库权限。

备份/恢复测试还要求运行 Python 的环境中有 PostgreSQL 17 `pg_dump`、`pg_restore` 工具；仅启动数据库容器不会把工具放入宿主机 PATH。安装客户端后设置 `PG_BIN`。常规 pytest 命令直接运行，无需再套 `with_postgres.py`。

结束服务使用 `docker compose down`。需要保留测试数据时保留命名卷；重新开始全新数据库前，应明确处理自己的测试卷，避免误用旧迁移结果当作空库验收。

### 5.4 按风险分组复核

将相应 pytest 参数放在同一个 `with_postgres.py -- ...` 中执行：

| 关注点 | pytest 目标 |
|---|---|
| 世界事务、幂等、分支、旧版历史 | `tests/integration/test_world_kernel.py` |
| 真实连接并发、依赖守卫、write skew、phantom、撤权等 | `tests/concurrency/test_world_races.py` |
| 历史/关系/认知、权限、UnifiedQuery、Context Compiler | `tests/queries` |
| 对象持久化、GC、任务租约、取消、预算、Outbox | `tests/reliability` |
| 专门的故障与隔离恢复 | `tests/reliability/test_recovery.py` |
| 真实 HTTP 边界、限流背压、两 API 进程共享状态 | `tests/service/test_http.py` |
| 通过真实 TCP 创建/领取任务、编译、提案、证书、正式接受及幂等重试 | `tests/service/test_http_write.py` |
| 10/50 逻辑 Agent 与有计划到达率的有限负载 | `tests/service/test_http_load.py` |

例如并发与恢复：

```bash
.venv/bin/python scripts/run_recorded.py "$NF_EVIDENCE_DIR/concurrency_recovery" -- \
```

负载测试的独立客户端拥有独立授权和任务，服务器通过真实 TCP 接收请求。指标区分逻辑 Agent 数、成功工具请求/秒、SQL 条数/秒、数据库事务和正式世界修订数；本轮 HTTP 压测为查询负载，新增世界修订为 0，不能将 RPS 当成事件提交 TPS。规模与限制详见 `reports/HTTP与初步负载验证.md`。

## 6. 启动最小服务与真实历史查询

### 6.1 创建私有测试访问文件

对已启动并完成迁移的隔离数据库：

```bash
export NF_OBJECT_ROOT="$PWD/var/objects"
.venv/bin/python scripts/bootstrap_fixture.py --fixture r1_sword --history \
  --output .runtime/demo_access.json
```

脚本通过应用服务创建青霜剑测试世界，再经任务、Context Compiler、提案、证书和正式接受路径写入历史。它在新文件中生成随机 Bearer token、固定 WorldRef 和查询任务；权限为 `0600`，不向终端输出 token。默认拒绝覆盖已有访问文件。任务带租约和截止时间，过期后应创建新任务，不能修改旧任务输入绕过代际检查。

使用本地 PostgreSQL 包装器时，先建立可复用的隔离目录：

```bash
.venv/bin/python scripts/with_postgres.py --pg-bin "$PG_BIN" \
  --data-dir .runtime/demo_pg --log-dir "$NF_EVIDENCE_DIR/demo_bootstrap_pg" --migrate -- \
  .venv/bin/python scripts/bootstrap_fixture.py --fixture r1_sword --history \
  --output .runtime/demo_access.json
```

`--data-dir` 仅复用有专用测试标记的目录，拒绝接管没有标记的已有数据库目录。

### 6.2 启动 API

已启动的 Docker/独立 PostgreSQL：

```bash
export NF_POOL_SIZE=8
export NF_POOL_OVERFLOW=0
export NF_POOL_TIMEOUT=2
export NF_API_PROCESSES=1
export NF_WORKER_PROCESSES=1
.venv/bin/python -m uvicorn novel_factory.interfaces.http:from_environment \
  --factory --host 127.0.0.1 --port 8000
```

包装器复用上面的测试库：

```bash
.venv/bin/python scripts/with_postgres.py --pg-bin "$PG_BIN" \
  --data-dir .runtime/demo_pg --log-dir "$NF_EVIDENCE_DIR/demo_service_pg" -- \
  .venv/bin/python -m uvicorn novel_factory.interfaces.http:from_environment \
  --factory --host 127.0.0.1 --port 8000
```

`GET /health` 是进程存活检查，不证明每个业务查询可用。服务默认无 CORS 浏览器来源授权；用于有 Bearer 凭据的非浏览器 Agent HTTP 客户端。输入仍受当前 grant、TaskSpec、角色 profile 和固定 WorldRef 约束。

连接预算默认 API 池 8、独立 worker 预算 4、维护预留 16，共 28，小于测试数据库最大 60。新增 API/worker 进程必须同步配置声明的进程数与池预算，不能只增加 Uvicorn workers 而忽略每进程连接池。HTTP 请求排队与模型等待不持有数据库事务。

### 6.3 查询 D25 的所有权与实际持有

在可访问同一 loopback 网络的另一个终端运行：

```bash
.venv/bin/python - <<'PY'
import json
from pathlib import Path
import httpx
access = json.loads(Path('.runtime/demo_access.json').read_text())
with httpx.Client(base_url='http://127.0.0.1:8000', trust_env=False) as client:
    response = client.post('/api/v1/queries/timeline', json=access['query'],
        headers={'Authorization': 'Bearer ' + access['token']})
    response.raise_for_status()
    print(json.dumps(response.json(), ensure_ascii=False, indent=2))
PY
```

预期 D25 所有权属于主角、实际持有属于朋友；响应携带 WorldRef、解释版本和证据。当前 HEAD 可以晚于 D25，历史查询使用明确故事时间，不把 HEAD 版本号当作剧情时间。

若环境像本次执行器一样隔离每条工具命令的网络，不应期待第二条工具命令访问第一条的端口。使用下一节的一次性检查，数据库/服务/客户端都在同一执行环境中运行。

## 8. 备份与隔离恢复的操作命令

连接到自己的隔离开发数据库，配置好 `NF_OBJECT_ROOT` 和 `PG_BIN` 后：

```bash
.venv/bin/python scripts/backup.py create .runtime/backups/review_001 \
  --report "$NF_EVIDENCE_DIR/backup_create.json"
.venv/bin/python scripts/backup.py verify .runtime/backups/review_001 \
  --report "$NF_EVIDENCE_DIR/backup_verify.json"
```

备份目录必须是新目录。内容包括 PostgreSQL 自定义格式 dump、被引用正文对象、解释代码、公开 Schema、运行时权限 profile 及校验清单。备份冻结通过共享/独占维护锁和对象锁完成；所有应用写入路径必须遵守维护锁，直接用拥有者 SQL 绕过应用属于操作权限边界。

恢复前用 PostgreSQL 客户端连接环境创建新的空库。Docker 示例：

```bash
docker compose exec postgres createdb -U nf_dev nf_restore_review
export NF_RESTORE_DATABASE_URL='postgresql+psycopg://nf_dev:nf_dev_local_only@127.0.0.1:55432/nf_restore_review'
.venv/bin/python scripts/backup.py restore .runtime/backups/review_001 \
  --restore-object-root .runtime/restored_objects_review \
  --report "$NF_EVIDENCE_DIR/restore_review.json"
```

不要预先迁移恢复目标库，恢复要求其中没有业务表；对象目录也必须为空。必须使用备份清单匹配的解释代码、Schema 和角色查询 profile。版本不匹配会阻止恢复，不应编辑哈希绕过检查。

恢复先比较冻结数据库的规范化快照，再进行故障隔离：未完成任务增加代际并 PAUSED，未知外部调用保留 UNKNOWN，Outbox 在途投递回到可恢复状态。因此隔离后的任务表与冻结前不再逐字节相同，这是明确的恢复协议。旧 worker 不能用旧 generation 接受结果。

完整业务恢复断言位于 `tests/reliability/test_recovery.py`，包含事件/投影/任务/对象/Outbox/历史查询核验。此版本提供逻辑备份，不包含 PostgreSQL 集群角色、WAL/PITR、外部真实模型副作用对账或生产高可用切换。

## 9. 证据与审计方法

`run_recorded.py` 同时保存 `.log` 原始输出和 `.json` 元数据，记录 argv、工作目录、时间、环境和退出状态。pytest 另输出 JUnit XML 与 JSON。数据库日志包含版本与持久化配置。首次失败日志保留，由最终结果解释哪些问题已修复。

建议依次核验：

1. 在交付根目录校验 `MANIFEST.sha256`，确认代码、迁移、Schema、报告与证据完整。
2. 检查集成审计报告中的最终命令与机器可读结果；区分首次失败、最终成功及未执行范围。
3. 运行原契约检查与纯领域测试，再运行独立空库迁移和干净 wheel 一次性复现。
4. 重点复核正式提交、有限 guarded 模板、授权撤销、故事时间/修订区分、任务代际、对象持久化和恢复边界。
5. 查看 Git 提交/标签中的 P0/P1 阶段边界；不从本包启动 P2 自动小说生产。

## 10. 常见限制与处理

| 现象 | 原因与处理 |
|---|---|
| `PostgreSQL 17 binaries not found` | 指定 `PG_BIN` 到包含 `postgres/initdb/pg_dump` 的目录 |
| `initdb must run as a non-root user` | 包装器需普通账号；root 容器使用独立非 root 用户或 Compose |
| 创建 Unix socket 被拒绝 | 使用包装器禁用 Unix socket，以 loopback TCP 运行 |
| 前一命令启动数据库，后一命令无法连接 | 检查命名空间；把客户端和数据库放在同一次包装器调用 |
| HTTP 客户端意外请求 SOCKS/代理 | 本地请求用 `trust_env=False`；不要把 loopback 验证送到外部代理 |
| 版本/代际/租约错误 | 创建新任务、重新编译上下文与校验；不要修改旧 TaskSpec 或关闭守卫 |
| `RESTORE_TARGET_NOT_EMPTY` | 选择新的空数据库和对象目录，保留已有数据 |
| `INTERPRETATION_UNAVAILABLE` | 使用备份对应的代码、Schema 和查询权限 profile；检查校验清单 |
| 负载出现 429/503 | 记录拒绝、排队、成功量与连接占用，按预算调整速率；拒绝不计成功吞吐 |

本轮没有验证 Docker 容器启动、外部真实模型、原生 MCP Host、200/1000 Agent、长时间压力、百万级历史或跨卷生产。无状态 HTTP 接入与 10/50 逻辑 Agent 小规模负载已经实际运行；这些结果不能扩展为生产容量承诺。

# P3-04 / P2 A04、H05｜异步派生索引与工作者恢复

## 实现与边界

新增 `DerivedWorldWorker`，实际消费现有 PostgreSQL outbox 的 `world.accepted` 消息。每个不可变 WorldRef 生成带来源哈希的时间线、关系、认知、资源/生命周期历史和失效范围产物；对象写入现有 ObjectStore，数据库使用现有 artifacts、inbox、index_watermarks 表。没有新数据库、消息中间件或第二套权威历史。

每个产物身份由 WorldRef 和 `nf-derived-world-1` 版本确定。重投递和乱序处理生成相同来源、相同哈希；后来的计划/发布操作即使在同一 WorldRef 登记更高版本的 scope 失效，也不会改变这个历史世界索引的内容。该工作者仅覆盖固定世界修订自带的失效；计划、发布和连续性自己的异步主题并未在此实现。

物化阶段在事务外读取固定修订并写内容寻址对象。消费事务检查持久化消息、租约 owner/generation/expiry 和源哈希，先取作品 SHARE 锁、再锁定该分支，原子登记产物、两个索引水位与 inbox。只有该事务提交后才确认 outbox。水位按分支的 `branch_seq` 单调前进；候选分支不能更新 canon 或其他分支的水位。失败可留下未引用对象，由原有对象清理机制处理。

`dependency_impacts` 为拥有该分支及 WORLD 资格、无角色身份且故事授权足够的控制主体返回有上限的影响清单。缺少物化时返回 `INDEX_PENDING`，截断时 `complete=false`。当前世界提交仍由同步 scope 守卫判断依赖；工作者迟到不会让旧证书提交成功，也不会擅自取消任务、改变角色认知或改写正文。

现有 `WorldQueryService` 继续从 PostgreSQL 权威修订读取，并使用实际水位标明 CURRENT / STALE / PARTIAL。本轮没有声称把查询改造成使用未经权限过滤的派生大对象，也没有由此推导查询提速数据。新的产物与影响查询是可恢复的派生基础，不是新的授权入口。

## 真实故障与一致性验证

新增 `tests/integration/test_derived_worker.py`，10 个 PostgreSQL 集成用例。其中四个用独立 `multiprocessing` 子进程执行 `os._exit(74)`，分别在下列位置退出：

1. 对象已写入、消费事务尚未开始。
2. 产物数据库记录已插入、水位尚未更新。
3. 水位已更新、事务尚未提交。
4. 消费事务已经提交、outbox 尚未确认。

前三种恢复时重新消费；第四种由 inbox 去重后确认。真实退出后验证数据库持久状态，再让替代工作者接管。所有场景均确认：一个派生产物、两个一致水位、同一个世界修订和一个原正式事件，世界效果没有重放。

跨模块复核还发现：如果工作者先取 branch UPDATE，后插入 artifact 时隐式取得 work FK key-share，可能与先取 work UPDATE 的运行升级发生反向锁等待。现已显式先取 work SHARE、再取 branch UPDATE；受控 PostgreSQL 用例持有管理员 work UPDATE，验证工作者等待期间尚未占用 branch，管理员能继续获取 branch 并提交，然后工作者完成。该修复未给普通世界接受增加新锁。

其余用例覆盖新消息先于旧消息的乱序、过期租约与并发重复消费、候选分支隔离、晚到的非世界产物失效不会改变索引身份，以及工作者延迟期间的旧依赖证书拒绝和读接口显式陈旧标记。权限反例覆盖普通角色、附着角色身份的控制 grant 与不足的故事时间授权。

本地实测环境为 CPython 3.12、PostgreSQL 17.11、独立 loopback 生成数据集群；`fsync=on`、`synchronous_commit=on`、最大连接数 60。无真实模型调用。阶段结果：

| 验证范围 | 实际结果 |
|---|---:|
| 最初 8 个异步工作者用例 | 8 passed，5.67 s |
| 完整 9 个工作者 + 9 个宏微集成用例 | 18 passed，12.01 s |
| 工作者最终授权复核 | 9 passed，6.46 s |
| 补齐锁顺序的 10 个工作者 + 22 个运行升级用例 | 32 passed，11.72 s |

后续完整 CI 与远程提交 SHA 见本轮总报告。原始 JUnit 与 PostgreSQL 会话文件的 SHA-256 清单在 `evidence/p3/derived_worker/validation_index.json`；原始大日志应通过 CI artifact 保留。

## 运行与复现

正常部署由受信任的服务进程启动；数据库连接使用项目现有 `NF_DATABASE_URL` 环境变量，`--objects` 必须指向同一部署的对象目录。一次运行有界，达到上限或队列为空即退出，方便由既有调度器重复调用：

```bash
uv run python scripts/run_derived_worker.py \
  --objects /srv/novel-factory/objects --worker-id derived-01 --max-messages 100
```

独立 PostgreSQL 回归：

```bash
uv run python scripts/with_postgres.py --pg-bin "$PG_BIN" \
  --port 56452 --log-dir /tmp/nf-derived-pg -- \
  uv run python -m pytest tests/integration/test_derived_worker.py \
  tests/integration/test_refinement.py -q --junitxml=/tmp/nf-derived.xml
```

## 未完成的容量门槛

以上验证解决实际派生消费与崩溃恢复语义，没有测量 500/1000 Agent 下的工作者吞吐或长期队列积压上限。长期服务应监测 outbox 滞后、租约重领、物化耗时、对象大小及 branch lock 等待；大历史修订会产生较大的不可变派生对象，需要按实测决定分页或增量索引。相关高并发与长稳门槛由独立负载实验裁定，不能从这 10 个正确性用例推定通过。

当前持久化生产方式与原 ObjectStore/单 PostgreSQL 部署一致。跨主机对象共享、真实消息服务、多地域灾难恢复和文学质量不在此验证范围。

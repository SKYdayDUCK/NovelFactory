# P3-04 并发扩展与长稳验证

## 验收结论

**P3-04 完整容量与长稳验收仍未通过。** 已完成独立负载客户端、真实 PostgreSQL、双 API 进程下的 500 Agent 混合负载、1000 Agent 开放到达读负载，以及同一组服务进程持续 600 秒的读稳定性实验。500 Agent 完成全部 **51/51** 新世界提交；1000 Agent 的原 1000/s 到达目标没有达到；600 秒只读探针完成 **12000/12000** 有效响应。三者不能相互替代，也不能推导出生产环境的 1000 Agent 写入容量或多小时运行能力。

指标与原始文件 SHA-256 见 [CP3 性能证据](../evidence/p3_p4/checkpoint3/performance_summary.json)。本报告所有数值来自该次实际执行；未以 Agent 数量、计划到达率或 CPU 核数作吞吐估计。源码实现和实际检查点 SHA 的对应关系由总交接记录给出，负载 JSON 中的本地 Git HEAD 仍是 `206eaa5b655419d29bd6b15d618ae6eaf9048354` 加工作树修改，不能当成正式远程交付 SHA。

## 1. 环境、负载和计量边界

本地实际环境为 Python 3.12.14、PostgreSQL 17.11、SQLAlchemy 2.0.57、psycopg 3.3.8、Uvicorn 0.54.0、HTTPX 0.28.1。可见 9 个逻辑 CPU，型号标识为 AMD EPYC 9V74，系统报告内存约 9.7 GiB。没有读到标准路径的 cgroup 配额文件，也没有独占 CPU 承诺。其他开发/验证任务可能共享主机，因此这是有限开发环境观测。

三个实验顺序运行，数据库开启 fsync 和 synchronous_commit，shared_buffers 为 128 MB、max_connections 为 60。应用总池固定为 **8**，两个 spawn 服务进程各 4；观察器另使用 1 个连接。每个进程在 spawn 之后创建自己的池。客户端与 API 位于不同 Python 解释器，通过 loopback TCP 通信，但仍共享物理主机和 PostgreSQL。

总连接池没有扩大，多进程的其他局部预算并不等同于单进程：每进程最大入口 128、操作队列 64，双进程合计 256/128；进程内的按主体限流和查询缓存也各自独立。数据和权限仍由同一 PostgreSQL 权威事务校验。此测试工具不是已验收的生产进程管理器，也没有声称跨进程全局公平性和全局速率配额已经统一。

500 mixed 保留原负载比例、正常相位到达 10/s、写入到达 1/s、原始请求身份、5 次/30 秒有界同请求重试、2 秒队列超时及正式容量判定。500 个真实持久化任务对应 622 个实体、1519 条初始关系、4 个已接受历史事件；50 个独立命令及 50 个共享资源候选中预期产生 51 个新提交。共享候选的选定控制命令属于已有 TEST_FIXTURE，不代表由数据库抢锁顺序实现联合裁决。

1000 open-arrival 使用 1000 个真实任务/授权、5 轮共 5000 次固定切面状态查询，80% 读主体为热点。所有请求都保留结果记录，HTTPX 连接上限 256，没有自动重试。请求预编码，完整响应契约验证移到网络窗口之后执行，只有验证通过的 200 响应计入有效吞吐。新增的 `http11.send_request_headers.started` trace 观察 HTTP 头发送开始；它比协程计划时间更接近实际发送，但不是抓包，也不是服务器已经接收的证明。

600 秒稳定性探针复用同一组服务进程和固定 WorldRef，500 Agent 循环读取，状态/历史/图查询比例为 90%/5%/5%，目标 20/s；每 10 秒采集服务计数和进程资源。该探针正常内联完成响应验证，延迟口径因此与延后验证的 1000 开放到达探针不同。

500 mixed 的实际负载窗口为 362.238 秒，原相位调度本身约需 350 秒。7.5945/s 是这次完整业务流程的实际吞吐，不能据此判断服务峰值上限。160 个首试失败，224 次基础设施重试，原始容量规则保持 NOT_MET；49 个过期共享候选依照预期冲突拒绝。50 个独立资源及 1 个共享资源最终数量均为 99，51 个正式修订对应 51 个效果组，重复回执未重复扣减。记录中没有世界正确性错误或未解决的关键业务错误。

1000 开放到达网络窗口为 107.857 秒，随后完整客户端验证额外使用 2.516 秒。实际调度调用开始为 47.7143/s，实际 HTTP 头发送开始为 47.6432/s，远未达到 1000/s 的 95% 门槛。计划到网络完成的 P95 达 100103.45 ms，表明计划时间与实际完成时间有很大差距。移开客户端契约验证后仍存在明显到达不足，不能把全部问题归因于 JSON Schema 验证；HTTPX 调度/连接池、共享主机 CPU 和服务排队仍需跨主机对照。3541 个明确背压响应和 64 个传输失败全部作为容量失败保留。有效响应未发现切面或状态不一致，正式世界未改变。

600 秒实际窗口为 600.165 秒；10800 次状态读取、600 次历史查询和 600 次图查询全部通过完整契约及固定世界切面检查。服务结束时借出连接、活动请求和排队请求均为 0。脚本明确输出 `probe_gate=PASS` 与 `long_duration_gate=NOT_EXECUTED`，没有将有限读稳定性升级为持续写入、故障注入或多小时耐久性结论。

cursor 时间是并行连接上的累计客户端执行时间，含锁和线程调度等待、排除结果解码，不是数据库纯 CPU 时间。连接峰值 8 是各进程峰值之和，不能作为同时占用峰值的精确样本。500 mixed 的客户端用户/系统 CPU 为 15.881/0.948 秒，峰值 RSS 为 104924 KiB；两个新增只读探针没有单独记录客户端 CPU，不补造数值。

500 mixed 出现 **645 个 active/Lock 连接观测**，单条 cursor 最长 6.532 秒；该负载比 200 Agent 更明显地暴露写入事务竞争。它不是锁等待总时长，也没有提供锁对象和持有者归因，下一步应针对 prepare/accept 时段关联数据库锁链和应用 spans。1000 只读采样没有观察到 active/Lock，仍有大量 idle in transaction/Client；这与 CPU/反序列化/验证路径及客户端调度均可能贡献耗时相容，不能推断绝无短暂锁等待。三个实验的数据库累计统计均未报告死锁增加，原始观察样本保留。

稳定性实验的 RSS 历史峰值之和从开场 200976 KiB、60 秒 219948 KiB、120 秒 238440 KiB，升至结束 244008 KiB。300—540 秒采样约为 243868 KiB。`ru_maxrss` 是进程存续期高水位，并非当前驻留内存；这样的有限曲线不能证明无内存泄漏。查询缓存累计命中 2262、未命中 9738，平均每个成功请求仍触发 21.05 条应用 SQL，说明不能用“缓存存在”代替真实费用核算。

## 4. 故障恢复、Host 兼容和剩余边界

CP1 的 `tests/service/test_process_isolation.py` 已在真实两个 API 进程下完成：正式提交后代理丢弃回包，实际终止两个服务进程，重启后同请求取得完全相同的持久化回执且世界效果只有一次；过时代际和撤销授权依然拒绝。这是独立故障恢复测试，不是 600 秒负载期间的混合故障实验。异步派生工作者的集成结果由相应检查点单独交接。

尚未实测 1000 Agent mixed 写入。原准备全部候选、再集中接受的负载节奏，在 1000 档位会显著增加早期证书年龄，与现有 300 秒证书有效期形成调度约束。下一步应另建保持同等业务规模、明确有界在途窗口的 P3 流式准备/接受实验，再验证其依赖/冲突和公平性；不能为了跑绿而延长现有证书期限或修改原 P2 门槛。本轮没有把未执行的候选实验计为完成。

正式接受仍从 genesis 和已选择事件全量重放，`Kernel._accept_transaction` 对选择事件数量保留 **2000** 上限；查询扫描预算默认 10000。这里的有限合成世界远低于真正长篇跨卷事件规模。删除上限或未经证明地绕过重放都会影响可信内核，本轮没有这样做。

所有负载的真实模型调用为 0。内部 HTTP 接入、绑定授权和本地 OpenAI-compatible 协议夹具不等于真实商业 Agent Host 集成。没有对 Codex/Claude 等真实 Host 作兼容性验收，没有角色模拟/规划/写作/审核模型实测，也没有独立文学质量评价。

## 5. 可复现命令与独立审核

按仓库方式提供 `NF_TEST_DATABASE_URL`，或通过现有 `scripts/with_postgres.py` 创建隔离 PostgreSQL。负载会自行创建隔离测试数据库与临时对象目录，不操作生产库。

```bash
.venv/bin/python -m benchmarks.p2_behavioral_load --agents 500 --profile mixed --service-mode isolated-process --api-processes 2 --hot-fraction .2 --arrival-rps 10 --open-loop-rps 1000 --rounds 5 --max-attempts 5 --retry-budget-seconds 30 --gate-scope capacity --output ci-evidence/scale-500mixed-two-process.json
.venv/bin/python -m benchmarks.p3_open_arrival --agents 1000 --rounds 5 --arrival-rps 1000 --hot-fraction .8 --api-processes 2 --output ci-evidence/open-1000-hot-two-process.json
.venv/bin/python -m benchmarks.p3_stability --agents 500 --seconds 600 --read-rps 20 --api-processes 2 --output ci-evidence/stability-500-600s-two-process.json
.venv/bin/python -m pytest tests/unit/test_open_arrival_evidence.py tests/service/test_process_isolation.py -q
```

本次三个负载脚本退出码依次为 **1、1、0**，符合保留容量失败和有限只读通过的语义。不能把前两个非零退出改为成功来获得绿色检查。新增记账单元反例验证了非法 200 响应不算成功、429 不算吞吐成功、无或单个发送样本不能建立发送速率；完整阶段回归由正式提交记录关联。

大型本地逐请求与观察日志位于此次工作区 `perf-evidence`，仓库仅保留紧凑指标、60 个周期摘要和完整文件哈希。清单不会声称这些本地原始文件已经上传 Actions；[P3 独立规模实验工作流](../.github/workflows/p3-scale-experiments.yml) 重跑三种场景并上传自己的 Artifact，应另行核对 run ID、源码 SHA 与文件摘要，本报告不提前宣称远程重跑通过。审核优先核对三个门槛的不同含义、每个计划请求是否计入失败或成功、重复回执是否排除在新提交之外，以及共享资源和连接归还结果。

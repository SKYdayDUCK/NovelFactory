# P4-03 基础设施架构评估

## 决策

**本轮保留 PostgreSQL 与模块化单体，不新增独立图数据库、向量服务、Redis、消息队列、数据库读副本或分布式编排平台。** 独立 API/负载进程已用于测量，双 API 进程保留为有实际工程测试的部署候选；它仍需全局限流、公平性、运行管理和部署级故障验证，不能直接宣称生产扩容验收通过。

这一决策源于当前证据不足以证明新增基础设施能够解决瓶颈。它**不表示现有实现已经满足全部容量、长篇跨卷或长稳目标**。200 Agent 热点远程负载、500 Agent 首试容量、1000/s 开放到达目标仍为 NOT_MET；2000 个选择事件的全量重放边界也没有解决。应先完成应用路径与调度的受控优化，再以同规模、同正确性、同部署预算对照替代方案。

本评估的工程交付是可追溯的当前选择、各组件的准入证据和下一轮实验边界。它不是容量通过证明，也没有授权合并 PR 或改变 main。

## 2. 按组件的选择与准入条件

| 候选组件 | 本轮选择 | 现有证据与约束 | 重新考虑时必须补充的证据 |

| 向量检索服务 | 暂不引入 | 文学记忆目前是确定性中文语料和来源对照；没有授权模型/embedding 质量或成本实验 | 在同一授权候选池、相同预算与金标准上比较召回、错引/隐藏来源率、中文 token 成本、时间切面和完整证据；随后独立评阅完整作品，而非仅比较命中率 |
| Redis 或共享缓存 | 暂不引入 | 当前只增加 4096 项纯时间坐标缓存；世界/权限数据未加入新缓存。600 秒读探针中本地查询缓存命中 2262、未中 9738，仍有 21.05 SQL/成功读 | 证明可复用载荷及跨进程命中收益；冻结 WorldRef、解释 epoch、权限版本、任务代际和认知切面键语义；验证撤权、Retcon、升级、重启和坏缓存时无越权/过期答案 |
| 独立消息队列 | 暂不引入 | 热点失败发生在交互读以及 propose/certificate 的背压耗尽，队列本身不减少服务所需 CPU/锁工作。现有持久任务/outbox 与派生工作者沿用数据库事务边界 | 先测数据库任务领取、排队公平性、积压清空和租约恢复；候选 MQ 须展示同请求幂等、代际 fencing、UNKNOWN 外部调用预算和恢复对账均等价，并实测整体吞吐/尾延迟收益 |
| 多进程服务 | 保留双进程候选及可运行框架 | 已有真实双进程提交、丢回包后杀进程/重启和同回执恢复；500 mixed 完成 51/51，但容量未过。进程级入口/队列/限流预算会相加 | 在固定硬件、同数据、同总预算下比较 1/2/4 进程；验证全局公平性/限额需求、优雅退出、发布滚动、对象路径、健康检查、数据库连接上限与客户端独立供给 |

| 对象存储升级 | 保留当前实现，远程对象存储待验 | 已有内容摘要和对象清单一致性机制，P4-02 有真实隔离恢复。没有大对象/跨机带宽、远程可用性或复制延迟的测量 | 对真实对象数量/大小分布测上传、校验、读取、清单落点与恢复；证明缺失/半写/多版本/目标后对象的处理，不仅检查备份文件存在 |

## 3. 先解决的应用与事务问题

### 3.1 区分供给不足、首试失败和业务恢复

目前有三种独立结果：首试 HTTP 容量、实际开放到达供给、同命令有界恢复后的正式世界效果。新的基础设施比较必须同时保留三者。429 可以是正确背压，却仍是原容量门槛失败；重复回执可以证明恢复正确，却不增加新世界提交。1000 Agent 只是任务/授权数量，也不等于 1000 个模型请求同时执行。

优先在独立负载主机或固定 CPU 资源的环境测量客户端发送能力，再测相同请求的端到端路径。记录计划时间、实际 HTTP 发送开始、服务进入/退出和完整验证完成时间。当前响应验证延后实验已排除一部分客户端干扰，但实际发送仍不足；下一步不能把 `agents × rounds / 计划秒数` 当实测吞吐。

### 3.2 关注 JSONB、全量重放与锁内工作

小范围纯值缓存与元数据 SQL 已通过语义反例和完整回归；它们没有改变世界事实。下一步应对大世界、长历史分别量化 JSONB 读取字节、解码、Schema 验证、哈希、事件重放及数据库锁持有时间，并将 source/ref/hash 与每个 span 关联。对于 500 mixed 的长 cursor 和锁采样，应观察锁拥有者、等待者和语句阶段，而不是直接提高连接数。

`Kernel._accept_transaction` 仍对已选择事件设定 **2000** 上限，并从 genesis 加选择事件完整重放；查询默认扫描上限 10000。这是长篇、多卷持续增长的真实边界。单纯增加 API 进程、Redis、MQ 或读副本不会消除该算法成本。需要研究经过验证的重放检查点、不可变投影增量或局部材料读取，并证明规则版本、Retcon、效果替换、时间区间和历史修订与完整重放完全一致。该研究属于当前系统内部的重大工程工作，不能通过直接去掉保护上限交付。

### 3.3 保留严格接受与有限依赖守卫

同一权威分支的接受顺序、版本和回执由现有原子事务确定。分支锁与依赖守卫不是可以因为排队而随意取消的开销。先把不依赖可变状态的验证移至可证明安全的阶段，再在事务内校验必须保持的新鲜依赖；是否能进一步缩小锁粒度，应由具体冲突与重放等价证明决定。本轮没有新增全局世界快照缓存、拆分数据库、放松接受权限或改变效果身份。

对于准备全部候选再集中接受的 1000 mixed 未来实验，应比较有界在途的准备/接受流水，但保持同任务数、同效果数量、同请求幂等和同公平性要求。默认 300 秒证书有效期继续生效；未实测的调度方案不能宣称已解决证书老化或高并发写入。

## 4. 跨卷、灾难恢复与真实模型约束

跨卷服务继续引用同一世界历史和文本版本。新增基础设施不得构建第二套“卷历史真相”，也不能静默替换已经发布的连载前缀。图索引或记忆缓存失效时，应允许从权威版本重新生成，且旧版本的独立审计仍可完成。

P4-02 的隔离物理恢复确实执行了 base backup、WAL 目标恢复、逐表和对象摘要核验、回执/代际与 UNKNOWN 调用检查；首次夹具为 37 表、19 对象、2 个恢复世界事件。该结果及测量边界见 [恢复与升级验收](P4_02_恢复与升级验收.md)。它没有验证远程对象存储、跨地域灾难、任意在线 WAL 点与对象清单的一致性协议或大库生产 RPO/RTO。仅为迁入新对象服务而增加复制流程，不能自动提升恢复结论。

文学记忆的 660 条受控观测证明的是该评测集内的来源打包与完整性；例如累计历史材料让五个审稿案例取得更多原文来源，不等于审稿更准确或作品更好。相关结果见 [P3-03 受控评测](P3_03_受控记忆评测与历史成果恢复.md)。没有授权真实模型调用和独立全文评价，不能用向量服务部署或缓存命中率填补后两项验收。

本轮真实模型调用为 0，没有商业 Agent Host 实测。供应商限流、token 预算、服务费用、流式回包中断和未知外部副作用都不能由当前 HTTP/数据库负载数据推算。后续真实模型实验必须与工程吞吐分别记账。

## 5. 下一轮可否改变架构的判定门槛

1. 固定场景与规模，保留原 200 Agent 正常/热点目标，并补充 500/1000 混合写入与明确的新长篇数据档位。不能通过减少世界事件、减少主体或省略授权校验获得表面提升。
2. 在能供应目标实际到达率的独立客户端环境重复原实验，同时记录服务/客户端 CPU、当前 RSS 与峰值、SQL 与载荷字节、锁链、队列、每个逻辑操作和每个正式效果。新方案必须面对相同硬件与总资源预算。
3. 对提出的新组件做单变量对照：除可明确解释的部署变化外，保持相同世界切面、权限、规则、任务代际、来源和原始命令。收益应体现在有效业务吞吐、首试成功、尾延迟或可恢复性，而不是只减少一个局部计数。
4. 所有候选都必须通过宏微不重复、撤权、Retcon、并行接受、旧回执恢复、版本升级和坏对象/坏索引恢复测试。长稳需包含持续世界增长、异步积压和故障后的恢复，600 秒读探针不能替代这些场景。
5. 在收益和运维代价都可核验后再提出正式引入决策；在此之前保持 PostgreSQL 权威历史与当前模块边界。

当前没有证据要求立即迁往另一类数据库或增加独立基础设施。当前有充分证据要求继续解决应用 CPU、重复材料读取/验证、写入锁长尾、开放到达供给及完整重放上限。对应性能与生产验收状态应继续如实保留，不因完成了架构评估文档而改为全通过。

# P5.9 MCP 并发、工作流与资源调度实验

**建议保留两个独立可选项**。静态角色反复读取本人任务与上下文时可启用 `--compact-role-reads`。在同一 Workshop 安装中批量读取委托回执时可启用 `aw-reconcile --reuse-session`。两个选项默认关闭。[设计与完整时序](../../../docs/design/MCP_CONCURRENCY_AND_SCHEDULING.md) · [独立补丁及最新 main 移植验证](INTEGRATION.md) · [代码来源及原始证据清单](source-map.json)

## 三类容量

| 验证对象 | 实际业务结果 | 解释边界 |
|---|---|---|
| stdio 连接 | 独立 runner 同时保留 200 个 stdio 子进程、200 个 SDK 会话、200 份授权。Host 每次激活最多 8 个绑定，最终一轮任务/知识/上下文/发现全量扫描 800/800。 | 单槽、2 秒 idle，独占内存 USS 合计约 11.61 GiB。另一独立 runner 的默认配置在第 100 个初始化时遇到 PG 连接数限制，实际复核 99 个活绑定。 |
| stdio 同时请求 | 同一组 200 个活会话的绑定池全部回收后，同时发送一次本人状态读取，99 正确、101 个 SERVICE_UNAVAILABLE。 | PostgreSQL 的 max_connections 为 100。日志确认此时发生连接拒绝。分波扫描与冷池同时恢复各有自己的时间边界。[两份原始 CI 附件](stdio/HOSTED.md) |
| 热 stdio 正确调用率 | 十绑定、二十个闭环槽，任务/上下文读从每次 35 条 SQL 降至 27 条。两对有效吞吐 +23.2% / +19.2%，P95/P99 均符合 10% 容差。 | 四臂 PG 峰值同为 20，服务线程与 SQL 累计工作量下降。四绑定持续复验 32,000/32,000 正确，两对均通过；两绑定 12/s 开环有一组尾延迟超限。[持续复验](stdio/SUSTAINED.md)[逐请求 A/B/B/A](stdio/RESULTS.md) |
| Agent 工作流 | 500、1,000、2,000 份独立角色授权的真实持久任务，分别获得 490、980、1,960 份逐项核验结果，MCP 唤醒依赖等待 99、199、399 次。 | 每档另有 1% 发送前取消、1% 发送后 UNKNOWN。两项目控制会话、两个模型执行槽、商业模型调用 0。排空为 3.566、3.275、3.392 份正确结果/s。创建、领取、执行在内核中运行，状态和恢复经 MCP。[各任务原件](workflow/README.md) |
| 远程 MCP 突发 | 两个作品，200/500/1,000 个已初始化、独立授权的 SDK 客户端同时访问一个两槽副本，正确 2/4/5 条。入口鉴权 429 分别为 186/482/976 条。 | 在该配置中，主要拒绝发生在鉴权入口。模型调用为零，不能单凭连接池使用率把损耗归因于 PG。Host 限制在途后的完成率、等待代价及全程期限见[突发复验](remote/RESULTS.md)。 |

原 HTTP timeline 的客户端、鉴权、接入和业务路径与 stdio 不相同；重复授权、查询、审计和调度是两者都有的成本。原 HTTP AT-30 仍未取得符合原条件的 950 次/秒，本实验不修改其门槛。[历史 Issue #13](https://github.com/SKYdayDUCK/NovelFactory/issues/13)

## 候选与选择

| 候选 | 实测与决定 |
|---|---|
| A 原始 | 官方 SDK 1.29.0、PG17、真实握手与角色授权，含静态发现、本人任务、角色 BELIEF 素材、固定 WorldRef 和 ContextBundle。 |
| B 重新使用连接 | 同一安装的批量回执查询，按完整墙钟计，正确吞吐是每次冷启动的 4.34× / 3.58×。32 个真实委托创建分属两个 A/B/B/A，四对吞吐均为基线的 2.23–2.89×；一对 P95/P99 比为 1.100568，超过上限 1.10。仅按已通过的负载采用。单纯把热 stdio 绑定降至一槽会拒绝更多业务。 |
| C 批处理 | 静态读消除同次调用的重复工作有条件通过。成组发现的吞吐和尾延迟不稳定。另一候选只在同一绑定内合并任务/上下文，640/640 正确且审计逐项匹配；每臂只省 18 条 SQL，闭环吞吐分别下降 7.9% 和 13.2%。[跨请求批处理原型和反例](stdio/TASK_BATCH_RESULTS.md) |
| D 分级、公平、弹性 | Supervisor/PG 实路承担三档工作流。九种候选加基线的 62,208 条离散事件记录比较 WFQ、DRR、老化、保留位置和弹性槽。热点 FIFO→DRR 按期续租 18/57→40/57，模拟 P99 240→263 tick；组合突发出现重新入队失败。保留原持久状态机，未采纳生产级自适应扩容。[回放与种子](scheduling/README.md) |
| E 持久操作快速返回 | 真实 Workshop 委托先返回 operation ID，经 NF 业务提交得到 task ID 和幂等回执，再查询状态。验证跨服务故障对账、结果丢失和 UNKNOWN，不依赖未协商的协议 Tasks。 |
| F 入口负载均衡 | 真 SDK/PG/TCP 回环，960 次调用，单副本双槽与双副本单槽、RR、最少在途和二选一均按序复测。最少在途两次各完成 79/80，但排空变慢，正确/s 低于 RR。三个双向对照均未通过。[逐行数据及资源差异](remote/RESULTS.md) |
| G 混合 | B+C 在双绑定四种工具下每臂 64/64 正确，未取得额外的吞吐收益。短空闲回收＋有限活动集实测可保有 200 个活 stdio 绑定，全部冷池同时读取仍有 101 次失败。 |

## 数据库、故障与复现

- **数据库。** 验证历史 14 次运行、44 个原始 ZIP 的摘要、长度和 CRC。新 DB 混合负载中微批 SQL 从 4,600 降至 1,400；两对正确吞吐 228.70→747.02、232.86→785.02 次/秒。真实 HTTP 详情 GET 虽省 40% SQL，本机逆序 P99 +25.88%，未再过门槛。[独立重算](db-review/AUDIT.md)
- **授权和恢复。** 已测试跨作品错绑、撤权争锁、动态 witness 刷新期间撤权、SDK 热缓存、客户端取消、已提交未回包杀进程、幂等冲突、Redis 丢失/重建、模型 UNKNOWN 的预算保留。丢失强写回包后重连，只获得一个候选对象和同一回执。[权限审核](scheduling/AUTHORITY.md) · [故障结果](stdio/reconnect-group.json)
- **等待。** 真实网关的 fixture Provider 阻塞约 3 秒时，6 次短 MCP 查询在 25.06–67.68 ms 内完成，续租 10.71 ms；网关池 checkout 为 0，仍占一个调度槽并预留预算。独立授权操作员通过脚本作出审核决定，重连恢复唤醒数为 0、1、0。另验作者待批计数为 1，未做真人点击批准稿件的试验。[等待与审核](waits/README.md)
- **环境。** Linux、Python 3.12.14、MCP 1.29.0、PG 17.11；故障测试 Redis 8.0.2。PG 集群、数据库、凭证、端口、对象目录与适配器均属各试验，宿主物理资源有共享。原生过程阶梯与另一大负载曾交叠，进程退出 137；工作流和逻辑身份突发均用新库复跑。独立 Windows 原生 PG17 运行 26 项通过，Windows 大规模吞吐未测。[Windows CI](https://github.com/SKYdayDUCK/NovelFactory/actions/runs/43357148016)
- **复现。** 使用仓库锁定依赖，负载机另装 psutil 7.2.2。各驱动与数据库实例在一个可控环境中启动，取 SQLAlchemy cursor 和资源采样，采样连接或锁峰值是下界。[stdio 参数和门槛](stdio/PROTOCOL.md) · [远程协议与命令](remote/RESULTS.md) · [工作流命令](workflow/README.md) · [协议、论文及开源实现](scheduling/SOURCES.md)

# 200 个独立 stdio 绑定的独立 runner 复验

每个身份均有独立测试凭证、数据库任务、世界版本、OS 进程和已经 initialize 的 SDK 客户端。两台独占 GitHub Ubuntu runner 内存约 15.61 GiB，PostgreSQL 17.11 `max_connections=100`，驱动及观察同样占用连接。不使用连接代理或远程 HTTP。在两台 runner 上分别运行，以下绝对能力边界不能用来计算因果吞吐增幅。

| 模式与时段 | 同时复核的存活 PID/会话 | 对已初始化身份的业务复核 | PostgreSQL 与内存 |
|---|---:|---|---|
| 默认 2 槽/30 秒 idle；原生阶梯 | 99 | 最后一轮四种工具共 396/396 正确，第 100 个身份初始化失败 | 该时刻服务端日志出现 `FATAL: sorry, too many clients already`；全部进程独占内存 USS 合计 5.73 GiB。|
| 1 槽/2 秒 idle；Host 每次最多激活 8 个绑定，波次间空闲 2.25 秒 | 200 | 200 档四种工具 800/800；最终再扫描 800/800，所有 PID 和会话继续保留 | 全部 200 个 stdio 的 USS 合计 11.61 GiB、PSS 合计 11.63 GiB；在另一次突发前，该组在 PG 的池连接采样为 0。|
| 同一组 200 个活会话，冷池同时读取本人任务 | 200 | 200 个请求全部发出，99 正确、101 个 SERVICE_UNAVAILABLE；前后 200 个 PID 均存活 | SDK 交给发送端的时间跨度为 5.15 ms，排空 1.486 秒。数据库原始日志在这次 runner 记录到 102 行连接过多的信息；包含健康检查等，日志行与失败请求不能逐行对号。|

保留空闲会话与承载同时活跃请求各自消耗不同资源。在该机器和这组 fixture 上，进程保留的代价在十余 GiB 内存，冷池同时恢复的代价表现为数据库连接争抢。分波策略调整了池预算、回收时间和实际在途宽度；未做三因素全析因。800 个分波成功不能换算成 200 个同时执行。两次均使用角色查询，不含模型。

本地另外两次实验保留了不同的资源观测：仪表化受限阶梯在 54 个绑定同时复核 216/216；原生阶梯留下 130 个握手记录后客户端退出 137，缺少该档同时复核。独立 runner 提供了额外的 200 活会话证据。这些数字不覆盖 500/1,000 个同时存活的 stdio 子进程。[本地原始与方法](RESULTS.md)

# 独立角色 stdio 实测

一次绑定对应一个角色凭证、一个真实 PostgreSQL 任务、一个冻结的世界版本、一个 OS 子进程和一个 SDK 会话。使用 Python 3.12、MCP SDK 1.29.0、PostgreSQL 17.11，Linux CPU 亲和性 0–5，PG 每个隔离集群设 max_connections=128。任务/上下文每次同该角色数据库中的预置对象比较，知识查询检查精确作品版本、主体、谓词、BELIEF、UNKNOWN 及空数据/证据。发现必须精确返回四种允许工具。所有读矩阵逐轮核验世界 HEAD 和零 Provider Attempt。

逐请求复核五个矩阵共 3,584 个计划项，均有对应的实际 SDK 发出和服务端分派记录。子进程退出后以绑定索引加 JSON-RPC 请求 ID 联接，业务状态、SQL 合计及每作品成功数均可从原始记录重算。

A 使用默认参数。B 为 `--compact-role-reads`。两种工具在十绑定每阶段核验 240/240 次，两绑定为 48/48。每个成功业务调用跨 SQLAlchemy cursor 的实测 SQL 执行由 35 降为 27（−22.86%）。10 绑定闭环两对有效吞吐增幅 +23.2%、+19.2%；两对 P95 分别 −28.3%、+9.1%，后者接近预注册上限 +10%。两绑定低到达率未通过；单阶段仅 48 条，不能用一个低负载阶段保证普遍的 P99。

## 层级归因

10 绑定、20 个闭环槽，所有四臂从 SDK 发出 240 个，被服务端分派 240 个，业务均成功。以各查询、线程时间相加时可超过墙钟，因为同一阶段有并发。SQL 时长包含客户端与 PG 往返，连接池 checkout 包含取连接、连接验证及可能的等待，不能当作精确排队时间。没有 pgbouncer 或代理。0.25 秒采样捕获四臂 PG 连接峰值均为 20，未采到 Lock 等待；短锁可能漏采。

## 连接容量

4 GiB 子进程合计 RSS、1 GiB 宿主内存保留的预注册实验。2、10、50 档分别完成 8/8、40/40、200/200 次混合操作，同一进程组逐步增加身份。50 档的一轮四工具扫描 80.52 正确/s，P95 860ms，主要用于同时存活验证。第 54 个绑定验证后合计 RSS 4,269,801,472 字节，下一进程按 79,355,904 字节估算将越过预算，当时宿主仍有 5,301,297,152 字节可用。54 个真实进程和 54 会话均在场，再次完成 216/216 条，P99 1,069ms。该保护阈值没有触发系统内存耗尽。冷启动/握手逐进程中位 1.27s，最短 0.85s，最长 2.37s，包含实验仪表加载。

另做不加仪表、使用原生生产命令的主机余量实验，见 STOCK_PROTOCOL.md 与 stock-host-200.json.gz。该补测记录 USS/PSS 以避免将重复共享页当作专属内存。使用独立 PostgreSQL 与端口，但同机另有独立 200-client SDK 实验，共享物理内存。在 130 个不同 PID 分别完成 SDK 握手和授权发现并写入原始记录后，负载客户端被 KILL，launcher 退出 137。第 130 个进程启动前的可用内存为 1,197,723,648 字节，初始化时测得的 130 个进程 USS 逐次相加为 7,967,551,488 字节（各自启动时采样，不是同一时刻的总量）。200 进程档未达。没有内核 OOM victim 日志，无法定位哪一项分配触发了 KILL。检查点每身份记录了 PID 与工具发现成功，缺少 130 个进程同刻存活的完整再核对，最后全部会话同时完成四工具扫描的 stock 档为 50，共 200/200 次。退出清理后独立 PG 完成 checkpoint 并关闭，宿主释放内存。四臂性能实验在此补测之前已经结束。原样保留部分检查点 stock-host-200.json.gz、stock-launcher.txt、stock-postgres.txt 和 stock-exit.json。

## 故障与边界

在真实 SDK 的 _send_response 之前将服务子进程退出，保证候选对象/回执已提交、客户端仍未收到答案。新绑定进程重发相同键后取得持久同一回执，异内容记 IDEMPOTENCY_MISMATCH。独立查询只有一条候选和一条回执，正式世界 HEAD 保持原值。撤权提交后四个同时发现均为空，后续上下文访问返回 VIEW_DENIED，关闭后该绑定无 idle-in-transaction 连接。

数据库锁注入让发现停在真实授予表上，PG 报告等待后向 MCP 发取消指定 ID 通知。两调用测试中被取消 ID 立即得到协议错误，另一调用正确，之后下一次紧凑读取正确。四成员单批机制试验注入 dispatch 前屏障以控制 4 个真实客户端请求进入同一批次，取消一个，剩余三个全部正确且未出现跨角色内容。未插入屏障的早期试验中，三个剩余请求未全部成功；缺少该轮分组边界，无法区分普通限流和取消影响。失败保存在 discovery-cancel-first.txt。早期刷写探针包装器未代理 SDK 异步 context manager，导致初始化后异常结束，mixed-A-first.json.gz 不含有效性能样本。修复仪表后重新运行所有正式矩阵。

## 复现

在实验 checkout 的隔离环境中安装 pyproject/锁定依赖及 `psutil`，将 NF_DATABASE_URL 指向专属 PG17。每条矩阵命令生成新的作品、任务、绑定和临时对象目录。每个矩阵仅在独占数据库上执行，对照的四臂共用同一组角色。数据库和临时凭据不会写入结果。Linux 若需复制资源配置可对客户端、派生服务器和数据库均设置 CPU 亲和性 0–5。

```sh
python -m alembic upgrade head
python benchmarks/p59_mcp_stdio.py reads-2.json.gz --suite reads --bindings 2 --arms ABBA
python benchmarks/p59_mcp_stdio.py reads-10.json.gz --suite reads --bindings 10 --arms ABBA
python benchmarks/p59_mcp_stdio.py pools.json.gz --suite reads --bindings 2 --arms ASSA
python benchmarks/p59_mcp_stdio.py discovery.json.gz --suite discovery --bindings 2 --arms ACCA
python benchmarks/p59_mcp_stdio.py mixed.json.gz --suite mixed --bindings 2 --arms ABCG
python benchmarks/p59_mcp_stdio.py staircase.json.gz --suite connections --rss-budget 4096
python benchmarks/p59_mcp_stock_capacity.py stock-host.json.gz
python benchmarks/p59_mcp_binding_recovery.py recovery.json
```

记录中的 `tracked_product_diff_sha256` 为 git diff 相对当时 HEAD 的摘要，`product_tree_sha256` 覆盖所有受测 src Python 的相对路径与内容摘要。各臂跨文档/其他实验提交时该产品摘要保持一致。逐文件从 Git 提交 `2d3fad6d502a262d051669223e352ff385717b18` 重新取出 src Python 内容并按相同规则散列，实测完整产品摘要 `16f8e313cd3a15c331afb1c824b2ff86b86dc4b2a7eb10d885591d14df5b6843` 与 Git 源码吻合。完整采样为 `*.json.gz` 中的 `trials[].phases[].rows` 和 `resources`。客户端和子进程使用同机单调纳秒时钟。每条记录的 due、call、send、end 分别为计划、开始调用、SDK 将消息交给写流和结果对账结束；server.receive、workers、server.reply 标记 SDK 分派、实际工作线程起止及响应处理结束。checkout 为含验证的取连接时间；sql_ns 仅为 SQLAlchemy 游标执行，未包含事务提交或底层协议的每个往返。每阶段客户端最大在途和拒绝表可从 rows 重建。在极短阶段 CPU/锁样本可能不足以看到峰值。stock-host-200.json.gz 使用未插桩服务，没有服务端游标和 worker 字段。

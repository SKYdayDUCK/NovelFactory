# 远程 MCP 回环原型和突发在途请求

实验使用真实 TCP、Streamable HTTP、SDK 和实时 PG 授权。每次 HTTP 请求按 Bearer 查询当前 grant，工具内部再次验证角色、任务、版本和知识切面。服务端启动时获取两个固定 principal 的绑定，每个 principal 只允许对应一个 task binding。原型不作为托管多租户服务。在 SDK 2025-11-25 的 stateless 模式，同一初始化过的客户端使用可复用 HTTP 连接，没有服务端 MCP Session ID。主机按实际已发送未回包数选择副本，副本之间没有共享活动事务。

## 副本和路由

80 个闭环读/阶段，两个角色共四条客户端工作流。对照总业务槽、总鉴权工作线程和总 PG 池预算均为 2。鉴权候队上限是每副本 4，单副本总数 4、双副本总数 8；拆分副本也改变这个轻量候队预算。每一对比例按候选/对照重算，尾延迟包括有效回包与业务拒绝。在这三组 A/B/B/A 中，各阶段 80 次请求均有有效结果或明确背压。

| 比较 | 两对正确吞吐比 | 两对 P95 比 | 两对 P99 比 | 判定 |
|---|---|---|---|---|
| 单副本双槽 → 双副本单槽 RR | 1.091 / 1.155 | 0.958 / 1.071 | 0.758 / 1.460 | 第一对吞吐不足 10%，第二对 P99 超限 |
| 双副本 RR → 最少在途 | 0.923 / 0.893 | 1.554 / 1.091 | 2.224 / 1.395 | 两对吞吐下降 |
| 双副本 RR → 随机二选一 | 0.888 / 0.878 | 1.539 / 1.282 | 1.951 / 1.300 | 两对吞吐下降 |

最少在途两次各完成 79/80，RR 对照为 69/80、67/80。较多请求走完整业务路径延长了整个固定请求数阶段的排空时间。按正确结果/墙钟，候选分别只有 17.65、19.55 次/秒，RR 为 19.11、21.88。二副本时二选一和最少在途在非平局时选到同一副本，平局决策及实际时序仍不同。四份工作、两个业务槽和短阶段是该比较的适用范围。[原始 960 条](replicas.json.gz) · [预登记和第一次失败](PROTOCOL.md)

## 多角色同步突发

每个身份都有自己的 ClientSession、Bearer、在数据库中核验过的完整任务对象；两个作品共享同一回环副本。每个身份均完成握手和工具发现。原始突发矩阵只断言合法工具数量为四；普通 stdio 与远程路由矩阵另行核验精确名称，归档后的突发驱动也已改为断言四个名称。所有成功数据读均逐项比较授权角色的完整任务对象。随后在一个 Python 客户端事件循环内释放屏障，同时请求一次本人状态。该服务副本只有两个 PG/业务槽，最多四个在途鉴权。每格在新库运行一次。计划时间取设置屏障前的首个资源采样起点，比真正释放早约 5–7 ms。该矩阵拥有客户端、HTTP 状态和 PG 采样，未逐条采集服务端分派、worker 占用或每条 SQL。SDK HTTP 请求钩子表示交给 HTTPX 的时刻；抓到 429 是服务器明确拒绝，其余没有 HTTP 响应头的 ExceptionGroup 不能据此归给业务或数据库。

| 真实客户端身份 | 正确 | HTTP 429 | MCP BACKPRESSURE | 其他传输异常 | 两作品正确数 | 首个计划到最后结果 s | 采样 PG 峰值 |
|---:|---:|---:|---:|---:|---|---:|---:|
| 200 | 2 | 186 | 4 | 8 | 1 / 1 | 0.631 | 2 |
| 500 | 4 | 482 | 6 | 8 | 2 / 2 | 2.488 | 2 |
| 1,000 | 5 | 976 | 7 | 12 | 3 / 2 | 4.848 | 2 |

在 1,000 身份这次突发中，单进程客户端用于发送、处理错误和回收连接的 CPU 增量为 4.73 秒，最后一个 SDK 调用在屏障后约 374 ms 才开始。976 次 429 的位置由本原型入口直接确定；业务服务另拒绝 7 次。在此配置和原型中，入口鉴权准入是已观测的主要拒绝位置，客户端 CPU 和排空也是墙钟的一部分。多数请求根本没有进入模型调度。不能从这里判定 PostgreSQL 最大可服务 QPS，也不能把这个结果套到 stdio 或生产远程集群。多进程发生器、更多授权槽和更高业务/DB 预算尚未保持总资源代价做独立对照。

初次交叉运行占用相同宿主内存，200 身份进程被杀。保留[失败记录](burst-overlap-failure.txt)，重新隔离时序后所有档位完整记录。首个远程双副本原型还触发过 HTTP 429 使 SDK 后台任务组终止，保留[原始栈](first-429.log.gz)。这些实验共同指出，在远程入口用 HTTP 错误表达过载和在 MCP call result 返回可识别的 BACKPRESSURE，客户端行为有实质差异。[200](burst-200.json.gz) · [500](burst-500.json.gz) · [1,000](burst-1000.json.gz)

复现时使用项目锁定环境，加装仅限负载机的 psutil 7.2.2。用独占的 PostgreSQL 17 及对象临时目录，以下驱动在每次运行时自行创建并迁移试验库。

```sh
python scripts/with_postgres.py -- python -m benchmarks.p59_mcp_remote --output /tmp/replicas.json.gz
python scripts/with_postgres.py -- python -m benchmarks.p59_mcp_fanin --population 1000 --output /tmp/burst-1000.json.gz
```

## 同一批请求在 Host 限制两项在途

全部客户端先初始化，屏障释放后，每个 SDK 工具调用须先获得 Host 的两个槽之一，调用结束立即归还。服务端仍是同样的两个业务槽，使用实时身份授权与角色校验。每个身份只提交一次。预注册总等待人口有上界，不允许无限新请求排入。下面的 P99 和排空含 Host 等待与客户端排程，以计划参考时间为起点。

| 客户端 | 直接突发正确 | Host 两槽正确 | 两作品正确 | 正确/排空秒 | 排空 s | 全程 P95/P99 s | 计划起 30 秒内正确 |
|---:|---:|---:|---|---:|---:|---|---:|
| 200 | 2 | 200 | 100 / 100 | 21.34 | 9.37 | 8.86 / 9.31 | 200 |
| 500 | 4 | 500 | 250 / 250 | 18.16 | 27.54 | 26.50 / 27.33 | 500 |
| 1,000 | 5 | 1,000 | 500 / 500 | 28.36 | 35.26 | 33.38 / 34.88 | 860 |

客户端放行更多请求会提高入口拒绝数，按原始到达计的低 P99 包含大量很快就收到拒绝的客户端。Host 两槽提高了正确完成率，也把等待移到 Host。1,000 个身份中只有 860 个在计划起 30 秒内正确完成。SDK 的单次 30 秒 timeout 在获取 Host 槽后才开始；如果产品要求该期限覆盖排队，这次试验有 140 项逾期。各规模只做一次前后对照，不能把吞吐差异外推为所有业务可采用的 2 槽最优配置。

原始三档与 window2-200/500 使用的驱动在文件写入时记录工作树哈希。运行期间还有独立 Git 提交，相关 HEAD 可为完成时的值；通过阶段间相同的服务代码、驱动版本和逐行结果核查。最后一版改为驱动启动时取哈希、并断言四个工具的精确集合，适用于后续复现。比较依据是相同的任务和公开业务契约，未重用身份或回包。[200](window2-200.json.gz) · [500](window2-500.json.gz) · [1,000](window2-1000.json.gz)

```sh
python scripts/with_postgres.py -- python -m benchmarks.p59_mcp_fanin --population 1000 --host-window 2 --output /tmp/window2-1000.json.gz
```

# Distinct-identity admission population

Register before timed trials. Freeze the driver and service source in Git and execute a detached checkout. One Linux PG17 cluster, one initialized Uvicorn server on loopback TCP, one combined client/API Python process, two seeded works, four physical application DB connections (zero overflow), two authentication and two execution slots. No model worker. Include a 20-identity smoke run before the 5,000-identity run.

The 5,000 positive commands have 5,000 distinct authorized principal IDs, grant IDs, credential hashes and task IDs. Assign exactly 2,500 to each work and 2,500 to each submit protocol, interleaved by index so both protocols represent both works. Freeze an idempotency key and complete task specification before release. Each MCP identity initializes its own authenticated Python SDK session. Each REST identity has a private HTTP client. Maintain at most 20 outstanding client identity lifecycles (each limited to 2 TCP connections), including setup and teardown. At release, the entire preassigned population becomes eligible once. Start the next identity as soon as a lane is free. Retain one row for every offered identity including failed initialization. No retries. This is bounded admission of a simultaneous logical backlog, not a 5,000-live-socket trial.

Time from release to last positive reply and to full SDK/client teardown, and separately time each identity's initialized business call and release-to-reply delay. Exclude world/grant provisioning and post-drain verification from throughput. Report client/API CPU and peak RSS, PG backend CPU and sampled RSS, SQL and pool peaks, observed established TCP connections, app admission/queue peaks, initialized SDK sessions, admitted/denied counts by work and transport and any missing responses. Keep any open-ended latency result as measured; no preregistered latency or throughput target is implied for this identity-cardinality drill.

Acceptance requires 5,000 correctly bound durable acknowledgements, a matching READY task and durable admission for every offered (task, principal, grant, work, branch), one matching creation outbox entry per task, unchanged branch heads and zero provider calls. Negative controls outside the positive denominator: exact cross-work read denials over each transport and retryable over-capacity submit denials over each transport, with no additional tasks, admissions or commands. Set global and resource limits to population, work limit to half and principal limit to one. Residual application waiters, checked-out connections, and unexpected errors after draining must be zero. Pool and client operation concurrency must respect their caps. Compare the prior 5,000-task / 20-identity experiment descriptively only; dedicated SDK handshakes and identity turnover change the measured workload.

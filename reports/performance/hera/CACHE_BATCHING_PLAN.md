# In-flight task status coalescing experiment

Freeze before implementation. Compare the same fenced Task status reader (A) against that reader with scoped in-flight coalescing (B). Use one pool of eight connections, zero overflow, two authentication and six operation slots, at most six active operations per principal, a joining window bounded at 1 ms, at most 64 collecting groups and six callers per group. A group closes before its live PostgreSQL read begins. Responses are never retained after the shared operation. The service must authenticate every network request and dispatch each MCP call through its existing audited binding.

Real TCP REST/SDK MCP mix 50/50, six concurrent clients, six rounds per arm, with a per-round start barrier. Compare A/B/B/A with (1) the same authorized task and grant, and (2) distinct tasks and grants. Collect each request's transport, dispatch, completion time and result check, SQL counter and waiter counts. Also test one REST request at a time to expose idle-window overhead. Record the number of auth-fenced reads saved, including zero. Keep the feature off by default unless both reciprocal hot comparisons improve correct throughput, all workloads complete correctly, and P95/P99 on each candidate arm stay within 20% of the paired baseline for every workload. More identities or active writers are not implied by this small hot-read experiment.

# Supervisor and Workshop experiments

The class-cap candidate bounds MODEL and CPU_COMPUTE under the existing global/work/role leases. Authorize and hold one model while trying a second model and a derived index against the same two-slot global limit. No paid inference. On the combined PostgreSQL supervisor hold its one local model slot; enroll an expired task and require its retirement without releasing the provider. Validate existing provider UNKNOWN, process death, dependency wake, and weighted admission regressions.

Compare Workshop legacy per-event publication/receipt with immediate batches of at most 32 existing events (no fill timer), order A/B/B/A. Each run uses a newly migrated isolated schema, one publisher and one consumer, ordered groups of exactly 1, 32, 128 addressed messages with valid 1-hour TTL and identical roles, no prior history. Measure full publication and inbox reconciliation together, durable authorized receipts, Redis pending and published counts, and raw elapsed times per invocation; tail metrics are per invocation, with only two samples per arm and size. Require both reciprocal comparisons to improve at each size and no correctness regression before recommending a particular deployment. Original behavior is selectable and remains default. Reopen SQL after Redis network operations. Test explicit failure between publication and SQL marking plus replay, revocation and receiver crash.

Do not infer availability/fairness across transports, novel generation, or paid inference from these measurements.

For fast-read isolation, use 10 clients, 5 remote MCP and 5 REST, with 100 correct status responses per arm in quiet / loaded / loaded / quiet order. Fixed four-connection shared zero-overflow pool and two global model slots. Each loaded arm holds two real enrolled jobs in simulated model generation after all short database transactions have closed, with two further enrolled jobs waiting. Check pool occupancy, attempt-ledger uniqueness, pending jobs, reciprocal goodput loss and P95/P99 change. This isolates waiting on model service; sustained database-heavy processing needs a separate comparison.

For DB-heavy backlog use 100 actual world transfers enqueued for derived-index rebuild. Two index workers share the same four-connection pool as the 10 status clients. In each loaded arm, start workers after all SDK sessions initialize, immediately before the measured read start. Save the start and finish time and exact outbox ID for every index, the number completed by the last status response, and confirm the final authoritative index watermark. Run quiet / loaded / loaded / quiet; assess against the same 20% degradation limit.

Follow-up after the two-index-worker quiet/loaded gate failed. Compare 2 / 1 / 1 / 2 static CPU_COMPUTE slots, at one sequential client and ten mixed clients, 100 reads each. Both competing workers continue to request index work, using the same four DB connections. Record both read throughput/latencies and index completions per second over the read interval and through final drain. All 100 indexes must finish each run. Require higher reciprocal read throughput, no >20% tail regression, and no >20% loss of concurrent and total index throughput in both pairs; otherwise retain the two-slot setting. This tests an operator cap before adding another adaptive policy.

For the workflow progress follow-up, run four fresh two-book fixtures in quiet / loaded / loaded / quiet order. Each branch has two enrolled MODEL tasks; both remain READY in quiet arms. In loaded arms one task per branch is held at the simulated provider after SENT, with one additional eligible task per branch. The shared pool has four connections and zero overflow, with two global model slots. Use four scoped readers (one REST and one real remote SDK client per branch) and 80 measured progress operations per arm, 20 from each client, with no writes during that window. Read ordinary authoritative workflow progress with the optional projection disabled. Require each response to match its branch's complete authorized snapshot and independently count task states in SQL before and after. Verify the two SENT attempts and two READY tasks bracket each loaded interval, track peak pool use, P95/P99 service latency and correct requests/s. Drain loaded tasks once and check durable attempts. Assess each adjacent quiet/loaded pair against the previously used 20% throughput loss and tail increase gates. This is a short operational check.

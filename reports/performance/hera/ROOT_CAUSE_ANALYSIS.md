# HERA performance attribution on PostgreSQL 17.11

The earlier -6.0% / -5.2% relative throughput change is **not reproducible as a stable percentage or attributable to a single change**. The earlier two series ran in different time windows with the REST load generator and the API in one interpreter. Even main moved from 5.53–5.58 to 7.25–7.71 lifecycles/s. A real admission hotspot and a real empty-projection trigger cost are separately reproducible. The latter is too small in measured function time to explain the historical slowdown by itself. [Historical apples-to-apples operations](MAIN_REST_COMPARISON.md)

## Frozen full-path experiment

The client, Uvicorn and PostgreSQL ran in separate Linux processes. The driver migrated a **new database with the same schema source in every arm** (1478ddf for attribution). We then changed the explicitly named policy/trigger treatment. Every arm seeded two works and sixteen principals. A fresh application served sixteen first-use lifecycles and then sixty-four warm lifecycles. First-use includes cold application/DB paths and new sockets on a migrated, seeded database. Kernel page caches were not flushed. All responses and the database state were checked, including task generation, WorldRef, duplicate receipt, claim, cancellation, Outbox count, two command receipts and unchanged canonical heads. Each pool had four slots, zero overflow, two auth and two business slots. The monitoring connections are separate from the application budget. The 14 baseline arms used PG on CPUs 2–3, API on 1 and 4, and client on 0. Affinity restricts these processes but does not reserve host CPU time. The cold-start definition, startup time, affinity, PostgreSQL settings, commit and driver digest are in each file. Order was A E B X O N M M N O X B E A. All 1,120 lifecycles and 7,840 HTTP responses passed. The original early and previous-final source trees differ in HTTP/MCP binding and recovery code. Most of this REST workload does not traverse those changes. Reverting just the recovery body changes the sign of the throughput difference across repetitions. Main's two end controls also differ substantially. The driver measures PL/pgSQL inclusive time with track_functions=pl and nested SQL with pg_stat_statements.track=all. Each active arm executed 240 calls for 80 cycles. The 0026 function occupied about 30–35 ms in the two B arms across both phases, compared with over six seconds of warm load alone. With no configured counter there was no progress tuple to contend on. Comparing B with O still changes elapsed time by more than these measured function times; two observations cannot assign that entire difference to the trigger. PG measurements omit some trigger-manager/commit overhead and do not estimate every scheduling interaction.

Switching off admission in the previous product saves 256 application SQL calls per 64 warm cycles. All measured B and N arms use the same four application connections. The driver did not reproduce a hidden connection-budget change between early and final. The policy UPDATE and occupancy scan hold the singleton until the rest of the creation transaction commits. As the backlog grows, waiting on that owner compounds the aggregate scan. In the final 5,000-item controlled component experiment, the old UPDATE averaged 66.22 ms, the scan 15.64 ms, and the old task INSERT 3.81 ms. Exact count mode moved enforcement into the same transaction as the task insert. That INSERT averaged 30.38 ms **including waiting**, and the shared policy SELECT averaged 2.06 ms. Task creation, command receipt, Outbox and release remain real costs. [Stage samples, per-create records, WAL and locks](CAPACITY_COUNTERS.md)

## Scope and reconstruction

The warm restored controls approximately bracket 9.77–13.19 full lifecycles/s; 1478ddf lies inside that range. Direct costs are identified. Recovering a counterfactual decomposition of two historical executions, or assigning the residual to OS scheduling alone, exceeds these data. The index-loaded fast path, the live single-status MCP path, and deep admission use different denominators. [MCP single-status timing](MCP_STATUS_AUTH.md) · [Projection write contention](PROJECTION_CONTENTION.md) · [Full combination and selection decisions](OPTIMIZATION_ABLATIONS.md)

Each .json.gz includes the post-run database oracle, per-request intervals, cycles, PostgreSQL snapshots, WAL and blocking PID samples. Each accompanying .trace.gz contains the SQL shapes, per-cursor timings, connection identities, transaction begin/precommit intervals and ingress/auth/operation waits. Transaction precommit timing excludes the final COMMIT round trip. PostgreSQL query text comes from parameterized queries. Resource samples include backend CPU ticks and RSS pages. The pilot failed before recording its first PostgreSQL 17 statistics snapshot because the driver used an older column name. Its error and partial application trace are preserved. The baseline shell driver emitted a syntax diagnostic after writing the last result while its control script was being edited. All 14 finalized JSON files and corresponding traces were decoded and their 14 database oracles checked. The later ablation/final sequences use distinct scripts.

## New frozen comparisons

The audited role path repeated its complete authority evaluation and looked up the same grant-owned task again for audit scope. On eight independent live roles these calls accounted for thirteen avoidable app SQL statements per valid read across the combined changes. The timer includes server scheduling and PG round trips.

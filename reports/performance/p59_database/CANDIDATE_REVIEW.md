## 候选处置依据

|候选|首轮评审|限制和证据|
|---|---|---|
|queues|不采纳单独分队|只读总 SQL 与基线相同；正序只读 238 对 290 次/s，P99 705 对 379ms。混合时续约有利，部分反序试验整体 P95 却上升。|
|sql|保留低复杂度入口候选|只读业务与真实 GET 都有重复收益。混合正序出现吞吐和尾延迟退化，需按相同协议复验。|
|micro|保留内部高并发状态读候选|混合两次每千项 1,400 SQL，整体 P95 最低。首轮未有正常 HTTP 入口的专属对照。|
|micro_queues|不作为默认调度|两轮混合层吞吐最高，也拉长了续约尾延迟，相比 micro 的续约 P95 从 82/65 增至 255/213ms。|
|hybrid|保留机制证据|纯业务层峰值最高，但真实 GET 达不到双向预登记门槛。分队的续约尾时延高于 FIFO micro。|
|baseline|继续作为完整业务默认与历史对照|默认无协调器。没有一项首轮候选对全部目标、全部入口达到双向门槛。|

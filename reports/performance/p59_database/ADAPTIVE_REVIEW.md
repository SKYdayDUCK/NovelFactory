# 自适应 FIFO 与固定微批的独立对照

在 [43292818072](https://github.com/SKYdayDUCK/NovelFactory/actions/runs/43292818072) 中，源码 `d9a0df493918b351542e0a0d978bf3474b099e85` 使用独立 PG17 Runner 顺序执行 16 轮。四个并发度各采取固定、适应、适应、固定顺序。每轮 50 个身份、两部作品、900 次状态读与 100 次独立强事务续约，池与执行槽上限 4，队列上限 128，双模式的 SQL 实现相同。全部 16,000 项业务结果与持久租约核验一致。[校验清单](raw/candidates/adaptive-manifest.json) · [逐轮指标及实际批大小直方图](raw/candidates/adaptive.csv) · [原始包](raw/actions/43292818072/13978461022.zip)

## 调度与关闭方式

默认实现和原六种模式不启用该算法。选择 `--mode adaptive` 或 `--profile adaptive` 才启用独立实验类。无排队、无正在收集/执行的工作时，状态读直接交原 Kernel.get_task，使用同一个有界数据库线程池。繁忙时按 FIFO 收取连续兼容读，遇续约立即结束读批。对已积累但尚未满的读批，仅在可以等待时计算目标为下一档二次幂，上界为 32。允许额外等待的预算取配置的 2 ms 与上一批状态读服务耗时 EWMA 的 1/4 的较小值，扣除最老请求已等待时间，且以最早超时为上限。EWMA 新样本权重为 1/4。直通与批次共享同一连接预算。

并发 1 的两次适应运行各 900 个状态读真实直通；其余 100 个续约各自执行。没有减少 SQL，吞吐与尾时延收益未在两个方向重现。并发 8 的两次运行观测到 41 和 29 次按实时延迟预算等待，批大小跨越 1 至 7，证明控制分支实际运行。此时适应方案 SQL 比固定多，吞吐下降。

并发 64 的两方向吞吐和尾时延均达到该负载数值门槛，但两种方案在每轮完成了完全相同的分组：100 个九项读批、100 个单项写、1,400 个应用 SQL，适应方案没有额外反馈等待。同期固定模式两轮自身吞吐为 758/1,211，变化较大。该组数据不能把速度差归因于选择了更好的批量大小或等待窗口。并发 128 的分组仍然相同，适应方案两方向的吞吐均未超过基线 10%。

**处置**　保留可重现的实验原型。直通语义和动态反馈均经实际验证，工作负载对照缺少可归因且可重复的综合优势。后续接入优先保留简单模式；不因64客户端一组高数值更改生产调度。

## 分层实测

每个业务层独占一个 runner，先在相同机器上运行 2 次冻结 HTTPX 纯传输对照、1 次单分片 h11，再运行 2 次四分片 h11 校准。每次使用相同字段布局、2,104 字节固定响应、同一总连接上限 256、相同 5 秒到达计划。四台主机的冻结客户端录得 207.56–253.77 次发头/s。h11 单分片为 999.50–999.76/s，四分片两次为 999.85–1,000.06/s。所有新客户端校准均在接收端看到 5,000 个请求并验证了响应全文。连接复用和协议客户端一起发生了变化；单进程对照表明达到这一档不需要四个进程。

业务测试使用 1,000 个实际授权身份，2 个生产 HTTP 进程和合计 8 个数据库连接，每个层都从一个新数据库开始。每台机器随后对自己的业务层提供 5,000 次首次请求。下表延迟从预定发送时间算到响应读完，包含失败请求和排空时间。鉴权对照保留真实请求解析、Schema、鉴权、限流与操作准入，最后一步用返回已认证 principal ID 的测试函数替代业务查询，客户端核对这个 ID。业务读的输出在独立父进程验收。

| 层级 | 校验通过 / 计划 | 429 | 发头/s | 校验通过/s | P50 / P95 / P99（毫秒） | 应用 SQL 条数 |
| --- | ---: | ---: | ---: | ---: | --- | ---: |
| 真实 HTTP 健康接口 | 5,000 / 5,000 | 0 | 999.90 | 992.30 | 41.76 / 41.84 / 42.80 | 0 |
| 真实鉴权与准入 | 2,472 / 5,000 | 2,528 | 999.87 | 481.52 | 83.19 / 656.22 / 756.21 | 2,472 |
| 真实鉴权及角色自己的任务读取 | 2,447 / 5,000 | 2,553 | 623.21 | 295.34 | 1,681.48 / 3,167.42 / 3,359.45 | 14,315 |
| 真实固定版本 timeline | 93 / 5,000 | 4,907 | 630.12 | 8.88 | 1,809.62 / 3,857.25 / 5,926.61 | 1,673 |

完整查询这一轮全部 5,000 次均到达服务端，5 秒提供窗口内客户端开始发送 3,162 次。客户端协程调度滞后 P95 为 1.57 毫秒，等待可用连接槽 P95 为 2,693.46 毫秒。鉴权队列直接拒绝 4,459 次、超时 356 次，业务队列拒绝 8 次、超时 84 次，这四项合计等于 4,907 次 429。两个 API 进程各有独立容量上限，池占用峰值之和为 8，压测收尾时归还全部连接。脱离这些队列只调整数据库批大小，无法消除已经发生在数据库访问前的拒绝。启用更快客户端时，高压业务测量暴露了更多服务端背压，不能把冻结客户端与新客户端的有效读取数视作服务代码 A/B。[分层实测与各机校准](https://github.com/SKYdayDUCK/NovelFactory/actions/runs/43289598993)

第一版工具的 `admitted_by_server` 对应已发出资源票。在完整查询这一轮，业务层发出 94 张票，其中 93 个调用进入并完成。鉴权层发出 388 张票，进入并完成 185 个；另 203 张与等待超时交错。原始 `timed_out` 已包含这类超时，不能将之再加回失败数。随后工具直接在 ASGI 接收点和准入上下文进入点计数；第二版输出反映实际进入。第一版 `environment` 中继承的 P2 默认拓扑说明以 `configuration`、`effective_service_processes` 和实际的逐进程指标为准。后续版已显式写入拓扑和校验 CPU。每个合法 200 还会按请求核对 subject、predicate 与 knowledge cut。

## 复现与错误归因

从仓库根使用锁定的 Linux Python 3.12 环境。每次使用新的输出路径。生产 API 和业务规则没有导入新负载工具。原工具的资源限制说明及定速负载的计时依据分别参见 [HTTPX](https://www.python-httpx.org/advanced/resource-limits/) 和 [wrk2 原始说明](https://github.com/giltene/wrk2)。

```bash
python -m benchmarks.client_calibration --response-bytes 2104 --repeats 2 --output /tmp/frozen-transport.json
python -m benchmarks.p59_http_shards --layer transport --workers 4 --rate 1000 --agents 1000 --rounds 5 --output /tmp/new-transport.json
NF_BENCH_DIAGNOSTICS=1 python scripts/with_postgres.py --log-dir /tmp/nf-http-db -- python -m benchmarks.p59_http_shards --layer query --workers 4 --servers 2 --connections 256 --rate 1000 --agents 1000 --rounds 5 --output /tmp/new-timeline.json
```

压测器把每个全局请求索引固定分给一个进程。排队发生在有界连接槽之前，从计划时刻计算端到端延迟。一次请求限时覆盖连接槽等候、连接建立和完整响应读取，对未发送、已开始发送、服务端接收、实际准入及有效返回分别计数。所有状态及错误保留，客户端不会自动重试。跨机比较需要独立校时；此实现使用同机多进程的单调时钟。对未通过校准的机器，工作流仅输出诊断数据。

长测冻结工具已支持原始 3,600 秒单租约和每隔 1,200 秒由当前 owner/generation 续租的变体。新的 PG17 用例给两个活跃任务设置同一短租约，在一个任务成功续租之后对两者作等量时钟偏移。两者读取同一固定世界版本，续租者取回原值，过期者读取及迟来的续租均报 `LEASE_EXPIRED`。该测试验证失败类型，在 CI 中的一小时持续观察单独计时。[真实数据库反例](../../../tests/integration/test_p59_read_soak_renewal.py) · [PG17 回执](raw/http-portable.xml)

仓库的每份 GitHub artifact 元数据包含文件 ID、源码、外层 SHA256 及 URL。下载 ZIP 至 `<archives>/<run_id>/<artifact_id>.zip` 后，以下命令逐一校验 GitHub 记录的 ZIP SHA256 及解压后的每份 JSON SHA256，重建汇总。

```bash
python -m benchmarks.p59_http_evidence --archives /path/to/archives --metadata reports/performance/p59_database/raw/http
```

## 固定版本条件传输的完整入口复验

四个样本在同一 runner 上依次运行。每轮重新建库和对象目录，使用相同的 SQL、资格、CPU 及队列仪表。两个纯传输校准分别为 1,000.03 和 999.94 次发头/s，各验证 5,000 个响应。A 使用冻结的版本读，B 在实际 PostgreSQL 行上核对快照内容摘要，再决定是否重复传输。CPU 仪表中的方法名分别为 `Kernel.revision` 和 `WitnessKernel.revision`。

| 顺序 | 实际进入业务 / 校验通过 | 429 | 校验通过/s | 计划至完成 P95 / P99 毫秒 | 连接槽等待 P95 毫秒 | SQL |
| --- | --- | ---: | ---: | --- | ---: | ---: |
| A1 | 121 / 121 | 4,879 | 13.60 | 2,659.93 / 4,443.01 | 1,456.98 | 2,180 |
| B1 | 170 / 170 | 4,830 | 15.55 | 4,111.61 / 6,064.15 | 3,217.78 | 3,667 |
| B2 | 157 / 157 | 4,843 | 15.10 | 3,825.35 / 5,248.25 | 2,709.78 | 3,215 |
| A2 | 117 / 117 | 4,883 | 13.25 | 2,624.47 / 4,191.47 | 1,202.34 | 2,183 |

四轮均收到所有 5,000 个请求；业务结果内容校验错误均为零。B 的两次有效吞吐中位数比 A 高 14.16%，同时 P95 的两轮中位数上升 50.20%，P99 上升 31.01%，均超过预先登记的 10% 尾延迟上限。B 在相同的 5 秒提供窗口内发送了 3,018 / 3,331 个请求，A 为 4,133 / 4,111 个；其余排队后发送。更长的连接槽等待和更慢的排空可直接从时序看到。根据本轮采纳标准，保留证据并拒绝把这一版本读候选集成到生产路径。四个完整查询样本均未达到 950/s 容量门槛。[同机 ABBA 作业及原始 ZIP](https://github.com/SKYdayDUCK/NovelFactory/actions/runs/43291814145/artifacts/13977741822)

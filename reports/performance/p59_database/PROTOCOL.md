# P5.9 database experiment registration

Registered before measuring candidates. Product baseline is PR 33 at 3e6b59268f1e89520230c8b70e9a26b9950a2f79. Historical main is 434840593179e6c1faa6b7aeca3d7d747644506d (PR 32 merged). Issue 13 is open and PR 4 is a separate draft. All experimental changes use one new branch and private services. A candidate is selected by an explicit switch in committed source. The default remains the frozen implementation.

* Compare the same authorized calls, expected answers, offered load and connection ceiling, in forward and reversed order. Measure individual failures, queue delay and service work. Throughput is correctly completed business operations divided by elapsed wall time. Count writes and reads separately. Do not treat an HTTP header-send event as a server receipt.
* For recommending a production change, require zero semantic differences or unexpected errors, no additional confirmed state changes, no increase in resource ceilings, at least 10% higher median goodput at saturation OR at least 25% fewer SQL executions with goodput within 5% of baseline. Allow a maximum 10% deterioration in each of P95/P99. Require repeatability in both orderings and a matching real-entrypoint check. If any condition is unmeasured, describe a candidate as limited to the tested layer.
* Use 4 workers in the candidate DB comparison, at most 4 application connections plus a separate observer, with bounded pending operations. For the historical HTTP and workflow fixtures retain original limits (including their separate observer). For controlled microbatch comparisons test sizes 1/8/16/32/64/128 and 0/1/2/5/10 ms. Reject unstable error behavior even if latency on successful responses falls.
* Keep the original 200 mixed and 1000 open-arrival gates and the one-hour fixture unchanged. Separately measure the existing renewal variant. For the new 1000/s calibration require all scheduled calls to reach the server and validate, at least 950 first-send starts/s, and report scheduling lateness, delivery in the offered interval plus drain; do not import a pure transport pass into AT-30.
* Treat 50/200/500/1000/2000 workflow identities, active execution slots, database pool occupancy and HTTP offered/sent/verified rates as separate populations. Use distinct fixture data per run. Do not run overlapping high-load comparisons on the same machine. Record shared-host and timing limitations. External models and production data are outside the experiment.
* No schema migration, production middleware or changes to strong-transaction isolation, billing, role/cut/version checks or retry policies are authorized by performance alone. Preserve source, ordering, raw records, failures and reproduction commands before selecting a candidate.

## Additional fixed-revision candidate

After the first calibrated 5,000 full timeline requests produced 93 valid replies and 4,907 admission responses, register an alternative that reduces repeated PostgreSQL-to-Python transfer on a fixed revision. Keep all business semantics, payloads, fences, pool limits and original AT-30 benchmarks. Compare the unmodified kernel with a one-entry cache of verified UTF-8 snapshot text in the benchmark process only. Every warm read still addresses the exact work/branch/revision row and hashes its live contents in PostgreSQL. Require the original throughput/tail thresholds in both orderings, matching delivery outputs and an independent corruption test. This calibration experiment cannot replace the historical HTTP gate.

## Additional adaptive FIFO comparison

Before measuring the optional adaptive mode, compare fixed FIFO micro against adaptive using the same unjoined read SQL, four execution slots and connections, capacity 128, batch ceiling 32, maximum delay 2 ms, 50 bound reader identities, two independent supervisor leases, and 1,000 operations per run (90% reads, 10% independent renewals). On one runner run fixed/adaptive/adaptive/fixed separately for 1, 8, 64 and 128 concurrent closed-loop clients. Require full semantic and durable renewal verification. Record actual idle direct calls, observed batch sizes, immediate flushes, feedback waits, per-operation latency, and connection occupancy. The sparse case must call the incumbent get_task and bypass queue admission when idle. Peak parallel database work must stay within four. A change that only creates more queued work fails.

Relative to fixed FIFO in both run orders, adoption at a load level requires either 10% more verified throughput or 25% fewer SQL executions with goodput no worse than -5%, and no more than 10% deterioration on P95/P99 of both the total and renewal-only samples. Do not infer a universal setting from a load-level pass. A normal-entrypoint confirmation is additionally required before proposing production adoption.

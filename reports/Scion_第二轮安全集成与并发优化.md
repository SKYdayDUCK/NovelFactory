# Scion 第二轮安全集成与并发优化

本阶段将第一轮的三个列投影调用独立配置，并将稀疏 Scope 查询限制在服务端已经证明足迹闭合的模板。库表、事件、审批、回执、公共 API 和原容量门槛沿用原版本。

## 实际集成

| 配置 | 未设置时 | 运行位置及回退 |
|---|---|---|
| `NF_SCION_WORKER_COLUMNS` | 开 | 派生工作者同步发布前的第二次源复核读取分支序号、状态摘要和清单摘要。设为 0 恢复同一 SQL 条件的全行读取。 |
| `NF_SCION_REVIEW_COLUMNS` | 关 | 显式设为 1 时，晋升审核的历史枚举只读取修订 ID 和 provenance；仅有两个候选修订的本轮完整晋升未表现出稳定收益。 |
| `NF_SCION_QUERY_COLUMNS` | 关 | 显式设为 1 时，已固定版本的查询只取既有清单中的列。仍需读取和校验 snapshot。上下文编译继续读取完整修订。本轮固定查询两组各仅 5/9 对更快。 |
| `NF_SCION_SCOPES` | 关 | 显式设为 1 后，闭合模板的证书签发与复验只读取足迹所需键；其他模板回退到全部分支 Scope。两档均减少读取行，接受操作耗时没有稳定下降。 |

四项设置在 Kernel 初始化时生效。显式细分配置优先；未指定细分时，继承原组开关 `NF_SCION_COLUMNS=0/1`，再未指定才用表中默认。多进程 API、独立工作者要分别重启并应用配置。恢复第一轮完全关闭的读路径时设 `NF_SCION_COLUMNS=0` 和 `NF_SCION_SCOPES=0` 并清除三个细分覆盖，也可直接将四个细分/Scope 开关都设为 0。无需数据库回迁。后缀重放另行验收。

## 调用路径和一致性

- 工作者的 `_material` 在一致读取事务中取完整源版本，校验状态哈希、调度来源和 outbox 的 WorldRef，然后生成确定性派生物。正式发布仍先校验投递租约、锁定 work 与 branch、对照已准备材料的三个标量；完成 inbox、artifact、watermark 和 ack 的原顺序一致。三列查询保留 work/branch/revision 三个谓词。迟到生产者、重复投递、提交回执丢失和崩溃重放均经过原处理。
- `Kernel.promote` 仍验证双方权限、读取并校验完整候选投影、重放所选事件、复审 repair 的独立审批。细分开关仅缩小枚举历史修订的列。写事务仍锁定 work 和分支、重新判断 canon/candidate 双头、批准有效性及 fork 基线。
- `WorldQueryService._sample` 在读取权限和任务代际后固定 WorldRef。列投影保留状态哈希、调度摘要、选择清单和时间覆盖；授权切面、认知视图与交付复检沿用旧路径。编译上下文依赖 `scope_versions`，始终读取完整版本。
- B2 的唯一生产写模块入口是 `prepare` 与 `_verify_tokens`（由 `accept` 调用）。签发用服务端重新构造的足迹；验收用受信任签发记录及已绑定的提案足迹。只有模板注册表 `GUARDED` 中的五类命令可做稀疏查找。接受使用持久化证书上的模板身份，模板、签发记录、审批、祖先和 generation 在原流程检查。严格模式下的历史修订等其他模板读取全表，变更注册表需同时验证负向和跨行约束。
- 稀疏 SQL 同时限定 work_id、branch_id 和 reads∪writes，保留原读写列表顺序。缺失键以 0 构造；注册表、谓词范围、空范围与 closure 继续进入原足迹。授权、审核、canon、解释 epoch 从原所有者取得。正式写入 bump 后仍取全量 Scope 映射生成不可变修订；新添完整性用例逐项核对该映射。依赖校验不能替代分支锁、幂等回执或数据库约束。

## 相同输入的真实 PostgreSQL 对照

PG 17.11，启用 fsync 与 synchronous_commit。50、200 个逻辑身份的世界分别包含 176、536 个既有 Scope；每档先运行一对预热并丢弃，再交替执行 9 对。每臂有相同种子数据库的独立克隆、相同的已授权请求和独立复制的对象目录，应用与数据库共享固定 CPU 2–3。实验分别调用完整单次服务流程，包括 worker 认领至 ACK、真实修订晋升、固定状态查询、签发以及携带同一签发结果的正式接受。晋升使用单独的真实修订世界，每次枚举两条候选修订。50/200 是夹具规模；本项测试顺序调用业务流程，不计为并发容量验收。

每行是各臂九次完整操作的中位数，顺序为“全量 → 对应优化”。“更快”按同一对的墙钟判定。PG CPU 用本次操作实际签出的数据库后端 PID 的 Linux schedstat 运行时间，包含其 SQL 和发送结果的 CPU，进程后台维护另计。行数来自 cursor，JSON 字节为 psycopg 实际解码量，省略了 PG 协议、标量列与物理盘流量。每次独立克隆均验证固定查询输出、派生对象哈希、晋升结果、证书 token/审批/范围、接受后的状态/选择/完整 Scope；重试同一接受请求返回原回执。

工作者在两档均减少一份 Revision JSON 传输/解码，完整投递时间、应用 CPU 和 PG 后端 CPU 的中位数均下降，故开放其正常路径。晋升的读取字节确实减少，两档完整操作中位耗时均未下降。B2 证明了 Scope 读取行数和签发工作量的变化；正式接受仍读取全量版本和 Scope，在 200 人口下合计返回 586 行，不能从一次稀疏查询外推完整事务提速。观察到的限流、进程数压力及热区容量交由 S4/S5 的原工作负载验证。

## 测试、证据及复现

[50 人口逐操作记录](../evidence/scion_round2/s2/paired_50.json) · [200 人口逐操作记录](../evidence/scion_round2/s2/paired_200.json) · [PostgreSQL 局部回归 JUnit](../evidence/scion_round2/s2/targeted_pg17.junit.xml.gz) · [端到端计量代码](../benchmarks/round2_safe_reads.py)

两档记录含驱动与源文件 SHA-256、每对各臂五项操作的读行/字节、应用及 PG CPU、耗时、路径命中和一致性哈希。配对实验显式在两臂设置开关；采样完成后只按测量决定未配置时的 worker 默认值。在仓库根目录激活已安装项目依赖的 Python 环境，确保 PostgreSQL 17 工具在 PATH 中（也可设置 PG_BIN），可各运行一次以下命令。

```sh
export PYTHONPATH="$PWD/src:$PWD"
python scripts/with_postgres.py -- python benchmarks/round2_safe_reads.py --population 50 --pairs 9 --output /tmp/s2-50.json
python scripts/with_postgres.py -- python benchmarks/round2_safe_reads.py --population 200 --pairs 9 --output /tmp/s2-200.json
```

在 PG17 打开 worker、review 和 B2，保持 query、B3 关闭，76 项专项回归全部通过，0 失败、0 跳过。专项用例覆盖工作者掉电/重投、过期租约、跨分支索引隔离、晋升撤销审批与双头 CAS、读缓存撤权、固定 cut 与认知校验、负向谓词幻读、guarded 并发和代际、历史修订、回执重试、旧索引不会回退已发布水位。新增用例验证每个配置可独立开关、同名键在不同分支与作品隔离、缺失键取 0、签发和接受各查一次同一键集、幂等重放不再取 token、strict-only 模板使用旧完整读取。完整冻结版本与各阶段的系统性对照见本轮独立性能与验收材料。

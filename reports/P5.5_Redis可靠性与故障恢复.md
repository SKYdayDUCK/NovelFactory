# Redis 可靠性与恢复验收

本地实测 PostgreSQL 17.11、Redis 8.0.2、redis-py 6.4.0、Python 3.12。数据库启用 fsync、数据页校验和与同步提交。故障用例使用独立 TCP 端口和数据目录，Redis AOF 测试使用 appendfsync always，以便 SIGKILL 后验证可重复的持久化窗口。实际部署的 everysec 可能丢失最近的传输记录，对应恢复由 PG 权威源与稳定 event_id 验证。

| 验收项 | 状态 | 可复现证据 |
|---|---|---|
|多个组广播，同组竞争、PEL、XAUTOCLAIM、XACK|DONE|test_p55_real_streams.py 在真实 Redis 设置两个组和两个 consumer|
|XADD 后进程退出，SQL 回写前租约失效|DONE|test_relay_crash_before_recording_and_worker_crash_before_ack 在实际 Redis pipeline 返回后由子进程退出 74，重发产生两个传输 ID|

联合命令在项目根运行。先提供独立测试 Redis 的 NF_TEST_REDIS_URL，确保可执行 redis-server 在 PATH，设置 PostgreSQL 17 的 PG_BIN。脚本创建隔离 PostgreSQL 集群。

```bash
python scripts/with_postgres.py -- python -m pytest -q \
  tests/reliability/test_p55_eventhub.py tests/reliability/test_workflow_downgrade.py \
  tests/integration/test_p5_workflow_migration.py tests/integration/test_p55_real_streams.py \
  tests/unit/test_p55_stream_contract.py
```

本次运行结果为 **12 passed in 6.07s**。其中 5 项是包含多个故障边界的端到端用例，1 项单独验证 Redis 原语，3 项检查信封及版本契约，3 项是迁移及回退原有回归。传输层用 SQL 效果见证重复，实际 Kernel 世界提交、PITR、预算与模型未知调用的结果在综合交付报告中单独列出。暂无跨主机网络分区时长或多副本 Redis failover 性能数据。

## 迁移、权限与多进程传输复核

从 0007 升级前已存在一个等待生产者结果的 BLOCKED 任务。升级后的等待记录逐列相同，依赖完成前唤醒数为 0，完成后首次恢复唤醒 1 次，再次恢复为 0。第一次 Redis 实际投递后，回退到 0007 被拒绝并保留既有工作。Redis 使用仓库的配置文件和从 ACL 模板生成的三个独立账户启动。relay 能执行 relay/status/repair，worker 能启动所有六个 Processor CLI，maintenance 实际重投并清理已完成的消息。反向用例验证 worker 无权 XADD，relay 无权 GET。五项故障用例及两项部署升级用例合计 **7 passed in 8.69s**。可查阅 [JUnit 明细](../evidence/p55/transport-faults-upgrade-acl.xml)。

多进程测量分两段执行。数据库预先提交一批合成 audit.recorded，4 个独立进程先从 PG 争抢并投递，接着 4 个进程竞争消费同一组，在同一 SQL 事务写入无唯一约束的效果见证和 Inbox 收据。每进程至多 1 个 PG 连接、1 个 Redis 连接，批量 32。以 PG 时钟从批次开始计到每条效果写入。每档运行一次，Redis CPU 为服务进程的用户态与内核态 CPU 时间之和。每档刚投递完时的组 lag 等于批次条数，最终 lag 和 PEL 均为零。

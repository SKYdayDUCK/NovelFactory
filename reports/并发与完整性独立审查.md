# P1 并发与完整性独立实现审查

## 审查范围与结果

本记录来自负责可靠性模块的开发 Agent 对另一开发 Agent 实现的 Kernel、命令模板、统一查询及权限协议的交叉审查。它是开发期审查证据，不能代替用户要求的交付后独立审核。

审查重点为 P1-02、P1-04、P1-06、P1-08 与 P1-10 的正式提交边界、历史修订和权限。新增反例位于 `tests/concurrency/test_world_races.py`，**20 项均在真实 PostgreSQL 17.11 上通过**。与当时的 `tests/reliability/` 27 项联合运行为 **47 passed / 0 failed / 0 skipped**。收尾审查又修复任务接受终态和对象重复持久化确认，新增 7 项反例后，可靠性模块最新单独运行 **34 passed / 0 failed / 0 skipped**。完整项目的 P0/P1 总验收以集成审计报告为准。

未开展 P2 的模型接入、小说生产或自动语义合并。

## 真实竞争的制造方式

测试并非顺序调用后仅比较返回值。`_overlap` 让首个接受事务在 `after_events` 故障注入点持有分支锁暂停，第二个接受事务从独立连接进入，第三个连接查询 `pg_stat_activity` 和 `pg_blocking_pids`。测试断言存在不同 backend PID、第二个事务实际等待 `nf_branches` 的 `FOR UPDATE` 锁后才释放首个事务。这样在真实数据库内形成竞争，再检查最终状态与返回错误。

崩溃反例在独立进程中调用 `os._exit`：一个发生在插入事件但事务尚未提交时，另一个发生在提交成功、响应尚未返回时。前者应由 PostgreSQL 回滚完整事务，后者重试必须返回原收据；两者均核对世界效果没有重复。

## 已验证的不变量

| 范围 | 实际反例与预期结果 |
| --- | --- |
| `STRICT_HEAD` | 同一旧 HEAD 的两个独立连接竞争，恰有一个正式接受；另一个版本冲突 |
| `DEPENDENCY_GUARDED` | 同一旧版上两个独立物品变更、两个独立资源转移均可接受，并串接到同一最新世界历史；不把旧版改写成新版再掩盖冲突 |
| 共享资源 | 两个各自看似足额的资源支出合计超额时仅一个接受，余额不为负 |
| write skew | 两名守卫同时依据“仍有其他守卫”离岗，约束组保护至少留下一人 |
| phantom | 准备时未发现道路阻断关系，期间新增符合范围的关系，旧证书必须失效 |
| 采样竞态 | `after_sample` 插入真实世界变化，证书不得以新依赖版本覆盖旧查询观察；接受被拒绝 |
| 当前权限 | 撤销提交者授权、撤销批准、外层任务预检后撤权均不能产生新的授权写入 |
| 证书 | 过期证书、未登记伪证书、解释 epoch 变化均被拒绝 |
| 幂等 | 同键同内容返回原收据，同键异内容拒绝；同一 proposal 换幂等键仍不能重复世界效果；提交后取消或撤权不抹除原合法回执 |
| 数据库不变量 | 直接 UPDATE/DELETE 正式事件和修订记录被 trigger 拒绝；依赖范围 token 不可删除以重置历史 |
| 来源 | 不存在的认知事件证据不能正式生效；结构合法但不存在的规则和裁定引用不能用于修订 |
| 修订 | 从赠与改成借用后，后续“以拥有者身份出借”的旧命令失去前提，修订被拒绝；原版和分支不受污染 |
| 分支推广 | 修订已接受后撤销其独立批准，推广仍被拒绝；canon 在修订期间推进则双 HEAD CAS 拒绝，保留两条历史 |

## 实际发现并修复的问题

### 1. 任务权限预检存在时间竞争

初版统一入口在一个读事务核验权限后调用任务服务开启另一事务，中间撤权会留下窗口。修复后 `TaskService` 的公开变更入口接受 `authorize_in_tx` 回调，统一 Kernel 在真实写事务内部、维护锁之后、任务锁之前校验并锁定当前授权。回归反例通过在外层检查与内部调用之间实际撤销 grant，核对任务未创建。

### 2. 来源结构校验不足以证明来源存在

审查构造结构合法的随机 EventRef，以及结构合法但未登记的 ruleset/adjudication ArtifactRef。初版正式接受了这些数据。`source_integrity_confirmed` 的 **2 failed** 是对此问题的实测记录，不是环境错误。

修复后 proposal 建立和最终接受均验证：同作品真实登记的规则及裁定类型；事件证据在其声明版本和候选所依据的历史中被选中；证据事件时间不得晚于获知时间；文本片段必须符合对象长度和引用哈希。两个反例在最终运行中通过。

### 3. 历史效果可重放不等于后继命令仍然成立

初版修订只对替换后的 effects 重放。例如先赠与再由新拥有者出借，把赠与修订成借用后，后续出借仍可能机械重放成功，但命令前提已不成立。`repair_review_regressions` 保留此反例的原始失败。

修复后 `_revalidate_repair` 对确定故事时间排序，逐段重建历史前缀，调用已登记原始封闭命令重新验证后继前提及效果。无法证明的来源、延迟 effect 或未知后继保守返回 `REPAIR_INCOMPLETE`；修订上限 200 个被选事件，限制本阶段同步复验成本。替换事件本身由独立批准负责，未实现自动文学语义重规划。

### 4. 推广时需要再次检查批准资格

初版 `repair_ready` 和状态哈希通过后，未重查早先批准是否撤销。审查确认修订接受后撤销批准，推广仍成功。修复后推广收集修订分支历史修订的批准引用，并在 canon CAS 事务内重新检查当前批准及审查人资格并保持锁；双 HEAD 和原 fork 基线检查保留。撤权与 CAS 两项反例均通过。

### 5. 查询历史边界与恢复解释资产

交叉审查还发现：晚获知的未明确时间命题可能倒灌过去目标时点、未知资源可能错误显示零余额。领域与查询负责人修复并新增专门查询测试，覆盖明示 `subject_time` 的迟获知过去事实、UNKNOWN/未创建身份与合法零余额的区别；该部分最终结果由查询报告及全项目证据记录，本报告不把未在本次 47 项命令运行的测试计入本次结果。

部署审查发现备份原先只覆盖 Python 解释器文件，未覆盖 `query_profiles.json` 权限配置，wheel 环境 Schema 路径也需适配。可靠性模块补齐两个路径模式及权限配置哈希校验，相关两项新测试已计入本次 27 项可靠性结果。

### 6. 正式接受与任务终态没有在同一事务闭合

收尾按调用路径检查发现，世界接受已写入事件、版本、收据和 Outbox，但没有关闭对应 P1 封闭命令任务。它仍处于 RUNNING 或 RESULT_STORED，可能被当作待执行任务回收。与内核负责人确认后，增加 `TaskService.accept_in_transaction` 并由正式接受事务调用；同事务写 ACCEPTED、清租约与任务消息。一任务只能完成一次世界接受，历史同键重试仍提前查原回执。

新增参数反例覆盖 RUNNING、RESULT_STORED、VALIDATING、WAITING_REVIEW 四种有效输入状态，另验证外层事务失败时终态与 Outbox 同步回滚，以及任务完成后的已发送调用仍能正确结算。5 项新增可靠性测试通过。直接 RUNNING 接受仅用于已经完成本地封闭验证及独立批准的 P1 控制命令，不表示允许普通模型结果跳过验证。

### 7. 复用崩溃写者已发布对象时必须再次确认持久化

初版 `put` 发现 hash 路径已存在时只核验内容后返回。若写者在 link 发布后、目录同步前进程退出，其他写者可观察到路径，但不能据此认定目录项已经持久化。先运行真实子进程在 `after_publish` 的退出反例，记录后继 `verify` 和重复 `put` 没有 fsync，结果为 **2 failed**。

修复后 `verify` 完成哈希/长度校验，再实际 fsync 文件、分片目录和对象根目录；数据库引用者持续持有共享文件锁至事务提交。两个反例通过，并在最新 34 项可靠性回归中再次执行。该证据是实际进程退出与系统同步调用验证，不声称进行了物理断电测试。

## 收尾数据库与写入路径核对

只读追踪了 `infrastructure/database.py`、迁移 `0002`、`KernelRepository`、所有 Kernel 正式变更入口、Context Compiler 持久化、TaskService、Outbox 和 BackupService，结论如下：

- 正式事件、版本 snapshot、版本事件选择、提交记录、产物、ContextBundle、proposal、证书、回执、失效记录、推广记录及任务历史表安装 UPDATE/DELETE 拒绝触发器。历史 snapshot 从不可变版本读出，并核对 state_hash。
- 分支 HEAD、canon 指针和父版本具有复合作品/分支身份外键；版本事件选择具有 occurrence/effect_group 复合身份外键和同版本效果组唯一约束。核心提交在分支锁内比较预期 HEAD，正式事件、关键投影、同步失效、收据和 Outbox 在同一 UoW 内生效。
- 正式事件写入只出现在统一接受协议；bootstrap 写初始设定、fork 继承不可变选择、promotion 切换正式分支指针，均不绕过接受协议追加运行事件。内部 Repository 和数据库所有者属于可信维护边界，不直接对外暴露。
- 持久化对象引用的入口按“文件共享锁 → 维护共享 gate → 授权/分支/任务”顺序进入事务。GC 在排他文件锁内读取已提交引用，备份持有共享文件锁与维护排他 gate；已检查路径没有发现互相倒置的获取顺序。任务和 Outbox 普通变更均参与维护 gate。
- 备份在相同冻结窗口内记录所有 public 表、调用真实 pg_dump 并复制数据库登记对象；恢复先比较未恢复运行态前的精确逐表摘要，再围栏旧任务及消息资格。源代码和权限配置必须在 create/verify 的运行窗口保持稳定。

内核负责人另在收尾加入修订 `history_epoch` 原子推进和不可变版本 epoch 记录，阻止跨修订的旧输入重新取证；其最终新反例与迁移 DDL 冻结由全项目运行记录负责，本报告不提前宣称这些新增项已通过。

## 独立审核仍应关注的边界

1. 守卫能力只覆盖已登记、确定性、有限封闭命令。审核者应逐个追踪每个模板的实际读依赖、负范围、共享约束、精确写范围及失效 bumps 是否相互对应，不能由现有测试推论任意未来模板都安全。
2. 同一分支正式接受仍以分支行锁串行建立权威历史。独立 guarded 命令的收益是容许安全接受旧基线，不代表多个事务可同时修改同一 HEAD；本轮不声称分布式线性扩展。
3. `TaskService`、直接数据库连接、对象回收和备份属于可信内部/运维组件。公开入口必须始终通过 Kernel 权限验证，不能将内部方法直接路由给用户。
4. 修订限制是显式拒绝边界：精确时间、无延迟调度效果、最多 200 个选中事件、已登记命令后继。复杂修订应被拒绝并交由后续能力处理，不允许用当前能力声称完成任意语义修复。
5. 备份为 PG17 单机逻辑备份，要求全部权威写者参与维护 gate；对象锁依赖同一 POSIX 文件系统。不覆盖 WAL/PITR、网络对象存储或外部模型副作用的灾后对账。

# Scion 增量版本管理 PostgreSQL 性能对照

A 为冻结提交 2c28acba6e1932657162c6e55b3288365ce3ea23；B 为 1db99217497c74f0e6ebb6fdf8c4ed977022963f，除单项消融外三个开关均启用。世界及历史由正式内核入口生成。报告区分每次工作量、实际写入和端到端容量。阶段 A 中有问题的 codec 首轮、预热及计量脚本变化前的试跑均不计作加速。

## 试验条件

- 真实 PostgreSQL 17.11，fsync 与 synchronous_commit 开启。每对沿用相同连接池、负载脚本、超时与重试预算。业务读写受原鉴权、时间切面、审批、代际和 CAS 限制。没有使用外部模型。
- 顺序归因在克隆的数据库与对象目录中执行，验证源代码 SHA 和实际导入路径。冷样本是在新进程中第一次处理该父版本；连续写入使用同一个 Kernel 及其实际产生的下一父版本。用户查询缓存的冷热是另一维度。
- 长历史采用三实体、无初始关系的资源转移世界，逐次创建任务、提案、证书并正式接受，检查点按 PG 中真实事件正文完整重建。A/B 从同一份数据库快照恢复，固定业务时钟和身份生成，按 A/B、B/A、A/B 交替次序测三对。输出比较父/新 WorldRef、事件选择、状态和清单哈希、正式回执。关系较多的世界另由 1、20、100 事件实验承担。结果只代表相应数据形状。
- HTTP 负载用原服务进程、真实持久化任务和权限。两臂共享逻辑请求序列和预置世界；证书及正式接受使用各臂前序返回的真实引用，动态标识可不同。逐字相同的未变化输入、逐阶段语义正确性及协议字段见 C 的独立冻结对照。客户端实际发送、服务端 ASGI 到达和有效业务完成分开计数。
- 原始样本的 cpu_affinity 记录进程允许调度的逻辑核集合。每对使用相同集合；该值未测量独占算力或 cgroup 实际 CPU 时间配额。不同负载组并行运行于共享宿主，存在 CPU、I/O 和页缓存的背景扰动。本文列中位观测、配对数和不能复现的改善；小样本不作显著性检验。

## 各项收益、回归与故障边界

- **B1 列投影**。工作者源复核的返回值完全一致，省去了该次整行的 JSON 解码；普通固定 cut 查询少解码 4.42%，仍须读取并校验完整 snapshot。单项消融、进程 CPU 和服务尾延迟并未给出一致的查询提速证据。修订枚举只返回实际使用的列，其整次推广耗时没有作为独立收益。
- **B2 稀疏 Scope**。单独打开时，200 人口 fixture 的证书阶段 SQL 返回行由 559 降到 32，其中 token 读取由 536 降到 9。签发与接受仍复核相同的负向、范围和当前授权 token。往返次数和最终完整 Scope 写入没有变。可以独立审核读行优化；尚未观察到它单独解除共享入口的准入或容量限制。
- **B3 单事件后缀**。1000 事件的三实体世界中，连续接受的进程 CPU 从 1074.09 降至 323.92 ms，返回行从 3060 降至 2058（全开 B 也使用稀疏 token）；完整重放从 1 次降到 0 次，仍处理 1 个新增事件。首次提案有明显回归，特别是在建立证明并仍做完整重放时。较小世界、不同实体/关系分布及多进程分流可改变收益方向；200 人口单开关消融也保留了这种差异。Retcon 和复杂因果串继续完整重放，两臂处理的完整事件数相同。
- **原容量门槛**。普通业务、端到端全流程、有效请求率和新提交 TPS 是不同指标。200 突发的一核诊断 A 在 compile 阶段有一个 Agent 耗尽 5 次尝试，原生成器随即结束后续阶段；A 只发 381 次，B 发 3733 次。两侧分别 0 与 15 个新世界提交，这次差距不能归因给内核。两核重复换成 21/21 对 21/21，得到相反的逐 Agent 差异。1000 开放到达的客户端实际 headers 速率远低于 1000/s，同时服务端仍出现大量 429。原规模目标继续为 NOT_MET。

除经同仪表、同输入检查的样本外，原始目录保留了仪表定稿前的试跑。首次 50 混合和四核 1000 开放 A 缺少同版 ASGI/PG CPU 记录，对应缺项留空；50 使用 mixed50-repeat、1000 使用 open-repeat 作为完整对照。顺序剖析的首对如缺少同一仪表摘要/连续写测量，已从统计中剔除。不同配额和不同新旧仪表不混算。状态查询试跑所用的旧阶段 A profile.json 同样被排除。业务请求中实际生成的不同证书引用单独登记，另以固化查询、提案、证书及接受请求的夹具核验完整请求摘要和接受后的状态及选择。

500 Agent 的三组 600 秒配对共计每臂 36,000 次计划读取，每位 Agent 每组各 24 次。主组（四个可用核）两臂均有 500/500 位 Agent 完成，均成功 12,000 次，P95 为 860.22 → 506.08 ms。第一组双核重复为 17 → 113 位，成功 10,466 → 11,370 次；A 侧与长历史作业重叠，两臂均未过容量门槛。带独立 headers 计量的另一组双核重复，两侧客户端与服务端均实测约 20 次/秒，完整 Agent 为 471 → 500 位，成功 11,971 → 12,000 次，429 为 29 → 0，P95 为 1611.99 → 1181.58 ms。各组原始判定分别为 PASS/PASS、NOT_MET/NOT_MET、NOT_MET/PASS。共同方向是这三组候选 P95 均下降；全量业务完成率只在两个双核样本上升，不能保证所有运行都通过。

## 复现及指标口径

从 PR #4 的交付工作树运行。下面的 A 和 B 都是只读的独立 Git 工作树；D 的脚本使用当前工作树中的版本。用项目锁定依赖的绝对 Python 路径及可执行的 PG17 二进制替换环境变量。每个配对共享数据库模板，但使用自己的数据库和对象副本。私有测试数据目录只在本机使用，不上传存储副本或临时凭据。

```bash
set -eu
delivery_root=$(pwd)
scratch_dir=$(mktemp -d)
a_sha=2c28acba6e1932657162c6e55b3288365ce3ea23
b_sha=1db99217497c74f0e6ebb6fdf8c4ed977022963f
git worktree add --detach "$scratch_dir/A" "$a_sha"
git worktree add --detach "$scratch_dir/B" "$b_sha"
runner="$delivery_root/scripts/with_postgres.py"
driver="$delivery_root/benchmarks/scion_paired.py"
test_python="$delivery_root/.venv/bin/python"
export PG_BIN=/usr/lib/postgresql/17/bin
"$test_python" - "$scratch_dir" "$b_sha" <<'PY'
import json, sys
from pathlib import Path
out = Path(sys.argv[1])
flags = {f"NF_SCION_{name}": "1" for name in ("COLUMNS", "SCOPES", "REPLAY")}
(out / "B.json").write_text(json.dumps({"root": str(out / "B"), "sha": sys.argv[2], "env": flags}))
PY
(
  cd "$scratch_dir/A"
  export PYTHONPATH="$PWD/src:$PWD"
  "$test_python" "$runner" -- "$test_python" "$driver" --candidate "$scratch_dir/B.json" \
    --baseline-sha "$a_sha" --output "$scratch_dir/attribution" --repetitions 3 \
    --cases history-1-10 history-20-10 history-100-10 population-200
)
```

HTTP 运行使用相同 coordinator，将 cases 改为 mixed-50、mixed-200、hotspot-200、mixed-500、open-1000、steady-500，保留结果中的默认到达、轮次及持续时间。200 Agent 的 1000 RPS 突发另用 scion_ci_overload.py 运行 hotspot-200。不要在同一组统计中合并不同 CPU 配额。例如单独以 taskset 固定原始证据中的允许核，连同服务和 PG 父进程一同限制。所有 HTTP origin 的诊断运行保持 NF_BENCH_DIAGNOSTICS=1。完整复现脚本在 benchmarks 下；scion_ablation.py 独立开启各开关，scion_exact_requests.py 复用字节一致的调用，scion_agent_completion.py 从逐请求结果重算每个 Agent 的成功条件。

长历史另从 B 工作树运行 scion_long_history.py，设置 PYTHONPATH 指向 B 的 src 与根目录，先用 --output 私有目录、--candidate-sha 和 --checkpoints 20 100 500 1000 生成实际接受的检查点，再用 --probe、--baseline-root、--candidate-root、--baseline-sha、--candidate-sha、--results 和 --repetitions 3 比较相同快照；20 事件的修订场景再加 --repair。两次均由 with_postgres.py 在独立 PG17 上启动。同一历史累计占用的选择行数可由 nf_revision_events 实际计数复核。

响应检查使用原始契约、world_ref、语义返回及实际新增版本数。有效调用 RPS 扣除有意重复的成功回执；预期的 409 可满足该 Agent 的争夺处置任务，但不计入成功调用 RPS 或新世界提交 TPS。429/503 来自全部 HTTP 尝试，包括重试；按逻辑操作和按 Agent 的分母都不包括这些重复尝试。ASGI 到达率按首次与末次到达时间窗计算；全程有效 RPS 按实际试验耗时计算。长稳态原工具仅记录客户端 dispatch；stability-headers 补测在相同的 600 秒脚本中逐请求记录 headers 发送时刻，并保留服务端独立到达计数。等待事件以 pg_stat_activity 采样计数报告，没有据此推算累计锁等待毫秒。SQL 返回行不等同存储引擎扫描行，驱动 JSON 字节也不等同物理读盘。CPU、RSS、SQL 写入、错误、回退计数及各次时延保存在原始文件内。

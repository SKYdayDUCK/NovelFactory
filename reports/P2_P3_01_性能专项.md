# P2 遗留可靠性与 P3-01 性能专项

## 结论和范围

本阶段在已核对远程基线 `206eaa5b655419d29bd6b15d618ae6eaf9048354` 上开发。200 Agent 的本地正常负载从 **12/21 个新世界提交恢复到 21/21**；优化后的独立服务进程正常、热点负载也均完成 **21/21**，全部原定逻辑请求均已发出，世界资源、重复回执和固定知识切面检查通过。

**完整容量门槛仍为 NOT_MET。** 正常负载仍有首试背压，需要原有有界重试；热点开放到达目标仍为 1000/s，实际首次调用开始速率只有 47.84/s。没有调低目标、增加重试预算、放宽超时、增加总连接池、删除未完成操作或把重复回执算成新提交。`bounded_recovery_business_gate` 与 `capacity_gate` 继续分开。

本阶段完成的是有限、经测试的 CPU/SQL 优化和独立进程测量能力。没有扩大全部 guarded 命令集合，没有将全量重放改成未经证明的增量重放，也不声称完成完整 P3-01 容量验收。

## 1. 实际发现和实现

### 1.1 CPU 和重复验证

真实 PostgreSQL Context Compiler 的 cProfile 显示：300 个主体实体、12 个已接受历史事件的初始测量中，100 主体编译的剖析总耗时 0.457 秒；`validate_contract` 累计 0.329 秒，`point_key` 被调用 938 次、累计 0.092 秒。这些是包含剖析开销的定位数据，不用作吞吐测量。

`point_key` 现在只对**字段恰好为 tick/phase 且类型均为原生整数**的输入复用至多 4096 个已由原 JSON Schema 验证过的整数二元组。额外字段、bool、float、自定义对象、适配器和非法值继续经过原验证路径；无效输入不缓存。输入字典及任何世界、任务、权限数据不进入缓存。属性与反例测试覆盖负值、边界、可变输入、额外字段、布尔值和缓存上限。没有新增世界状态缓存或失效协议。

### 1.2 SQL 与 JSONB

`KernelRepository.ancestor` 原来读取两个完整 revision 行（含 snapshot JSONB），然后执行递归血缘查询。现在只执行一次按 work/branch 严格限定的父链 CTE，不读取世界投影；仍证明真实可达性，不能凭 branch_seq 推断血缘。反例验证逆向、未知版本、跨作品、伪造 work/branch 及完整查询仅涉及身份/父节点字段。

Context Compiler 原有批量依赖登记保持不变，本轮同切面配对的 SQL 数量仍为每次 47。世界接受仍使用原严格/有限依赖守卫、同一分支原子接受锁和完整重放；不通过取消权限检查或改变效果身份提高结果。

### 1.3 独立客户端与服务

新增 `benchmarks/process_server.py`，使用 spawn 创建独立解释器。每个服务进程在启动后自行建立池；负载客户端、API 服务不共享 GIL，也不继承活跃数据库连接。支持 1/2/4 个 API 进程，**总 API 连接池固定 8**；多进程分别分配 8/4/2 个连接。现有进程级限流语义与数据库权威事务不变。

驱动分别记录客户端和服务 CPU/RSS、SQL 次数及 cursor 执行耗时、进程池峰值、阶段结束连接、业务效果、延迟和显式背压。多进程峰值的汇总标注为“各进程峰值之和”，不冒充同一时刻的真实峰值。真实 PostgreSQL 观察连接独立计量，不计入应用 SQL。

新增测试在两个真实服务进程中提交世界事件，代理丢弃已提交回包后实际终止两个进程；重启后同请求返回完全相同的已持久化回执，世界效果仍一次。改变代际和撤销授权仍被拒绝。

## 2. 优化前后：原 200 Agent 规模与目标

测试使用 PostgreSQL 17.11、Python 3.12.14，fsync/synchronous_commit 开启；主机可见 9 个逻辑 CPU，非独占环境，未检测到标准路径的 cgroup 配额文件，不能据此宣称拥有 9 个独占核。数据规模、原任务比例、原请求、5 次/30 秒有界同字节重试、2 秒队列等待及总池 8 均保留。正常场景计划 1141 个逻辑请求，热点场景另加 1000 个开放到达读请求。

| 本地运行 | 新世界提交 | 逻辑请求未发出 | HTTP 尝试 | 首试失败 | 负载时长 s | 全响应 P50/P95/P99 ms | 完整容量 |
|---|---:|---:|---:|---:|---:|---|---|
| 优化前、原同进程、正常 | 12/21 | 23 | 1195 | 48 | 172.31 | 105.43 / 10819.75 / 18282.50 | NOT_MET |
| 优化后、同进程、正常 | 21/21 | 0 | 1151 | 6 | 145.51 | 91.88 / 1405.47 / 2574.66 | NOT_MET |
| 优化后、独立服务进程、正常 | 21/21 | 0 | 1173 | 20 | 142.96 | 101.10 / 2025.44 / 2762.27 | NOT_MET |
| 优化后、独立服务进程、热点+开放到达 | 21/21 | 0 | 3254 | 575 | 184.08 | 1841.57 / 13945.88 / 22017.83 | NOT_MET |

同进程正常场景的用户 CPU 从 115.03 秒降为 76.18 秒；峰值 RSS 从 149212 KiB 降为 141740 KiB。独立服务正常场景服务用户 CPU 为 75.94 秒、客户端为 6.64 秒；服务峰值 RSS 130504 KiB、客户端 87540 KiB。独立进程引入额外解释器内存，未显示本场景尾延迟优于优化后的同进程，因此不能把进程隔离本身描述成吞吐已提升。

正常场景原始 SQL 总数 31685→33013，并非 SQL 优化失效的同工作量对照：优化后额外完成 9 个新世界提交及其全部下游调用。血缘操作本身由 3 次 SQL/两个大 JSONB 读取减少为 1 次元数据 SQL。优化后同进程正常场景累计 cursor 执行时间 112.22 秒；独立正常 149.40 秒。它们是并行连接上的累计客户端 cursor 时间，包含锁和线程调度等待、排除结果解码，不能当作数据库纯 CPU 时间。原旧驱动未记录 cursor 时间，不补造其历史值；下节真实配对记录了两侧 SQL 次数和耗时。

独立正常场景观察到的连接采样主要是 idle/Client 或 idle in transaction/Client（分别 3024/927 个连接样本），active/Lock 为 11 个连接样本、active/IO 为 17；不是耗时占比。结合 CPU 剖析说明应用侧验证/投影工作仍应优先研究，不能仅凭连接数断言数据库容量不足。完整原始样本保留，不将短采样遗漏解释成绝无锁竞争。

热点场景实际首次调用开始速率 **47.8416/s**，最大调度延迟 **19882.50 ms**，未达到原目标 1000/s 的 95% 门槛。此速率还不是网络线上发送速率；客户端的响应验证和调度仍可能影响开放到达，需要更独立的到达/验证测量。系统成功请求吞吐、独立新世界提交吞吐均独立计数，背压与重复回执不计为新提交。

`benchmarks/p3_context_comparison.py` 从固定 Git 提交载入原 `point_key`/`ancestor` 实现，在同一个实际 PostgreSQL 世界、同一个不可变 WorldRef 上交替比较。每档 5 对，保留完整事实、完整来源证据、已验证任务特定字段和守卫材料，15 对均一致；事件数、世界 HEAD、状态/清单哈希及 scope 版本不变。任务标识等仅在验证其推导之后作任务局部字段处理。

## 4. 可复现命令

先按仓库说明配置真实 PostgreSQL 17，或用 `scripts/with_postgres.py --migrate --` 包装下列命令：

```bash
.venv/bin/python -m pytest tests/unit/test_temporal_coordinate_cache.py tests/unit/test_p2_load_evidence.py tests/integration/test_ancestry_metadata.py tests/service/test_process_isolation.py -q --junitxml=ci-evidence/focused.xml
.venv/bin/python -m benchmarks.p3_context_comparison --entities 300 --repeats 5 --output ci-evidence/context-p3.json
.venv/bin/python -m benchmarks.p2_behavioral_load --agents 200 --profile mixed --hot-fraction .2 --arrival-rps 10 --open-loop-rps 1000 --rounds 5 --max-attempts 5 --retry-budget-seconds 30 --service-mode isolated-process --api-processes 1 --gate-scope capacity --output ci-evidence/200mixed.json
.venv/bin/python -m benchmarks.p2_behavioral_load --agents 200 --profile overload --hot-fraction .8 --arrival-rps 10 --open-loop-rps 1000 --rounds 5 --max-attempts 5 --retry-budget-seconds 30 --service-mode isolated-process --api-processes 1 --gate-scope capacity --output ci-evidence/200hot.json
```

将 `--service-mode` 改为 `same-process` 可复测同进程模式；`--api-processes 2` 为总池不变的两个独立服务进程。`--gate-scope capacity` 未通过时程序退出 1，这是预期保留的容量失败证据，不修改为绿灯。

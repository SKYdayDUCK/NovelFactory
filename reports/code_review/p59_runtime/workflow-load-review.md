# Independent review of the workflow driver and selector

The workflow trial exercises application admission, the database task and Attempt ledgers, and the production candidate delivery path with an in-process fixture provider. Provisioning uses four client threads. After provisioning, two working execution slots drain two books. Separate measurements establish HTTP throughput and transport calibration. Scaling the total workflow population changes the size of the prepared queue.

| Driver observation | Interpretation |
| --- | --- |
| `i > 1 and i % 5 == 0` | 99 of 500 and 199 of 1000 workflows wait on their own book's prerequisite. A stored AND condition and a later PostgreSQL reconciliation scan awaken them. Separate integration suites exercise Redis recovery and independent review decisions. |
| `i % 100 == 83` and `i % 100 == 37` | Injected cancellations occur before a send. Indeterminate fixture outcomes occur after one send. Both classes are odd indices, so these injections all land in the second book. The driver verifies zero versus one Attempt and adapter invocation respectively. |
| Two prerequisite summaries | The first two successful summaries reach ACCEPTED. Most successful tasks reach RESULT_STORED, with the world head unchanged. They count as successful application work. This workload does not publish a book. |
| SQL state checks and callback records | The driver compares persisted states and Attempt counts for every matched task against the scenario and counts distinct principals. Its final gate also checks completion count, total wakeups, zero remaining slots and unchanged heads. Its result count, queue timing and distinct principal count do not count independent official world commits. |
| Queue and execution times | `creation_to_claim` spans task creation through the first recorded RUNNING event and includes provisioning and dependency waiting. `admission_to_result` times non-prerequisite futures from submission through completion. `completion_latency_from_enrollment` includes queue and wait time and excludes pre-cancelled tasks. Only completed successful results contribute to effective result throughput. |
| Resource and restart scope | The fixture pauses for either 5 ms or 100 ms inside a model call. In-flight model and worker peaks are measured separately. A new Supervisor object takes over the same Kernel, DB and gateway after provisioning. Process kill during a send, OS restart and commercial provider recovery need separate evidence. Peak RSS covers the Python process. It excludes the PostgreSQL server. |
| Admission under lost schedulers | A valid ticket can outlive its branch supervisor for up to two minutes. When the next selected task belongs to that branch, another branch returns IDLE. The alternating two-live-supervisor driver does not measure this interval. |
| External stdio processes | A standalone binding starts its own process and database pool. Idle bindings retire their checked-in connections after a configurable delay. Startup and recent calls can still overlap across processes. The workflow fixture uses a shared Kernel. A separate single-process MCP regression covers database reuse, release and renewed authorization. Aggregate connections, memory, process startup rate and end-to-end throughput for 5000 independently hosted bindings remain unmeasured. |

**Selector equivalence.** Migration 0005 defines `nf_supervisor_jobs.task_id` as the primary key. Replacing its inner join with a correlated single-key lookup and `OFFSET 0` preserves the zero-or-one matching enrollment and its config, including when no enrollment exists. The ordering, authorization predicates, task and grant locks and `SKIP LOCKED` behavior are the same at commit `f9f6634`. The planner can select a different index/loop strategy. Existing guarded-claim and fairness tests cover the subsequent write transaction.

A separate execution on a real PG17.11 database with 100 tasks and a single live branch ticket selected the exact same task in all four ABBA statements. Frozen timings were 26.41 and 49.35 ms, candidate timings were 35.85 and 36.99 ms. On the 2000-task fixture the frozen query timed out at the 15 s observation limit. That limit bounds the old runtime from below. A precise speedup for its hypothetical completion cannot be computed. On the frozen 200-agent HTTP run, the 1144 responses with HTTP 429 all carried `BACKPRESSURE`. Authentication admission recorded 1106 queue rejections and 25 queue wait timeouts. The business queue recorded 13 timeouts. The 19 HTTP 409 responses had `DEPENDENCY_CONFLICT`. The independent 1000-agent open run contains 3090 HTTP 429, 1870 HTTP 200 and 40 transport errors. There were no HTTP 401 responses in either run. ## Independent audit of the two one-hour HTTP read traces

Both archives reconstructed from their manifest parts with matching chunk, compressed-stream and uncompressed SHA-256 digests. Each contains every request index from 0 through 71,999 exactly once. Every one of the 500 logical agents started 144 reads. The assignment `agent = index % 500` and tool mix fixed by `index % 20` gave 450 agents state reads only, 25 history reads only, and 25 graph reads only. The validator checked the response contract and fixed world revision for every successful read. It also checked both expected state answers on state reads. The history and graph checks did not compare the complete returned contents with a reference answer. The original 409s started from second 3585.650 through 3599.951. The fixture claimed tasks sequentially with 3600-second execution leases before the read clock began. A running task's query checks both the current grant and its lease expiry. Every recorded 409 carried the lease error, and the driver classified these as unexpected statuses. The renewal variant renewed all 500 owner leases twice. Its single transport failure came from agent 103 at second 1205.154. Authentication admission completed 72,000 and 71,999 requests respectively, with no HTTP 401 or 403. Both runs missed the all-requests-valid gate. Summed process peaks reached 8 for the API pools, ending at zero checked out. The separate PostgreSQL observer, excluding its own session, sampled up to 8 and 10 connected database sessions respectively. Those observations include connections outside the API pools. [Read qualification](../../../src/novel_factory/application/queries.py) · [Database observer and fixture](../../../benchmarks/p2_behavioral_load.py)

The request timestamps are monotonic offsets. For each run, the measured start falls between the PostgreSQL wrapper's UTC start and its UTC finish minus the measured duration, assuming stable wall clock during that hour. Even at the extremes of those bounds, the first-to-last 429 intervals overlapped for at least 207.099 seconds on November 12, 2026. In the UTC minutes beginning 17:57, 17:58, 17:59 and 18:00, at least 41/21, 109/49, 2/4 and 131/44 pressure responses respectively **started** in the original/renewal runs. These lower bounds count only starts whose entire possible UTC range lies inside that minute. The overlap establishes concurrent pressure on the shared host. Request records do not isolate its cause.

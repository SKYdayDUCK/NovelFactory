# Independent review of the workflow driver and selector

The workflow trial exercises application admission, the database task and Attempt ledgers, and the production candidate delivery path with an in-process fixture provider. Provisioning uses four client threads. After provisioning, two working execution slots drain two books. Separate measurements establish HTTP throughput and transport calibration. Scaling the total workflow population changes the size of the prepared queue.

| Driver observation | Interpretation |
| --- | --- |
| `i > 1 and i % 5 == 0` | 99 of 500 and 199 of 1000 workflows wait on their own book's prerequisite. A stored AND condition and a later PostgreSQL reconciliation scan awaken them. Separate integration suites exercise Redis recovery and independent review decisions. |
| `i % 100 == 83` and `i % 100 == 37` | Injected cancellations occur before a send. Indeterminate fixture outcomes occur after one send. Both classes are odd indices, so these injections all land in the second book. The driver verifies zero versus one Attempt and adapter invocation respectively. |
| Two prerequisite summaries | The first two successful summaries reach ACCEPTED. Most successful tasks reach RESULT_STORED, with the world head unchanged. They count as successful application work. This workload does not publish a book. |
| SQL state checks and callback records | The driver compares persisted states and Attempt counts for every matched task against the scenario and counts distinct principals. Its final gate also checks completion count, total wakeups, zero remaining slots and unchanged heads. Its result count, queue timing and distinct principal count do not count independent official world commits. |
| Queue and execution times | `creation_to_claim` spans task creation through the first recorded RUNNING event and includes provisioning and dependency waiting. `admission_to_result` times non-prerequisite futures from submission through completion. `completion_latency_from_enrollment` includes queue and wait time and excludes pre-cancelled tasks. Only completed successful results contribute to effective result throughput. |
| Resource and restart scope | The fixture pauses for either 5 ms or 100 ms inside a model call. In-flight model and worker peaks are measured separately. A new Supervisor object takes over the same Kernel, DB and gateway after provisioning. Process kill during a send, OS restart and commercial provider recovery need separate evidence. Peak RSS covers the Python process. It excludes the PostgreSQL server. |
| Admission under lost schedulers | A valid ticket can outlive its branch supervisor for up to two minutes. When the next selected task belongs to that branch, another branch returns IDLE. The alternating two-live-supervisor driver does not measure this interval. |
| External stdio processes | A standalone binding starts its own process and database pool. The shared-kernel fixture does not measure several thousand independent MCP hosts or their aggregate connections. |

**Selector equivalence.** Migration 0005 defines `nf_supervisor_jobs.task_id` as the primary key. Replacing its inner join with a correlated single-key lookup and `OFFSET 0` preserves the zero-or-one matching enrollment and its config, including when no enrollment exists. The ordering, authorization predicates, task and grant locks and `SKIP LOCKED` behavior are the same at commit `f9f6634`. The planner can select a different index/loop strategy. Existing guarded-claim and fairness tests cover the subsequent write transaction.

A separate execution on a real PG17.11 database with 100 tasks and a single live branch ticket selected the exact same task in all four ABBA statements. Frozen timings were 26.41 and 49.35 ms, candidate timings were 35.85 and 36.99 ms. On the 2000-task fixture the frozen query timed out at the 15 s observation limit. That limit bounds the old runtime from below. A precise speedup for its hypothetical completion cannot be computed. On the frozen 200-agent HTTP run, the 1144 responses with HTTP 429 all carried `BACKPRESSURE`. Authentication admission recorded 1106 queue rejections and 25 queue wait timeouts. The business queue recorded 13 timeouts. The 19 HTTP 409 responses had `DEPENDENCY_CONFLICT`. The independent 1000-agent open run contains 3090 HTTP 429, 1870 HTTP 200 and 40 transport errors. There were no HTTP 401 responses in either run.

## Authority and state

* Both task create entry points reach TaskService.create_in_transaction. A matching original receipt is checked after current grant authentication and before capacity counting. The enabled singleton serializes concurrent occupancy decisions. The input, task, outbox and receipt share one commit. Old tasks count against enabled limits. Forward and reverse transport retries must retain the original spec and idempotency key.
* The new project progress path derives all counts from nf_tasks transitions in the same transaction. Its explicit backfill takes a lock that excludes task writes. The read applies quota retry time in its database snapshot and falls back to existing authoritative counts if no branch projection is installed. The watermark counts mutations of the aggregate. It does not identify a reconstructible global outbox position.
* Model sends use the existing attempt ledger. Lease recovery treats a SENT attempt with an unknown outcome as UNKNOWN and a held reservation. A repeated command with an existing receipt returns its original result. Actor-specific grants, dynamic role ceilings and knowledge cuts continue to govern the existing bound role APIs. Generic task metadata cannot return a knowledge bundle.
* An ordinary TaskSpec is available for an external worker to claim. Automatically dispatched model work uses the trusted delegation slot. Delegations._bind creates the task, binds its Supervisor config and adds its receipt in one transaction. The same installation verifies exact operation and receipt at Workshop settlement. PostgreSQL stores the durable wake intent. Restart and replay can deliver duplicate hints; inbox and generation guards constrain their business effect. No real provider charges were used in these tests.
* Both the publisher and consumer grouped Workshop paths perform network operations after PostgreSQL commit boundaries. The publisher can replay a lost Redis acknowledgement, and the consumer acknowledges its stream entries after committing the matching inbox transaction. The diagnostic stream and authoritative PostgreSQL transaction remain separate.

## Independent review of REST and MCP adapters

The durable admission implementation reviewer inspected the transport author's ordinary REST and MCP adapters against main `bcb03637`. The reviewed paths were `interfaces/http.py`, `interfaces/mcp_http.py`, `interfaces/mcp_stdio.py`, binding parsing, `application/bound_tools.py` and the associated role and task authorization methods. The operator roster assigns a binding to the exact authenticated principal/grant pair. Every remote POST authenticates the bearer, including initialize and discovery. Dispatch gets the runtime from that HTTP request, checks the available tools and argument schema, then the application method rechecks current business authority.

| Review finding | Correction and verification |
|---|---|
| The shared MCP error mapper added retry fields to a legacy stdio result. Main returned exactly one code in both the text content and `structuredContent.error`. A caller comparing whole structured errors could reject an otherwise valid refusal. | `a918a91` limits the new retry guidance to the request-resolved remote server. In a real role-bound stdio child two workers waited in PostgreSQL, verified using their blocking PIDs. A third SDK call returned `{"error":{"code":"BACKPRESSURE"}}` and the single text item `BACKPRESSURE`. The two original reads completed against the full role oracle after unlock. |
| The programmatic app factory retained its caller's mutable roster for REST while the MCP mount copied it. Reusing or clearing the mapping after startup could drop a narrower REST branch ceiling. | `a918a91` takes one startup snapshot shared by both adapters. The mixed TCP test clears the caller's mapping before any requests, then checks denied foreign-branch create/read/cancel, all-or-none batch results, and the original foreign task's READY state. An unchanged file-provisioned deployment already kept its roster private. |
| Denials and protocol version handling differ by layer. | Two simultaneously initialized SDK sessions bound a character actor and a writer to different frozen revisions and branches of the same book. Both contexts equaled their complete PostgreSQL oracles. The actor received an empty fact set and the writer a FACT. Cross-role metadata reads returned 403, MCP tool denials contained only their codes, and client-supplied alternate WorldRefs failed argument validation. An authorized but unregistered bearer received 403 at the remote mount. After revocation the actor received 401 and the writer retained its original context. SDK 1.29.0 negotiated 2025-11-25. A raw initialize negotiated the supported 2025-06-18 version, and an unknown subsequent protocol-version header received 400. |
| Remote overload and retry remain explicit. | The real TCP test filled a grant's durable capacity, then submitted a second command over REST and remote MCP together. REST returned 429, retryable and Retry-After 1. MCP returned an ordinary error tool result with code, retryable and retry_after_ms 1000. After cancelling the original task, REST accepted the retried command and the remote SDK retrieved its identical receipt. |

Ordinary MCP task operations have the installed work/branch ceiling and require the kernel grant. On REST the same task operations with an installed task-operations binding use that ceiling. The private MCP roster is an additional restriction on its named bindings. Existing REST-only worker claim/result and other domain routes keep their own native kernel authorization. Role-bound context and WorldRef checks still run in the application, independently of REST/MCP transport selection. Discovery on the fixed stdio server preserves the original empty list on a failed authorization or capacity check. A client cannot diagnose the cause from an empty list alone.

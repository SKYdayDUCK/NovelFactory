## 2. 剩余瓶颈

初始世界重复构造已明显减少，200 热点后续诊断中只执行一次。剩余观测集中于 revision 读取、JSON 解码/严格校验、query sampling、Context 与认证/查询准入等待。阶段计时重叠，不能相加，也不能仅凭总 CPU 定因。

固定回包校准四次真实 header-start 约 197–241/s，单客户端进程约用满一个核；正式服务仍有大量 429 和传输失败。校准不证明服务能处理 1000/s，计划速率也不是实际测量。

600 秒探针提供了独立服务容量证据：008fccf 两次均完整发出 12000、实际约 20/s，仍有 844/58 个 429，全部来自 query/world admission 等待超时；认证和 ingress 均通过。这不能归咎于客户端未发足。不同 runner CPU 下差异显著，持续查询执行和预算仍需处理。

没有足够证据认定数据库锁是唯一瓶颈。采样可能漏掉短等待；SQL cursor 不含结果解码，连接获取含 pre-ping/connect，事务计时止于 commit/rollback 前，均按各自定义解释。

## 3. 下一轮工程顺序

1. 固定客户端/服务/数据库各自 CPU、内存、连接预算；用多进程或专用节点校准真实 1000/s。保留原发送器对照，不变更请求分母、载荷和有效响应验证。
2. 对 revision JSON、指纹、query sampling、Context 做可重复配对；任何不可变结果复用需绑定完整语义身份，并回归权限、代际、历史和回滚边界。
3. 在原队列/超时/重试预算下重复 50/200 四格；业务、正确性、首试、实际到达同时满足才关闭 PR2 阻断。不能只增大容量参数。
4. PR2 全部门槛通过后重新核对 HEAD/审查/CI，用连接器 merge commit；得到 merged=true 和新 main SHA 后才将 PR3 base 改为 main。
5. PR3 针对新 main 重跑工程、迁移、PITR、500/1000/长探针，并测 API+派生工作者共同预算。继续复用 P2 内核和调度，不新建第二套系统。
6. 生产体量、多小时演练、真实模型和人工文学分别验收；通过前保留未执行/未评价标签。

这些是待验证方向，不是已实施功能或容量承诺。如用户希望在现有 NOT_MET 下调整合并范围，需新的明确批准；本轮没有采用该例外。

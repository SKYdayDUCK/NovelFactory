# P0/P1 环境与依赖验证

## 实际环境

本轮运行于 Debian GNU/Linux 13（trixie）、x86_64、Python 3.12.14。
环境提供 9 个逻辑 CPU，内存总量约 9.73 GiB；具体硬件、可用内存、磁盘及依赖许可证元数据见
交付证据中的 `environment/environment.json`。硬件读数是本次运行环境，不能推断生产部署容量。

运行账号无 root/sudo，未安装 Docker。通过 Debian 官方发布目录下载并校验 PostgreSQL 17.11
三个二进制包，使用 `dpkg-deb -x` 解压到独立目录。包 URL、字节数与 SHA-256 已保存在
`environment/postgresql_download.json`；复现入口为 `scripts/bootstrap_pg17_debian.py`。

数据库真实启用 `fsync=on`、`synchronous_commit=on`、`full_page_writes=on` 和数据页校验。
测试实例 `max_connections=60`、`shared_buffers=128MB`，仅监听 loopback TCP。

## 环境限制及已解决路径

当前执行器禁止 AF_UNIX socket，不同命令执行会话拥有不同网络命名空间。
因此“前一条命令启动 PostgreSQL，后一条命令连接”无法工作。这两种失败均留存原始记录，
没有把失败当成数据库业务测试通过。

`scripts/with_postgres.py` 在同一命令中启动真实 PostgreSQL、等待就绪、创建隔离库、
注入测试连接配置，再执行迁移/pytest/恢复/HTTP 子进程，最后正常停止数据库。
这一方式允许测试进程使用多个独立连接、多个并行子进程和第二个恢复数据库；没有使用 SQLite
或内存数据库替代事务语义。默认每次创建新集群；`--data-dir` 仅复用带专用测试标记的目录。

仅包含生成测试数据的临时实例使用 loopback trust；不提供将该认证方式用于生产的配置。
Docker Compose 给出独立开发账号与显式示例密码，仅绑定 127.0.0.1。
镜像 `postgres:17.11-bookworm` 的 Registry manifest 已核查并固定 digest；本机没有 Docker，
因此不能将 Compose 路径称为已执行。已执行的是本地 PostgreSQL 二进制路径。

## 资源预算与目标接入

默认一个 API 进程采用池大小 8、overflow 0；一个独立 worker 池预算 4；维护预留 16，
配置总上界为 28，小于 PostgreSQL 的 60。增加 API/worker 进程时需要重新计算。
HTTP `ConnectionBudget` 在启动时核验所有声明进程的上界，并将认证与业务请求的并发之和
限制在单进程连接池内。实际连接占用、限流、排队和 10/50 Agent 结果由 P1 负载证据给出。

本轮目标 Host 是受控 HTTP 客户端与 Python 应用服务。未接入外部付费模型、原生 MCP Host、
Claude Code 或完整 Codex 运行时；这些兼容性不计入本轮实际通过项。P0/P1 的范围允许保留
MCP 扩展位置而不实现完整协议适配。

## 原设计检查器的工程化调整

P1 安装 wheel 后，原 `validation/validate_package.py` 的全目录 `rglob` 会同时扫描
`.venv/site-packages` 内复制的契约文档，产生 8 个相对源码链接误报。原始失败记录保留于
`schema_validation/final_original_package.*`。本轮仅将三个递归入口改为统一源目录遍历，
剪除 `.venv`、`.git`、标准缓存、`.runtime`、`build`、`dist`、`node_modules` 等生成目录；
未修改 Schema、业务用例、反例、原文链接或验证目标，也未移动 P0 标签。

修复后 `final_original_package_clean.*` 实际退出 0，58 正例、31 反例、14 个基线哈希和
60 个案例来源哈希均通过。`checker_scan_regression.py` 与对应原始记录确认 `.agents`
技能仍在扫描范围内，真实源码的缺失链接及损坏 JSON 仍被拒绝。该工具回归不计入业务 pytest 数量。

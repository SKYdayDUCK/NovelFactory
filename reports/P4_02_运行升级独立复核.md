# P4-02｜运行升级独立复核与加固

## 结论

对 `RuntimeUpgradeService` 的现有实现进行第二名开发 Agent 的独立代码复核，发现并修复三个具体问题：可信产物证据缺少完整性核验、局部分支授权可能修改作品全局模型路由，以及同幂等键并发注册缺少串行化。实际 PostgreSQL 17.11 回归 **22 passed，5.04 s**，Ruff 通过。

这次复核及测试覆盖已实现的“语义相同、仅包版本元数据变化”的有限升级流程。世界规则值、reducer、日历和谓词含义变化仍返回 `UPGRADE_REQUIRES_REPAIR`，没有把历史重放通过解释成任意新解释器都可以替换。真实模型供应商、未来 schema 迁移及跨版本语义转换需分别验收。

## 修复的问题

### 1. 证据必须同时对应数据库载荷和对象字节

`Kernel.artifact` 只校验数据库中引用身份及 kind，调用者还应检查实际对象。新增统一 `_payload` 检查：

- 对象存在且字节哈希等于引用 SHA-256。
- 数据库中的结构化载荷 canonical hash 等于同一个 SHA-256。
- kind 与作品身份符合请求。

准备包、审核包、激活包与审批、原规则/解释包、模型选择记录均使用该检查；读操作持有对象共享锁。激活时也重验审阅过的原规则和解释包，避免在原证据丢失后推进 HEAD。

八个反例分别移除或损坏升级包、审批、源规则、源解释的对象文件。每次激活均拒绝，HEAD 和接受回执不变；修复对象字节后，同一审批与请求能够继续执行。另有源包缺失的 prepare 拒绝、模型路由对象损坏的读取拒绝用例。实验仅作用于隔离测试集群生成的对象，并在每例结束时恢复。

### 2. 全局模型路由必须具备 canon 范围

模型默认路由是作品级选择。新的 `select_model` 修改须绑定当前 canonical HEAD，并再次在作品 UPDATE 锁内校验；只有候选分支 ADMIN 权限不能改写全局选择。读取默认路由也要求 canonical 分支授权。旧 HEAD 上的新请求返回 `HEAD_CONFLICT`。

同一已成功请求的回执仍在新 HEAD 检查之前恢复，所以网络响应丢失后不会因世界后来推进而失去幂等恢复能力。既有任务的 `AGENT_INPUT` 保留原 adapter 和配置指纹，后续任务才使用新的选中路由；同一 adapter ID 携带不同配置仍拒绝。

### 3. 同幂等键并发注册可收敛

prepare 的产物登记和 review 事务在授权前先获取作品 UPDATE 锁，与 activate、模型选择和 canon 提升的锁顺序一致。多个并发请求在锁内重新检查回执，返回同一产物，不暴露唯一索引冲突，也不升级已经持有的 shared 锁。

并发测试使三个 prepare 请求在重放点同时进入登记阶段，再并发提交三次 review。数据库最终各有一个升级包、一个审批，三个调用方分别拿到相同引用；复用幂等键提交不同审核内容仍返回 `IDEMPOTENCY_MISMATCH`。

## 已核对的既有不变量

新修订沿用原世界时间线、不可变选中事件与快照；升级创建新 WorldRef 和 interpretation epoch，保留原规则、解释、事件及任务输入。独立审核人与准备者不同，激活前重新检查双方 grant epoch、canonical HEAD、原解释版本、投影和 manifest 哈希。旧提交证书会失效，已有正式接受回执仍可恢复。升级事务不额外应用世界效果。

这些是有针对性的代码与事务复核，不表示已穷尽所有安全问题，也不代表真实模型运行或文学质量验证。

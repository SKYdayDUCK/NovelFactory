# P5 事件唤醒、执行槽位与公平调度

## 接管时的行为

基线 `73cdc997` 已经把 AND/OR 边、Outbox、Inbox、任务代际、Grant 和调用回执写入 PostgreSQL。原服务在 `run_once` 内同步等待一次模型结果，空闲时默认每秒重新扫描。同一实例无法让两个独立角色的模型调用重叠，也没有跨实例共同执行的容量规则。

## 运行路径

迁移 `0007` 在 Outbox 新增任务变化、世界接受、撤权或连续性发布记录时，以及首次登记模型任务、归还槽位和修改额度时，发送一个无正文的数据库通知。同一事务的多个提示可合并。服务用专用 AUTOCOMMIT 会话提交 LISTEN 后，开启新的短事务读持久状态；收到提示后一律重新检查任务资格。模型线程不共享活跃数据库事务。断开通知连接会触发重新订阅和持久复核，正常情况下最长每 60 秒做一次维护；服务重启时立即复核。AND/OR 仍依赖确切上游代际的接受记录，重复提示不能代替该记录。[PostgreSQL 17 LISTEN](https://www.postgresql.org/docs/17/sql-listen.html) · [事务提交与通知](https://www.postgresql.org/docs/17/sql-notify.html)

每个实例用 `--workers N` 限定实际 Host 任务，默认 2，上限 16。一个协调线程只向有空位的线程池提交已领取任务。领取与槽位记录共用现有队列短锁和一次事务。单任务保留原 TaskSpec、grant、lease、execution attempt 和 generation。任务进入等待后无需 Host。普通完成或执行异常按本次 attempt 归还槽位；进程突然消失时，槽位在领取后 900 秒到期，与任务租约一起重新评估。已发送而结果未知的调用继续受调用账本围栏保护。每项调用仍需先获得既有资金及 token 预留。

多个服务共享 `nf_dispatch_limits`。数据库中的全局、作品、岗位额度各自生效，同时还受本机可用线程数限制。数据库默认三类上限各为 2，新任务只有在三者均有余量时才能领取。部署管理员可以在迁移后的数据库内调整配置，例如下列语句把整个数据库上限设为 6，并将角色行动者在所有作品中的合计上限设为 3。若作品默认仍为 2，同一作品最多占用 2 个槽位。

```sql
UPDATE nf_dispatch_limits SET slots = 6 WHERE scope = 'GLOBAL' AND subject = '*';
INSERT INTO nf_dispatch_limits (scope, subject, slots) VALUES ('ROLE', 'character_actor', 3)
ON CONFLICT (scope, subject) DO UPDATE SET slots = EXCLUDED.slots;
```

`WORK` 可按具体 work UUID 覆盖默认值。设置为 0 会暂停该范围内的新领取。每个有 READY 模型任务并有服务请求领取的分支登记一个限时票据。最早请求的合格队列优先，领取一次即让位。组内优先安排上次服务最早的任务类型，再按创建时间和任务 ID 排序。各岗位的运行模式在当前目录中互不重叠。达到岗位或作品上限的任务会被跳过，其余作品和岗位可以使用剩余槽位。服务消失后遗留的等待票在两分钟内失效。该机制保证持续到访的合格队列有领取机会，不估计任务时长或抢占已发出的模型调用。

## 验收与边界

| 反例 | 验证对象与结果 |
|---|---|
| Outbox 回滚、重复提示 | 事务提交前及回滚后均无提示。提交登记唤醒任务，人为重复 NOTIFY 后重复恢复返回 IDLE，合成上游只接收一次请求。 |
| 两个独立服务进程争三个任务 | 两个模型请求同时进入可控上游，两个不同任务拥有两个数据库槽位。第三个服务获取 IDLE。放行后第三项执行，每项只有一份调用记录。 |
| 两个作品及岗位的等待次序 | 岗位上限设为零，两个作品均等待。开放额度后，后来排队的作品先尝试仍不能插队。将前一个作品额度设为零后，另一个作品继续完成。 |
| 两个真正并行的角色 Host | 真实 Codex app-server 的 A 和 C 同时进入合成 HTTPS 回调。双方回调通过同一双向屏障观察到两个不同的存活进程，任务均 RUNNING，B 与卷导演均 BLOCKED。最终 8 个不同 Thread/Turn 全部完成，等待调用为零，联合位置效果只接受一次。[原始记录](../evidence/p5/scheduler/banquet.json) |
| 缺失通知、长时间空闲、连接中断 | 实际服务默认等待间隔为 60 秒。观察期内服务池无 SQL、无未提交事务、无模型调用和空任务。登记后在维护周期前完成任务。终止其 LISTEN 后端并再次登记，服务在原进程重建订阅后完成第二项。[实测时间](../evidence/p5/scheduler/idle.json) |
| 服务/提供方中断 | 进程在提供方已收请求后被终止。重启围栏将调用记为 UNKNOWN，重复恢复没有重发。覆盖已结算未交付的情况。 |
| 迁移与回退 | 0003→head→0003 空扩展往返保留原有数据。0007 新增三个管理表及通知触发器，无历史事件回填。安装触发器会短暂锁住相应关系，部署时应排空旧版服务。回退先停止领取并等待或核对旧槽位，单独保留自定义额度；迁移拒绝静默丢弃有效槽位或自定义策略。 |

默认只运行一个监听连接，每实例按 `max(5, workers+2)` 配置事务连接池。跨实例部署应核算数据库的总连接数。NOTIFY 频道属于同一数据库，其他活跃作品会唤醒监听服务做一次复核。实测覆盖小规模并发和有限空闲窗口，尚未量化大量同时在线作品下的通知放大。槽位统计面向已注册的 P5 Supervisor 流程；供应商侧实际用量需要独立对账。测试 HTTPS 端点输出确定性内容，真实付费账单与原 P2/P3 200、500、1000 档容量指标保留各自验收口径。

## 领取时的行锁竞争

真实 PostgreSQL 上，另一个事务锁住同作品最早 READY 任务时，原调度器返回 IDLE，第二个可领取任务没有执行。现在公平选择与内核领取在同一事务使用一致的跳锁规则。测试持有第一行的更新锁，断言第二项在锁释放前完成且上游只收到一次请求。调度、Supervisor、场次接续与多角色端到端组共 15 项通过。[回归记录](../evidence/p5/scheduler/claim_contention.xml)

## 超时及跨卷终态的恢复

已登记的 READY 任务在首次领取前到期时，恢复事务现在把它置为 FAILED，持久记录 DEADLINE_EXCEEDED。同次恢复可以关闭因该前驱失败而无法唤醒的 AND 等待。回归检查两项终态、各自原因、重复恢复不增加记录及零次模型调用。有历史调用记录的任务仍按现有对账流程处理。

已发布的连续性启动下卷规划后，若规划任务被取消、失败或过时，卷指针进入终态，并保存带 task_id 和具体状态的停止回执。测试通过任务持有者的正常取消接口终止 READY 规划，复核停止回执恰好一份、再次调度空闲、没有上游调用且历史未改写。调度、工作流和跨卷组共 19 项通过。[真实 PostgreSQL 回归](../evidence/p5/scheduler/terminal_recovery.xml)

# W6 预设、跨服务与容量的验收入口

W6 接续 W5 主线 `b30e76978830bec4c596c04194d749fd01f67402`。原有 PR #15 的提交和后续资格验证提交保留在历史中。原始预设、容量与恢复证据来自 `34e4e7658b8a6dba7055a6cab1c1a55971176bba`，原生双 SSH 入口来自 `73050eab6c5b64b79e58d6d1db3931148cf61e83`。本页列出候选与合并后必须执行的检查。

| 范围 | 可复现入口 | 验收依据 |
|---|---|---|
| 安装和服务归属 | `workshop/scripts/verify_installed_wheel.py`、`workshop/acceptance/dual_codex/run.sh` | 在源码树以外使用构建的 wheel，安装目录中加载固定目录和迁移。一个原生角色线程分别连接 NF、Workshop，核验用户、集群 ID、绑定隔离、工具范围和零模型轮次。 |
| 已部署数据库 | `workshop/acceptance/test_w6_historical_upgrades.py` 与既有 W0–W5 升级套件 | 以各自发布代码建立并填充旧库。从签收的 W5 和七个 W6 变体升级，核验单一版本、既有员工历史与授权、一致的委托账本。 |
| 预设岗位 | `workshop/tests/test_preset_fences.py` | 分别检查职位新增与复职时主管的实际职务、修复层级后的合法扩编、预览与执行和版本栅栏。 |
| 跨服务场景 | `workshop/benchmarks/cross_service_scene.py` | Minimal、Standard、Long-form、Research-Audit，真实数据库和 stdio 进程，把受限委托、角色行动、独立审核、回执及账本关联到该场景。 |
| 员工目录和故障 | `workshop/benchmarks/actor_directory_isolation.py`、`workshop/benchmarks/running_workshop_outage.py`、`workshop/integration/` | 检查组织目录与角色 BELIEF 及提示词的隔离、NF 已发送后 Workshop 离线、恢复后对账、Redis 恢复及双库物理恢复。 |
| 10、50、200 员工 | `workshop/benchmarks/message_capacity.py`、`workshop/benchmarks/delegation_capacity.py` | 每人三条消息。逐档检查发送/确认 P99、重复、确认数和重建时间。另在 fixed-1、fixed-2、adaptive-2 九个组合分别记录完成、重复、未结预留、合成请求和耗时。 |
| NF 主线回归 | P1 CI、P2 measured capacity、P3 scale、P3/P4 measured evidence、P4 physical recovery | 保留各轮原始结果、失败和重试。AT-30 四组历史未达标继续跟踪 [Issue #13](https://github.com/SKYdayDUCK/NovelFactory/issues/13)。 |
